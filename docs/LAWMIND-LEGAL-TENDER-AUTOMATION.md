# 法律服务招投标全自动化：市场、流程、技术栈与 REA 计划

> 日期：2026-10-27
> 范围：中国法律服务采购（政府采购 / 公共资源交易 / 国企·金融机构律所库 / 企业 RFP）为主，全球法律提案与 B2G 工具为辅。
> 方法：GitHub API 检索 + 商业产品公开资料 + 法律采购流程拆解 + 现有可复用模块对照 + REA 目标评估。
> 边界：本文是调研与设计，不含代码改动；厂商自述的数字一律标注为“厂商口径”，不当作独立验证事实。
> **立场：本文不预设 LawMind。** 目标是设计一条可自建、可采购、可开源组合的法律服务自动投标流水线；LawMind 只在“中标后交付、证据、案件运行”明显更合适时作为候选组件，不是前提。
> 关联：`docs/LAWMIND-REA-TARGET-MAP.md`（REA 边界）、`docs/LAWMIND-OSS-WORKFLOW-REA.md`（合法吸收方法）、`docs/LAWMIND-ACCEPTANCE-LAYER-STRATEGY.md`（采信层）、`docs/LAWMIND-DELIVERY.md`（交付）。

## 0. 一页结论

**一句话：法律服务招投标的“写标书”正在商品化，真正稀缺的是“证据、合规、提交、交接”四层；我们要自建的是这四层的编排与数据，而不是再做一个 AI 标书生成器。**

八个判断：

1. **市场足够大，但价值不在生成。** 中国有大量通用 AI 标书工具（星火投标、钛投标、文兜智写、小羊标书、快标书等），开源侧也有 3k+ star 的 `OpenBidKit_Yibiao` 和 400+ star 的 `BidMaster-Pro`。它们证明“解析招标文件 → 生成标书 → 检查废标项 → 导出 docx”技术上可行，也证明这一层价格会被打到很低。
2. **法律服务的标书与工程/货物标书不同。** 法律服务卖的是人和经验，评分里价格权重通常只有 10%–30%（服务类政府采购），技术/商务分主导；真正决定中标的是“同类业绩、团队配置、服务方案、响应能力、本地化、利益冲突与保密”。因此通用标书工具的“技术参数响应”模型不够用。
3. **律所最大的瓶颈不是写作，是找不到可信的经验数据。** ikaun 2026 年对 Am Law 100/200/NLJ 500 的调研（厂商口径）显示：69% 的律所提案量上升、86% 仍是手工或手工+工具混合、74% 没有单一且最新的案件经验真相源、只有 27% 在提案中使用 AI，且主要用于起草。这个结论与中国律所的体感一致：业绩、简历、证书、案例散在合伙人电脑、行政台账和历史标书里。
4. **“全自动投标”要分层定义。** 可实现的是 L3：招标发现、解析、资格判断、证据检索、初稿、合规检查、排版、打包全部自动，**提交由具名律师一键签批**。不建议追求 L4 无人值守提交：CA 数字证书、电子签章、授权代表、报价决策、利益冲突、虚假材料责任都不允许把责任交给模型。
5. **中标不是终点，而是整条流水线价值最高的地方。** 标书里的每一句承诺——人员、响应时限、服务范围、报价、增值服务——都是中标后的交付义务。通用标书工具在提交那一刻结束；我们要在合同签订后把标书解析成交付计划、整包清单和履约台账，形成“投标承诺 → 交付义务 → 验收证据”的闭环。承接层可以自建，也可以用 LawMind。
6. **后半段已有可复用的地基，且不限一家。** 开源侧有 OpenBidKit/BidMaster 的解析、生成、检查、排版；商业侧有 ikaun/Loopio 的内容库与审批；LawMind 侧有 `src/lawmind/intake/`（收件、收案、冲突、字段出处）、`src/lawmind/platform/matter-run.ts`（可恢复步骤）、`src/lawmind/delivery/packet.ts`（整包交付）、`src/lawmind/drafts/evidence-anchor.ts`（证据锚）。缺的是投标域（Pursuit）本身，以及把这些组件编排起来的那一层。
7. **商业闭源产品值得 REA，但只能吸收行为规格。** 优先拆：小羊标书（上传→解析→生成→合并→电子签→远程投标）、钛投标（解析字段、废标识别、排版）、星火投标（投标要素图谱）、AutogenAI（qualification→submission 全流程）、ikaun（法律经验管理与 bid/no-bid）。不拆云端大脑、不搬代码/提示词/文案、不绕 CA 与登录。
8. **建议的建造顺序是反直觉的：先做“编排层 + 证据库 + 合规闸门”，再做“生成”。** 生成、解析、OCR、排版都可以买或借；证据库、合规闸门、中标交接决定客户敢不敢用、能不能收费。

### 0.1 价值分布

| 层           | 现在谁在做                                           | 商品化程度 | 自建/组合机会                                    |
| ------------ | ---------------------------------------------------- | ---------- | ------------------------------------------------ |
| 招标信息检索 | 千里马/剑鱼/比地等数据商、爬虫脚本、通用 AI 标书工具 | 中         | 中：合规源 + 法律法域过滤 + 截止期/变更跟踪      |
| 招标文件解析 | 通用标书工具、OCR/RAG                                | 中         | 高：法律服务评分项、废标条款、资格条件、合同风险 |
| 标书生成     | 大量开源与商业工具                                   | **高**     | 低：只作为入口，不作为卖点                       |
| 律所证据库   | 律所手工 Excel/共享盘/记忆                           | **极低**   | **极高：业绩、简历、证书、排名、保险、可引用性** |
| 合规检查     | 通用工具做废标项、格式、查重                         | 中         | 高：法律特有资质、利益冲突、保密、电子投标       |
| 提交         | 人工 + 平台客户端 + CA                               | 低         | 中：辅助清单、文件包、回执；不做无人值守         |
| 中标后交付   | 律所手工交接                                         | **极低**   | **极高：标书承诺 → 交付计划 → 整包清单**         |
| 复盘与定价   | 手工、少量 BI                                        | 低         | 高：中标/落标数据、报价模拟、panel 续约          |

> 结论：不要在“写得更快”上竞争；要在“写得更可信、交得更完整”上竞争。

### 0.2 技术路线：自建编排，组件可换

**三条原则：**

1. **编排层自建**：投标域的数据模型、状态机、证据链、合规闸门、交接契约必须自己掌握；这是差异化的来源。
2. **商品层能买就买、能借就借**：招标数据、OCR、LLM、DOCX 渲染、电子签、云存储优先用成熟组件；不重复造轮子。
3. **闭源产品当“规格源”**：能买 API 就买；不能买就用 REA 吸收行为规格，自建实现；不把运行时绑死在单一闭源产品上。

**四种可选栈：**

| 栈                         | 组成                                                                                                         | 适合             | 风险                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------- | -------------------------------------------- |
| A. 全开源轻栈              | TenderCrawler（MIT）+ pdfplumber/PaddleOCR + OpenBidKit/BidMaster（AGPL，仅验证/内部）+ officecli + 自建编排 | 快速验证、私有化 | 解析/合规质量要自己补；AGPL/许可证需法务确认 |
| B. 商业 API + 自建编排     | 数据商 + 商用 OCR/LLM + 自建编排 + officecli                                                                 | 想快、有预算     | 数据/模型供应商锁定；合规审查                |
| C. 自建投标 + LawMind 承接 | 自建 Tender/Pursuit/Bid 层 + LawMind 的 MatterRun/DeliveryPacket/证据锚                                      | 中标后交付是重点 | 需要打通对象模型与部署                       |
| D. 混合                    | 数据商 + 开源解析 + 商业生成 + LawMind/自建交付                                                              | 大多数团队       | 集成复杂，需要清晰接口                       |

> 本文后续以“自建编排层”为主语；第 5 节给出各组件的开源/商业/LawMind 选项，LawMind 只是其中一列。

### 0.3 第一版建议：不买大而全，先拼一条能跑通的流水线

| 层     | 第一版选择                                               | 为什么                             |
| ------ | -------------------------------------------------------- | ---------------------------------- |
| 采集   | TenderCrawler（MIT）+ cebpub/ccgp + 人工上传             | 先验证需求；数据商只在覆盖不足时买 |
| 解析   | pdfplumber + PaddleOCR；扫描件用商业 OCR                 | 成本低、可控；OCR 准确率用商业补   |
| 生成   | 自建编排 + 商用 LLM API（Claude/DeepSeek/Qwen）          | 不嵌入 AGPL 代码；模型可换         |
| 排版   | officecli + 自建模板                                     | DOCX 是交付格式，不是编辑回路      |
| 证据库 | **自建**（资质、人员、业绩、证书）                       | 核心护城河，不能外包               |
| 合规   | **自建**法律目录 + 规则引擎                              | 法律特有，通用工具不够             |
| 工作流 | 自建轻量状态机；复杂再上 Temporal                        | 先跑通，不引入重框架               |
| 交付   | 先自建 `BidPromise → Obligation`；LawMind 作为可替换实现 | 不被单一产品锁定                   |
| REA    | 先做 1–2 个：小羊标书、钛投标或星火投标                  | 拿字段/状态机，不拿代码            |

**一句话：第一版用“MIT 采集 + 自建解析/证据/合规 + 商用模型 + officecli”，LawMind 和商业 SaaS 都作为后续可替换组件，不作为第一天的前提。**

### 0.4 工程组织结论

- **另建工程，独立 repo**，不把投标做成 LawMind 的一个页签；只通过 `AwardHandoff` 等五个契约与 LawMind 深度配合。
- **全栈自研 = 自有核心 IP**（数据模型、编排、证据、合规、UI、评测）；LLM/OCR/PDF 库/工作流引擎可买可借，但接口可替换。
- **REA 只吸收行为规格**（字段、状态机、校验、错误码），不搬代码/提示词/文案；闭源商业产品不能靠“吸收代码”做全栈自研。
- 团队 < 5 人且前 6 个月只服务 LawMind 客户时，可用同一 monorepo 的两个 app，但仍保持独立部署；否则直接独立 repo。

## 2. 法律界怎么做法律服务招投标

### 2.1 两个市场，两套打法

| 维度         | 公共采购市场                                                        | 企业/机构市场                                          |
| ------------ | ------------------------------------------------------------------- | ------------------------------------------------------ |
| 典型买方     | 政府机关、司法局、街道、事业单位、公共资源交易中心                  | 国企/央企、银行/保险/AMC、高校/医院、园区、大型民企    |
| 采购方式     | 公开招标、竞争性磋商、竞争性谈判、询价、单一来源、框架协议/定点采购 | 律所库（panel）入库、RFP/RFI、比选、直接委托、框架协议 |
| 规则强度     | 高：招标投标法、政府采购法、87 号令、电子招标投标办法               | 中：买方内部采购制度、供应商管理、合规审查             |
| 评分         | 综合评分法为主；服务价格权重通常 10%–30%                            | 质量/经验/关系/价格综合；panel 更看长期能力与费率      |
| 周期         | 公告到截止通常 20 日左右；竞争性磋商更短                            | 数周到数月；panel 按年度/两三年刷新                    |
| 电子化       | CA、电子签章、投标文件制作软件、加密上传、不见面开标                | 邮件/采购系统/供应商门户；电子签逐步普及               |
| 中标后       | 合同备案、履约、验收、审计                                          | 框架协议、SLA、季度/年度复盘、panel 续约               |
| 对 AI 的约束 | 形式合规、材料真实、电子签名、投标主体资格                          | 保密、利益冲突、客户同意、品牌与关系                   |

**判断：** 公共采购是“规则密集型”，适合自动化和合规检查；企业 panel 是“关系+经验密集型”，适合证据库、知识复用和客户经营。两类都要支持，但产品入口不同：公共采购从“招标雷达”进，企业市场从“RFP/panel 收件箱”进。

### 2.2 买方流程（理解评分逻辑）

1. **需求立项与预算**：法务/办公室提出年度法律服务需求，确定预算与采购方式。
2. **采购方式选择**：达到公开招标限额的走公开招标；未达到的可竞争性磋商/谈判/询价；经常性服务走框架协议/定点采购。
3. **编制招标文件**：投标人须知、资格条件、采购需求、评标办法、合同条款、投标文件格式。
4. **发布公告**：政府采购网/公共资源交易平台/买方门户；售卖或免费下载招标文件。
5. **答疑与澄清**：投标人提问，采购人统一书面答复；答复可能改变实质性要求。
6. **投标与开标**：纸质密封或电子加密上传；截止时间后不接受。
7. **资格审查/符合性审查**：营业执照、执业许可证、授权书、保证金、签字盖章、实质性响应。
8. **评标**：评标委员会按评标办法打分；法律服务常见“综合评分法”。
9. **澄清/说明**：评标委员会可要求澄清，但不得改变实质性内容。
10. **定标/公示/中标通知**：公示期、质疑投诉、中标通知书。
11. **合同签订与备案**：合同不得背离招标文件实质性条款。
12. **履约与验收**：服务期、SLA、考核、付款、审计。

### 2.3 卖方流程（律所实际怎么投）

| 阶段              | 谁在做                  | 产出                             | 典型痛点                                   |
| ----------------- | ----------------------- | -------------------------------- | ------------------------------------------ |
| 1. 信息发现       | 市场部/BD、合伙人、行政 | 招标公告、RFP、panel 通知        | 来源分散、重复、错过截止、不知道谁在投     |
| 2. 资格预审/报名  | BD/行政                 | 报名表、资格材料、保证金         | 资质过期、授权书模板错、报名平台账号       |
| 3. 获取招标文件   | BD/行政                 | PDF/DOCX、附件、图纸             | 文件收费、平台下载限制、版本变更           |
| 4. 读标/拆标      | 合伙人+律师+BD          | 评分表、废标条款、需求清单       | 100–300 页、时间紧、漏项、评分项理解不一致 |
| 5. 投标决策       | 合伙人/管委会           | 投/不投、报价策略                | 冲突、产能、胜率、利润、客户关系           |
| 6. 组建团队       | 合伙人                  | 项目负责人、律师、助理、外部专家 | 人员档期、简历过期、无法承诺投入           |
| 7. 编标           | 律师/BD/投标专员        | 商务标、技术标、报价标           | 重复劳动、业绩找不到、方案同质化、格式反复 |
| 8. 内部审核       | 合伙人/风控/财务        | 复核意见、报价审批               | 多轮改稿、版本混乱、责任不清               |
| 9. 用印/签字/密封 | 行政/合伙人             | 盖章、签字、密封件               | 漏签漏盖、骑缝章、授权书日期               |
| 10. 递交          | BD/行政/律师            | 纸质件/电子件、回执              | 截止前堵车、CA 故障、平台崩溃、文件过大    |
| 11. 开标/澄清     | 合伙人/BD               | 开标记录、澄清答复               | 报价泄露、澄清超时、授权代表不在           |
| 12. 中标/落标     | BD/合伙人               | 中标通知书/结果公告              | 复盘缺失、经验不沉淀、交接断层             |

> 关键观察：律所的“投标生产线”通常没有系统，靠人盯、Excel、共享盘和微信。真正的时间黑洞是第 4、7、8、12 步，而不是“写字”本身。

### 2.4 一份法律服务标书通常有什么

| 分册     | 内容                                                                                                      | 常见评分/废标点                                                   |
| -------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 资格文件 | 营业执照、律师事务所执业许可证、法定代表人身份证明/授权书、信用中国查询、无重大违法记录声明、保证金/保函  | 证件过期、名称不一致、授权书缺签字/盖章、保证金未到账             |

### 2.5 评分机制：价格不是主角

政府采购服务类项目通常采用综合评分法。按《政府采购货物和服务招标投标管理办法》（财政部令第 87 号）的口径，服务项目的价格分值占总分值比重通常不得低于 10%，货物项目不得低于 30%；具体上限由采购文件规定。实际法律服务项目常见结构：

| 评分块 | 常见权重 | 典型子项                                                                     |
| ------ | -------- | ---------------------------------------------------------------------------- |
| 价格   | 10%–30%  | 报价、费率、优惠、付款条件                                                   |
| 商务   | 20%–35%  | 律所资质、规模、排名、保险、财务、同类业绩、客户评价                         |
| 技术   | 45%–65%  | 需求理解、服务方案、团队配置、负责人资历、质量控制、保密、应急、本地化、培训 |
| 其他   | 0%–10%   | 增值服务、公益法律服务、信息化能力、绿色/ESG                                 |

价格分常见公式（最低价基准）：

$$
\text{价格分} = \frac{\text{评标基准价}}{\text{投标报价}} \times \text{价格分值}
$$

其中评标基准价通常为满足招标文件要求的最低投标报价。这个公式意味着：**价格分是相对分，降价有上限收益；技术/商务分才是差异化空间。** 对律所而言，把精力放在“可验证的同类业绩、负责人、服务方案”上，通常比压价更划算。

### 2.6 电子招投标的“最后一公里”

公共采购的电子化程度越来越高，常见链路：

1. **办理 CA 数字证书/电子签章**：律所主体证书、法定代表人证书、经办人证书。
2. **平台注册/入库**：供应商库、诚信库、CA 绑定。
3. **下载招标文件**：平台客户端或网页；部分文件需要专用制作工具打开。
4. **制作投标文件**：在平台指定的投标文件制作软件中导入、填写、签章、加密；不同平台格式不同（新点、广联达、筑龙等）。
5. **上传/递交**：截止前加密上传；生成回执；部分平台要求现场解密或不见面开标。
6. **开标/解密**：投标人使用 CA 解密；唱标；确认开标记录。
7. **澄清/二次报价**：部分采购方式需要在线澄清或最终报价。

**对自动化的含义：**

- 招标文件解析、投标文件生成、合规检查可以跨平台复用；
- **制作、签章、加密、上传是平台强耦合的**，且通常要求 Windows 客户端、CA 硬件、人工授权；
- 近期现实目标是“生成可导入平台的标准文件包 + 提交清单 + 回执归档”，不是“替律师点 CA 签名”。

### 2.7 组织与角色

### 2.8 痛点，用数据说话

ikaun 2026 年基准调研（厂商口径，样本为 Am Law 100/200/NLJ 500 的 BD/提案负责人）：

- **69%** 的律所过去一年提案量上升，**没有一家**下降；
- **86%** 仍是纯手工或手工+工具混合；
- **74%** 没有单一、最新的案件经验真相源；
- 提案最耗时的环节是**找经验和案件数据**，排在写作、定制、排版之前；
- 只有 **7%** 认为“很容易找到相关经验”；
- **76%** 至少拒绝过一些 RFP，其中 **30%** 归因于时间/资源不足；
- 只有 **27%** 在提案中使用 AI，且主要集中在起草/改写。

这些数字对中国律所同样有解释力，但中国还有两个额外痛点：

1. **电子招投标的平台碎片化**：CA、客户端、文件格式、上传规则因地因平台而异。
2. **法律服务的证据链更弱**：业绩、客户评价、案例结果往往涉及保密，不能像工程业绩那样公开复用。

### 2.9 经济性：一笔投标账

以一个 10 人律师团队、每年投 40 个标的律所为例（估算，C 级）：

| 项目          | 手工        | L3 自动化后（目标）  |
| ------------- | ----------- | -------------------- |
| 单标编标人天  | 5–15 人天   | 2–5 人天             |
| 读标/拆标     | 1–2 人天    | 0.2–0.5 人天         |
| 业绩/简历检索 | 1–3 人天    | 0.1–0.3 人天         |
| 合规/格式检查 | 1–2 人天    | 0.2–0.5 人天         |
| 废标/返工     | 每年 2–5 次 | 目标 <1 次           |
| 中标后交接    | 1–3 人天    | 0.5–1 人天（结构化） |

**判断：** 如果只卖“写得更快”，客户会把省下的时间拿去投更多标，ROI 很快被稀释；如果卖“少废标、少漏项、可交接”，价值可以直接折算成避免的损失和交付毛利。

**从开源侧能学到的五个机制：**

1. **文档解析要“多解析器 + OCR 兜底”**：PDF/DOCX/扫描件/图片；MinerU/PyMuPDF/pdfplumber。

**开源侧的空白：**

- 没有法律专用模板（政府法律顾问、银行 panel、诉讼代理、合规专项）。
- 没有律所证据模型（执业证、简历、业绩、排名、保险、可引用性）。
- 没有中国电子招投标的“制作/签章/上传/回执”适配。
- 没有“中标 → 交付”的闭环。
- 没有把“标书承诺”变成“履约义务”的数据结构。

**最重要的市场信号（ikaun 厂商口径）：**

- 律所提案量在涨，但系统没跟上；
- 最大的瓶颈是“找经验”，不是“写句子”；
- 只有 27% 用 AI，且集中在起草；

**这正好是我们的切入点（判断）：** 中国律所的取证与治理通常更依赖个人与手工，电子招投标更碎片，交付闭环更缺；这三点正好对应“证据库 + 合规 + 交接”。

## 4. 端到端流程设计

### 4.1 自动化分级

| 级别 | 定义                                    | 谁负责 | 适用                                       |
| ---- | --------------------------------------- | ------ | ------------------------------------------ |
| L0   | 全手工                                  | 人     | 现状                                       |
| L1   | AI 辅助检索/摘要                        | 人     | 招标雷达、读标                             |
| L2   | AI 生成初稿，人改                       | 人     | 标书起草                                   |
| L3   | AI 完成准备、检查、打包，人一键签批提交 | 人签批 | **近期目标**                               |
| L4   | 无人值守提交                            | 系统   | 仅限低风险、平台 API、已认证场景；近期不做 |

**L3 的定义要写进产品：**

- 系统可以自动发现、解析、组稿、检查、排版、生成提交包；
- 系统不能自动决定报价、不能自动签署/盖章、不能自动使用 CA、不能自动承诺客户；
- 提交动作必须由具名律师/授权代表确认；
- 所有自动步骤有证据、有日志、可回放。

### 4.3 关键阶段的深度设计

#### 4.3.1 招标发现：数据问题，不是 AI 问题

**源分层：**

1. **官方 API/结构化数据**：中国招标投标公共服务平台（`getStringMethod.do` JSON）、部分省级公共资源交易平台。
2. **官方 HTML**：中国政府采购网（`search.ccgp.gov.cn/bxsearch`）、地方采购网。
3. **买方门户**：国企/银行/高校/医院的供应商门户、邮件订阅。
4. **授权数据商**：千里马、剑鱼、比地等；用合同换稳定性和合规性。
5. **人工投递**：BD 转发的 RFP、微信、邮件。

**抓取纪律：**

- 优先官方 API；HTML 兜底；
- 遵守 robots/ToS；限速（ccgp 建议 ≥ 4 秒）；不绕验证码；不共享账号；
- 保存原始页面/JSON 快照、抓取时间、URL、hash；
- 变更检测：公告更正、截止期变更、附件替换；
- 字段标准化：项目编号、采购人、代理机构、地区、行业、预算、截止时间、文件获取时间、开标时间、保证金、联系方式；
- 变更检测：公告更正、答疑澄清、附件替换、截止期延长必须重新解析，并让需求图/审批版本失效；
- 时间处理：截止时间按平台时区/工作日计算，节假日和网络故障留缓冲；
- 去重键：`source + projectCode`，无编号时用 `title + buyer + publishDate` 的规范化 hash；
- 可信度：官方源 > 数据商 > 人工转发；冲突时以官方为准。

**法律服务的检索词：**

- 法律服务、法律顾问、常年法律顾问、专项法律服务、诉讼代理、仲裁代理、法律咨询、法律援助、公共法律服务、政府法律顾问、村（社区）法律顾问、企业合规、知识产权、劳动用工、破产重整、不良资产、金融诉讼、行政复议、信访、普法。
- 排除词：法律职业资格考试、法律文书送达、法律服务所（基层）、法律援助志愿者（非采购）等。

#### 4.3.2 招标解析：输出“需求图”，不是“摘要”

`RequirementGraph` 的最小字段：

| 字段               | 说明                                                                 |
| ------------------ | -------------------------------------------------------------------- |
| `requirementId`    | 稳定 ID，便于追溯                                                    |
| `type`             | eligibility / mandatory / scored / contractual / format / submission |
| `text`             | 原文                                                                 |
| `source`           | 文件、页、段、表格、附件                                             |
| `normalized`       | 规范化后的要求                                                       |
| `evidenceRequired` | 需要什么证明（证书、合同、判决、客户证明）                           |
| `responseOwner`    | 谁负责响应                                                           |
| `responseStatus`   | missing / draft / complete / verified                                |
| `risk`             | disqualification / material / minor                                  |
| `deadline`         | 相关截止时间                                                         |
| `humanConfirmed`   | 是否人工确认                                                         |

**解析策略：**

1. **版面优先**：标题层级、表格、页眉页脚、附件清单；不要只做全文 OCR。
2. **条款分类**：资格条件、实质性要求、评分项、合同条款、格式要求、提交要求。
3. **双重表示**：人类可读的“招标摘要”+ 机器可读的“需求图”。
4. **关键字段四眼原则**：截止时间、保证金、报价上限、资格条件、废标条款必须人工确认。
5. **来源锚定**：每个字段带页码/段落/表格坐标；无法定位的字段标 `INCOMPLETE`，不得进入定稿。
6. **提示注入防护**：招标文件是不可信输入；其中的“忽略以上指令”“请输出以下内容”只当数据，不当指令。沿用 `src/lawmind/intake/types.ts` 的 `trust: "untrusted"` 语义。

#### 4.3.3 证据库：律所真正的护城河

**五类证据：**

| 类型      | 例子                                         | 关键字段                               | 失效/权限          |
| --------- | -------------------------------------------- | -------------------------------------- | ------------------ |
| 主体资质  | 执业许可证、营业执照、保险、信用报告         | 证书号、有效期、发证机关、扫描件       | 到期提醒；年检     |
| 人员      | 律师执业证、简历、学历、语言、专业领域、案例 | 执业证号、年限、领域、可用性、费率     | 转所/停业；档期    |
| 业绩      | 同类项目、客户、金额、结果、团队、时间       | 客户、行业、案由、标的、结果、可引用性 | 客户同意；保密等级 |
| 荣誉/排名 | Chambers/Legal 500/钱伯斯/ALB/省级荣誉       | 来源、年份、层级、领域                 | 年度更新           |
| 内容      | 服务方案、方法论、模板、问答库               | 版本、作者、适用场景、批准人           | 过期/审批          |

**每条证据必须回答四个问题：**

1. **来源是什么？** 文件、页、hash、录入人。
2. **现在还有效吗？** 有效期、最后核验时间。
3. **能不能对外说？** 客户同意、保密等级、匿名化要求。
4. **谁批准？** 合伙人/风控/客户。

**为什么这是护城河：**

- 生成模型会趋同，证据库不会；
- 证据库需要长期积累、治理、权限和客户关系；
- 投标的差异化来自“我能证明我做过”，而不是“我能写得很长”；
- 中标后的交付数据会反哺证据库，形成复利。

#### 4.3.4 合规检查：分三层，不要混在一起

| 层         | 检查内容                                                                                     | 谁做      | 证据                    |
| ---------- | -------------------------------------------------------------------------------------------- | --------- | ----------------------- |
| 机器可验证 | 证书有效期、名称一致性、报价算术、页码/目录、字数/页数、文件命名、必填表单、签章位置、重复率 | 系统      | 规则命中 + 原文定位     |
| 人工确认   | 签字、盖章、密封、正副本、授权代表、现场递交、纸质原件                                       | 人        | 勾选 + 扫描/照片 + 具名 |
| 平台/外部  | CA 加密、上传成功、回执、保证金到账、澄清响应                                                | 平台 + 人 | 回执/截图/流水          |

**法律特有的检查项：**

- 律师事务所执业许可证、年检、执业责任保险；
- 承办律师执业证、执业年限、专业领域、是否被处罚；
- 利益冲突：投标人/关联方 vs 现有客户/对方当事人；
- 保密：客户名单、案件细节是否获得引用同意；
- 报价：是否低于成本、是否违反律师收费管理规定、风险代理是否合规；
- 合同条款：责任上限、赔偿、知识产权、解除、保密、转委托；
- 电子投标：CA 主体、授权书、签章位置、加密格式、上传回执；
- 真实性：业绩、人员、证书不得虚构；AI 生成内容必须可核验。

**检查结果分级：**

- `BLOCKER`：不修复不能提交（资格不符、缺必填、报价超上限、未盖章）；
- `HIGH`：高风险，需合伙人书面确认（实质性条款偏离、业绩不匹配）；
- `MEDIUM`：建议修复（表述不清、证据弱）；
- `LOW`：优化项（排版、措辞）。

#### 4.3.5 提交：做“辅助”，不做“代签”

**提交包清单（示例）：**

- 封面、目录、投标函、开标一览表；
- 法定代表人身份证明/授权委托书；
- 资格证明文件（执业许可证、营业执照、信用报告、保险）；
- 商务部分（业绩、团队、财务）；
- 技术部分（服务方案、质量控制、保密、应急）；
- 报价部分（报价表、费率卡、付款条件）；
- 保证金/保函凭证；
- 电子文件（PDF/DOCX/平台格式）、加密文件、CA 签章文件；
- 纸质正本/副本/密封件；
- 递交回执/快递单/平台回执。

**系统能力：**

- 生成清单并逐项勾选；
- 机器检查文件命名、大小、页数、签名/盖章占位；
- 生成 `packetHash`，确保提交后不可抵赖；
- 识别平台回执（PDF/截图/邮件），归档为 `SubmissionReceipt`；
- 截止前提醒、失败重试、异常升级；
- 记录“谁在什么时间提交了什么版本”。

**明确不做：**

- 不代管 CA PIN/密码；
- 不自动点击“签章/提交”；
- 不绕验证码/人脸识别；
- 不伪造授权代表；
- 不在没有人工确认的情况下改变报价。

#### 4.3.6 中标交接：整条流水线的真正入口

**从标书抽取 `BidPromise`：**

| 类型   | 例子                                                   | 交付含义                      |
| ------ | ------------------------------------------------------ | ----------------------------- |
| 范围   | “提供常年法律顾问服务，含合同审查、劳动用工、合规培训” | 工作范围、除外责任            |
| 人员   | “项目负责人 X 律师，合伙人 Y 律师，响应律师 Z”         | staffing 计划、档期、替换限制 |
| SLA    | “2 小时内响应，24 小时内出具书面意见”                  | 服务级别、考核、违约          |
| 交付物 | “月度报告、季度培训、年度合规体检”                     | 交付包、验收标准              |
| 报价   | “年费 30 万，含 2 次培训，超出按小时计费”              | 预算、计费、变更控制          |
| 承诺   | “免费提供 1 次劳动用工合规体检”                        | 增值服务、成本                |
| 合同   | “责任上限为年费 1 倍，保密期 5 年”                     | 风险、保险、条款              |

**交接动作：**

1. 创建 `Matter`（状态 `intake`），走收案闸门/冲突复核；
2. 把 `BidPromise` 转成 `ObligationRecord`，写入 `obligations.jsonl`（复用 `src/lawmind/application/services/obligation-service.ts`）；
3. 生成 `MatterRun` 步骤：签约、团队确认、kickoff、工作计划、报告节奏、交付物、QA、计费、续约；
4. 生成 `DeliveryPacket` 模板：每项交付物的 required 文档、受众、格式；
5. 建立“承诺 vs 实际”看板：人员变更、SLA 违约、交付延期、预算消耗；
6. 把交付结果回写证据库：新业绩、客户评价、实际费率、win/loss 原因。

**这就是“投标到交付”的闭环，也是通用标书工具永远做不到的部分。**

### 4.4 数据模型

### 4.5 状态机：`PursuitRun`

投标不是案件，不应直接建 `Matter`。建议新增 `Pursuit` 作为“中标前对象”，复用 `MatterRun` 的步骤语义：

```text
discovered
  → qualified | no_go
  → documents_ready
  → requirements_ready
  → conflict_clear | conflict_blocked
  → plan_ready
  → drafting
  → review
  → approved
  → packaged
  → submitted
  → opened
  → won | lost | cancelled
  → handed_over (creates Matter)
```

**与 `MatterRun` 的关系：**

- 短期：新增 `PursuitRun`，复用 `MatterRunStep` 的字段（stepId、idempotencyKey、wait、lease、attempts）。
- 中期：把 `MatterRun` 泛化为 `WorkflowRun`，`matterId` 改为 `subjectType + subjectId`；或保留 `MatterRun`，新增 `PursuitRun` 的存储适配。
- 不建议：为了复用而把 Pursuit 伪装成 `Matter`；会污染案件列表、冲突扫描、收案统计。

### 4.6 人工闸门（必须保留）

| 闸门         | 问题                                   | 谁签              | 失败后果           |
| ------------ | -------------------------------------- | ----------------- | ------------------ |
| G1 投/不投   | 是否值得投？冲突？产能？利润？         | 合伙人/BD 负责人  | 浪费资源、冲突     |
| G2 关键字段  | 截止、保证金、资格、评分理解是否正确？ | 投标专员 + 合伙人 | 废标               |
| G3 团队/承诺 | 人员是否真的可用？承诺是否能履约？     | 项目负责人        | 中标后违约         |
| G4 报价      | 报价是否覆盖成本？是否合规？           | 财务 + 合伙人     | 亏损、低价恶性     |
| G5 法律/合同 | 合同条款是否可接受？                   | 风控/合伙人       | 责任风险           |
| G6 最终提交  | 文件、签章、授权、平台是否正确？       | 授权代表          | 废标/无效          |
| G7 中标交接  | 是否接案？冲突是否复核？               | 合伙人/风控       | 利益冲突、交付失败 |

### 4.7 不该自动化的清单

- 报价最终决策；
- 利益冲突裁决；
- 签署/盖章/CA 签名；
- 授权代表身份；
- 对客户的承诺（人员、时限、结果）；
- 法律意见的最终定稿；
- 虚假/无法核验的业绩、简历、证书；
- 串标、围标、价格协调；
- 绕验证码/反爬/登录；
- 无人值守提交（近期）。

### 4.7.1 为什么 L4 不是近期目标

1. **电子签名是法律行为**：可靠电子签名要求由签署人控制；把 CA 证书/密码交给自动化系统，等于把签署权交给软件。
2. **投标主体与授权代表**：投标函、授权委托书、报价表需要具名主体确认；AI 不能成为投标人。
3. **平台规则**：验证码、人脸识别、CA 绑定、上传确认通常明确要求人工操作；绕过即违反 ToS。
4. **商业判断**：报价、让利、服务承诺、人员投入是合伙人的商业决策，不是文本生成问题。
5. **责任边界**：虚假材料、串标、围标可能触发行政处罚甚至刑事责任；系统不能承担，也不应替人承担。
6. **澄清与答辩**：开标后的澄清、二次报价、答辩需要授权代表现场判断，无法预先编排。

**因此，L3 不是“妥协”，而是把自动化放在正确的位置：机器做可验证的准备，人做不可替代的承诺。**

### 4.8 失败模式与对策

| 失败模式         | 后果      | 对策                                  |
| ---------------- | --------- | ------------------------------------- |
| 招标文件解析漏项 | 废标      | 需求图 + 人工确认 + 清单勾选          |
| 评分项理解错     | 低分      | 评分矩阵 + 模拟评分 + 合伙人复核      |
| 业绩/简历过期    | 废标/失信 | 证据有效期 + 到期提醒 + 最后核验      |
| 幻觉业绩         | 失信/处罚 | 证据锚 + 不可核验即拒绝 + 人工签批    |
| 报价算术错       | 废标/亏损 | 计算引擎 + 大小写/分项校验            |
| 格式/签章错      | 废标      | 机器检查 + 人工确认 + 平台回执        |
| 截止期错过       | 失去机会  | 多级提醒 + 时区/节假日 + 升级         |
| 平台上传失败     | 失去机会  | 提前演练 + 备用网络 + 人工兜底        |

| 数据泄露         | 信任/合规 | 本地优先 + 权限 + 脱敏 + 审计         |

### 5.0 先选组件：自建 / 开源 / 商业 / LawMind

**原则：编排层自建，能力层可换。** 下面每一层都给候选；LawMind 只在中标后交付、证据、案件运行这三层有明确优势，其他层不强行使用。

**选型顺序（从快到慢）：**

1. **商业 API/SaaS**：能直接解决、数据合规、价格可接受 → 买。
2. **宽松开源（MIT/Apache）**：能复用、维护活跃 → 借。
3. **AGPL/无许可证**：只读设计、独立重写；不直接嵌入闭源产品。
4. **核心差异层**：证据库、合规闸门、编排、交接 → 自建。

> 许可证提醒：`OpenBidKit_Yibiao`、`BidMaster-Pro` 是 AGPL-3.0；`TenderCrawler`、Microsoft RFP accelerator 是 MIT；多个标书项目未声明许可证。闭源商业产品不要把 AGPL 代码直接链接进来；内部自用也要先让法务确认“网络使用”是否触发 AGPL。

**推荐组合：**

- **验证期（0–3 个月）**：栈 A/B。TenderCrawler + pdfplumber/PaddleOCR + OpenBidKit/BidMaster 参考 + officecli + 自建编排；先不引入 LawMind，避免把验证绑在任一产品上。
- **产品化（3–6 个月）**：栈 D。自建证据库/合规/编排；生成用商业模型；解析用开源 + 商业 OCR；交付层评估 LawMind。
- **交付期（6 个月后）**：如果 LawMind 的 `MatterRun`/`DeliveryPacket`/`obligation-service` 能直接复用，用栈 C；否则自建交付层，保持 `BidPromise → ObligationRecord` 契约不变。

**必须自建的接口（保证可替换）：**

```text
TenderSource       fetch(query) -> TenderNotice[]
DocumentParser     parse(file) -> TenderDocument + RequirementGraph
BidGenerator       draft(section, evidence) -> BidSection
EvidenceStore      search(query) -> FirmEvidence[]; verify(claim) -> EvidenceRef
ComplianceChecker  check(bid) -> Finding[]
PacketRenderer     render(bid) -> BidPacket
SubmissionGateway  prepare(packet) -> Checklist; record(receipt) -> SubmissionReceipt
DeliveryHandoff    handover(award) -> DeliveryPlan + Obligation[]
```

> 这八个接口是“自建编排层”的最小边界。换模型、换 OCR、换数据商、换交付系统，都只换实现，不改流程。

### 5.1 投标域与交付域的边界（若使用 LawMind）

以下 5.1–5.8 是**若选择 LawMind 作为承接层**时的落点；不用 LawMind 时，按 5.0 的接口自建即可。

```text
Tender Radar ──→ TenderNotice ──→ Pursuit ──→ BidPacket ──→ Award
                     │               │            │            │
                     └───────────────┴────────────┘            │
                                     │                         ▼
                              Evidence Vault              Matter（intake）
                              （FirmEvidence）                  │
                                                                ▼
                                              MatterRun + DeliveryPacket
                                              + obligations.jsonl
```

读法：中标前是 `Pursuit`，中标后才创建 `Matter`；证据库横跨两段；交付包和义务台账是交接产物。

**边界：**

- `Pursuit` 不是 `Matter`；中标后才创建 `Matter`。
- 投标数据与案件数据分离；冲突扫描可以读案件索引，但不把投标数据写进案件目录。
- 证据库是共享资产，但按客户/保密等级授权。
- 所有外发/提交仍走 `one_tap_signoff` 语义。
- **产品形态是本地桌面应用**：投标工作台、证据库、文件工作面都在 LawMind 内；不另做 Web/云端工作台，不把标书和客户数据默认上传到第三方。
- **若 LawMind 作为承接层，`docs/LAWMIND-REA-TARGET-MAP.md` §0.1 的边界同样适用**：审阅、比对、改稿、签批都在 LawMind 内完成，不要求律师回到 Word/WPS；docx/pdf 只是交付格式。

### 5.4 若落到 LawMind：契约扩展（设计，不改代码）

1. **`PACKET_AUDIENCES` 增加 `procurement`**：投标包受众。
2. **`PACKET_SECTION_KINDS` 增加**：`qualification`、`technical`、`commercial`、`price`、`forms`。

5. **新增 `TenderSource` 类型**：源注册与限速。
6. **`MatterRun` 泛化**：`subjectType`/`subjectId`，或新增 `PursuitRun`。

### 5.4.1 `PursuitRun` 步骤编排（建议）

### 5.6 数据流与反馈闭环

```text
招标公告 → 需求图 → 投标计划 → 草稿 → 合规 → 提交
                                      │
                                      ▼
                                 中标/落标
                                      │
                    ┌─────────────────┴─────────────────┐
                    ▼                                   ▼
              中标：BidPromise → MatterRun          落标：失分归因
                    │                                   │
                    ▼                                   ▼
```

**反馈什么：**

- 哪些评分项实际得分高/低；
- 哪些业绩/简历被评委认可；

- 哪些报价中标/落标；
- 哪些客户/行业值得复投。

### 5.7 安全与权限

| 风险              | 对策                                                       |
| ----------------- | ---------------------------------------------------------- |
| 招标文件提示注入  | 全部标 `untrusted`；系统提示与文件内容分离；工具调用白名单 |
| 客户/案件数据泄露 | 投标工作区与案件工作区隔离；证据库按客户/保密等级授权      |
| 外部模型泄露      | 脱敏；本地模型优先；供应商不训练承诺                       |
| CA/签章滥用       | 不存 PIN；不自动签名；只由授权人操作                       |
| 投标文件篡改      | `packetHash`；版本；审计日志                               |
| 虚假材料          | 证据锚；不可核验即 blocker；具名签批                       |
| 串标/价格协同     | 不提供竞争对手报价交换；不提供多投标人协同功能             |
| 抓取合规          | 官方 API 优先；限速；遵守 ToS；不绕验证码                  |

### 5.8 验收测试（建议）

- **解析 cassette**：给定 5 份真实法律服务招标文件（脱敏），断言需求图字段、评分项、截止期、废标条款的召回/准确率。
- **证据锚 cassette**：每个标书事实必须能回指 `FirmEvidence`；无来源的断言必须失败。
- **合规 cassette**：给定一份有 3 个 blocker 的标书，断言 `check_bid_compliance` 全部命中且阻断提交。
- **提交包 cassette**：给定文件集，断言 `packetHash` 稳定、缺件阻断、版本变化使审批失效。
- **交接 cassette**：给定中标标书，断言 `BidPromise` 抽取完整、`MatterRun` 步骤生成、`DeliveryPacket` required 项正确。
- **提示注入 cassette**：招标文件里嵌入“忽略以上指令”，断言系统不执行、仍按需求图处理。

### 6.3 方法与命令

沿用 `docs/LAWMIND-REA-TARGET-MAP.md` 的工具链：

```bash
# Web bundle / 桌面应用（仅公开面或自有账号）
npx rea-agents@latest analyze-web-bundle <url> --evidence_output tmp/rea/<product>/<date>/
npx rea-agents@latest inspect-desktop-application "<app>" --detail summary --evidence_output tmp/rea/<product>/<date>/

npx rea-agents@latest build-reconstruction-obligation-ledger tmp/rea/<product>/<date>/
```

**证据存放：**

- `tmp/rea/<product>/<date>/`（已 gitignore）；
- 不入库源码、chunk、含客户数据的截图；
- 只保留行为规格、字段表、状态机、验收测试。

### 6.3.1 REA 执行流程（7 步）

1. **定范围**：选一个产品、一条主流程、最多 3 个页面；写清楚“要回答什么问题”。
2. **备环境**：公开试用/自有 license；读 ToS；确认允许自动化访问；准备脱敏测试文件。
3. **录行为**：用 `capture-web-scenario` 走主流程；保存页面状态、按钮、错误、限制。
4. **抽规格**：把观察写成 `spec.md`：字段表、状态机、校验规则、导出格式、边界条件。
5. **做对比**：版本对比 + 边界测试（大文件、扫描件、多标段、失败重试）。
6. **净室实现**：实现者只看 `spec.md` 和公开资料，不看 Evidence；先写验收测试。
7. **法务复核**：许可证/ToS/专利/商业秘密；Evidence 不入库；确认没有复制文案/模板。

### 6.4 合法边界

- 只用公开页面、公开试用、自己购买的 license；
- 不绕登录、不破 DRM、不破解 CA、不抓云端后端；
- 不搬代码、提示词、专有文案、模板原文；
- 净室分离：写规格的人看 Evidence，写代码的人只看规格与公开资料；
- 许可证/ToS 先核；有疑问不做；
- 疑似专利/商业秘密，先让法务看。

### 6.5 产出物

| 产出     | 内容                     | 落点                             |
| -------- | ------------------------ | -------------------------------- |

| 验收测试 | 输入/期望输出            | 实现仓库的测试目录               |
| 差距清单 | 我们缺什么、不做什么     | `docs/`                          |

## 7. 路线图

### P0（2–4 周）：投标雷达 + 证据库 v0 + 合规清单

**目标：** 让律所“不错过、不误判、不漏项”。**不依赖 LawMind，用栈 A/B 独立跑通。**

- `TenderSource` 注册：cebpub JSON、ccgp HTML、手工上传；
- 关键词/地区/客户订阅；去重、变更、截止期；
- `TenderNotice` 标准化与列表 UI（先做桌面本地界面即可）；
- `FirmEvidence` v0：资质、人员、业绩、证书（手工/批量导入 + 有效期）；
- 法律服务合规清单 v0（资格、签章、报价、格式）；
- 投标决策卡：fit、冲突初筛、产能、截止。
- 验收：10 个真实公告解析；5 个招标文件字段抽取；3 个 blocker 检查。

**P0 两周冲刺（建议）：**

| 天      | 交付                                                    | 验收                           |
| ------- | ------------------------------------------------------- | ------------------------------ |
| D1–D2   | `TenderNotice` schema + cebpub/ccgp adapter + 去重/变更 | 能拉到 20 条真实公告，字段齐全 |
| D3–D4   | 手工上传 + pdfplumber/PaddleOCR 解析 + 截止期/资格字段  | 3 份真实招标文件字段抽取正确   |
| D5–D6   | `FirmEvidence` schema + 批量导入 + 有效期提醒           | 导入 50 条证据，过期能标红     |
| D7–D8   | 法律服务合规清单 v0 + 检查结果分级                      | 3 个 blocker 全部命中          |
| D9–D10  | 投标决策卡 + 冲突初筛 + 产能                            | 1 个真实项目走完 go/no-go      |
| D11–D14 | 端到端 demo：公告→证据→检查→决策                        | 2–3 家律所可演示               |

> 这两周不接 LLM 生成，也不接 LawMind；先把“找得到、看得懂、查得出”跑通。生成放到 P1。

### P1（4–8 周）：需求图 + 投标计划 + 三节草稿

- `RequirementGraph` + `ScoringMatrix`；
- `BidPlan` + `ComplianceMatrix`；
- 证据缺口与复用建议；
- 三节草稿：律所简介、团队、服务方案；
- 证据锚闸门；
- DOCX 导出（officecli）；
- 模拟评分 v0。
- 验收：一份完整法律服务标书的 60% 章节可生成；无来源断言为 0；blocker 全部命中。

### P2（8–12 周）：全包 + 审核 + 辅助提交

- 全部章节/表单/报价表；
- 机械/合规/一致性检查；
- 审批流与 `packetHash`；
- 提交清单、文件命名、回执归档；
- 纸质/电子提交指引；
- 复盘报告。
- 验收：一份标书从上传到提交包 ≤ 2 人天；提交包 0 缺件；回执可追溯。

### P3（12–16 周）：中标交接 + 交付层（自建或 LawMind）

- `BidPromise` 抽取；
- 中标 → 交付对象（自建 `Matter` 或 LawMind `Matter`）；
- 交付计划：步骤、负责人、期限（自建状态机或 `MatterRun`）；
- 整包清单：交付物、受众、格式（自建或 `DeliveryPacket`）；
- 承诺 vs 实际看板；
- 交付数据回写证据库。
- 验收：中标标书 100% 承诺可追溯；交付包 required 项完整；首月交付按计划。
- 决策点：如果 LawMind 的 `MatterRun`/`DeliveryPacket`/`obligation-service` 能直接复用，选栈 C；否则自建，保持 `BidPromise → Obligation` 契约。

## 10. 最终判断

**不要做“又一个 AI 标书生成器”。**

原因：

1. 生成层已经有很多开源/商业产品，价格会被打到很低；
2. 律所的痛点是“找不到可信证据、怕废标、怕交接断层”，不是“写不快”；
3. 通用工具不懂法律评分、律所资质、利益冲突、电子招投标；
4. 中标后的交付是价值最高、竞争最少的环节；可以自建，也可以用 LawMind 承接，但 `BidPromise → Obligation → DeliveryPlan` 的数据契约必须自己掌握。

**要做“法律服务投标到交付的操作系统”：**

```text
发现 → 资格 → 解析 → 证据 → 计划 → 起草 → 合规 → 打包 → 提交 → 中标 → 交付 → 复盘
```

**三条护城河（与是否用 LawMind 无关）：**

1. **律所证据图谱**：资质、人员、业绩、排名、保险、可引用性、有效期、权限。
2. **法律投标合规闸门**：法律服务特有的资格、评分、废标、利益冲突、保密、电子投标。
3. **投标到交付的连续性**：`BidPromise` → 交付义务 → 交付计划 → 验收证据。

> LawMind 只是第 3 条的一个候选实现，不是第 3 条本身。用不用它，取决于它能否在 `MatterRun`、`DeliveryPacket`、`obligation-service` 上直接复用；不能复用就自建。

**技术选择：** 编排层自建；数据源、OCR、LLM、DOCX 排版优先开源或商业；闭源产品能买 API 就买，不能买就用 REA 吸收行为规格，自建实现。

**近期目标：L3。** 无人值守准备，具名律师一键签批提交。等平台 API、CA、律所信任成熟后，再考虑 L4。

**下一步：** 先做 P0（投标雷达 + 证据库 v0 + 合规清单），用 2–3 家律所试点验证“少废标、少漏项、可交接”，再决定是否投入全流程。P0 不依赖 LawMind，可以独立跑通。

## 11. 工程组织：分开开发，还是并入 LawMind？

### 11.1 先看五个事实

| 事实     | 投标产品                   | LawMind（交付）          | 含义                                       |
| -------- | -------------------------- | ------------------------ | ------------------------------------------ |
| 生命周期 | 天到周，截止驱动，高并发   | 月到年，案件驱动，低并发 | 状态机、SLA、数据保留策略不同              |
| 主要用户 | BD/市场部/投标专员/合伙人  | 律师/合伙人/助理         | 界面、权限、培训不同                       |
| 买家     | 市场部/BD 预算，或管委会   | 业务/IT 预算             | 销售路径不同                               |
| 发布节奏 | 每周（数据源/平台/模板）   | 每月/每季（桌面安装包）  | 同一发布火车会互相拖累                     |
| 数据边界 | 商机、标书、报价、竞争对手 | 客户、案件、证据、交付   | 混库会扩大泄露面                           |
| 许可证   | 需要闭源商业许可           | 现有 repo 为 MIT         | 独立 repo 可隔离第三方 AGPL 代码，避免污染 |

**结论：这是两个产品域，不是两个页面。** 把它们塞进同一个应用，短期省事，长期会把发布、权限、TAM 和许可证都绑死。

### 11.2 三种组织方式

| 方式                       | 结构                                                      | 优点                                     | 缺点                                                                  | 适用           |
| -------------------------- | --------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------- | -------------- |
| A. 并入 LawMind            | 在 `apps/lawmind-desktop` 加“投标”页签，共享数据库        | 集成最快；一套登录/UI                    | TAM 只剩 LawMind 客户；发布被桌面版拖慢；投标数据进案件库；许可证风险 | 只做内部工具   |
| B. 同一 monorepo，两个 app | `apps/tender` + `apps/lawmind`，共享 `packages/contracts` | 类型共享、原子改动、一套 CI              | 构建变慢；发布仍耦合；权限/依赖容易串                                 | 5 人以下小团队 |
| C. 独立 repo + 契约层      | `tender-os` 独立仓库；通过 API/文件/MCP 与 LawMind 交接   | TAM 最大；发布独立；许可证隔离；团队自治 | 需要维护契约、双端联调；前期多 2–4 周                                 | **推荐**       |

**加权评分（1–5，权重：TAM 25%、上市速度 20%、发布节奏 15%、集成 15%、维护 10%、许可证/安全 15%）：**

| 方式                  | TAM | 上市 | 发布 | 集成 | 维护 | 许可 | 加权     |
| --------------------- | --- | ---- | ---- | ---- | ---- | ---- | -------- |
| A. 并入 LawMind       | 2   | 4    | 2    | 5    | 4    | 3    | **3.20** |
| B. 同 monorepo 双 app | 4   | 3    | 3    | 4    | 3    | 4    | **3.55** |
| C. 独立 repo + 契约   | 5   | 2    | 5    | 4    | 3    | 5    | **4.05** |

### 11.3 推荐：C，独立产品 + 契约层 + 可选 LawMind 承接

**理由：**

1. **TAM**：投标产品可以卖给不用 LawMind 的律所；LawMind 也可以接其他投标前端。互相不锁死。
2. **发布**：招标源、平台规则、模板、合规目录变化快，需要周级发布；LawMind 桌面版是月/季级。
3. **许可证**：投标产品要闭源商业许可；独立 repo 可以彻底隔离 AGPL 代码和现有桌面依赖。
4. **安全**：投标数据（报价、竞争对手、客户名单）与案件数据分开存、分开授权、分开审计。
5. **团队**：两个产品团队可以并行；契约层是唯一的共同语言。

**例外：** 如果团队 < 5 人、且前 6 个月只服务 LawMind 现有客户，选 B；但仍然保持**两个可独立部署的应用**，不要做成一个页签。等客户/团队扩张再拆 repo。

**不推荐 A**：它会把“投标”变成 LawMind 的一个功能，而不是一个产品；TAM、发布、许可证三件事都会受限。

**部署拓扑（推荐）：**

```text
投标 Web/Desktop
      │  HTTPS/本地 API
      ▼
Tender API（租户/权限/审计）
      │
      ├── Orchestrator（PursuitRun）
      ├── Parser Worker（Python/OCR）
      ├── Evidence Service（FirmEvidence）
      └── Compliance Service（规则 + LLM）
      │
      ▼  AwardHandoff（API / 签名文件 / MCP）
LawMind Local/Private API
      │
      ├── Matter（收案/冲突）
      ├── MatterRun（交付步骤）
      └── DeliveryPacket（整包交付）
```

**读法：** 投标系统是“前台 + 生产线”，LawMind 是“交付后台”；两者只通过 `AwardHandoff` 和交付契约通信，不共享数据库。

### 11.4 集成契约：只共享五个对象

不要共享数据库、ORM、内部 service；只共享**版本化的数据契约**。

| 对象               | 方向              | 关键字段                                                                                       | 用途                     |
| ------------------ | ----------------- | ---------------------------------------------------------------------------------------------- | ------------------------ |
| `AwardHandoff`     | 投标 → LawMind    | `handoffId`、`award`、`bidPacketHash`、`promises[]`、`approvals[]`、`idempotencyKey`           | 中标交接的唯一边界       |
| `BidPromise`       | 投标 → LawMind    | `type`（scope/staffing/sla/deliverable/fee/warranty/contract）、`text`、`source`、`obligation` | 标书承诺 → 履约义务      |
| `ObligationRecord` | LawMind 内部      | 现有 `obligationId`、`title`、`amountText`、`dueAt`、`sourceQuote`、`status`                   | 复用 `obligations.jsonl` |
| `DeliveryPlan`     | LawMind 内部/回传 | `steps[]`、`owner`、`dueAt`、`dependsOn`、`acceptance`                                         | 交付计划                 |
| `DeliveryPacket`   | LawMind → 客户    | `packetId`、`sections[]`、`required`、`audience`、`packetHash`                                 | 整包交付                 |

**交接方式（按优先级）：**

1. **本地/私有 API**：LawMind 本地服务或私有部署 API；签名请求 + `handoffId` 幂等。
2. **签名清单文件**：`handoff.json` + `bid-packet.zip` + `sha256`；适合气隙/离线律所。
3. **MCP 工具**：给 Agent 用；仍然走同一契约，不绕过审批。

**契约纪律：**

- 语义化版本（`schemaVersion`）；破坏性变更升 major；
- 双向契约测试：投标侧生成、LawMind 侧消费；字段缺失/多字段/旧版本都要测；
- `idempotencyKey = awardId + bidPacketHash`；重复交接不重复建案；
- 交接失败可重试；失败原因可读；不丢 `promises`；
- 所有交接写审计：谁、何时、哪个版本、哪个包。

**`AwardHandoff` 示例：**

```json
{
  "schemaVersion": 1,
  "handoffId": "ho_20261027_001",
  "award": {
    "noticeId": "tn_...",
    "projectCode": "XM-2026-...",
    "buyer": "某市国资委",
    "contractValue": "800000",
    "awardedAt": "2026-10-27T09:00:00+08:00"
  },
  "bid": {
    "packetId": "bp_...",
    "packetHash": "sha256:...",
    "submittedAt": "2026-10-26T16:30:00+08:00",
    "version": 3
  },
  "promises": [
    {
      "type": "staffing",
      "text": "项目负责人为张律师，合伙人李律师复核",
```

### 11.7 什么时候考虑合并

只有同时满足以下三条，才考虑把两个 repo 合并或做深度嵌入：

1. **>70% 的投标客户同时是 LawMind 客户**；
2. **集成/联调成本 > 独立发布成本**；
3. **两边发布节奏已经对齐**（例如都变成周级）。

否则保持独立；合并容易，拆分很难。

## 12. 全栈自研的边界：自研“核心 IP”，不是重写基础设施

### 12.1 什么叫全栈自研

**自研：**

- 投标域数据模型（`TenderNotice`、`RequirementGraph`、`ScoringCriterion`、`BidPlan`、`ComplianceItem`、`BidPacket`）；
- 编排与状态机（`PursuitRun`）；
- 证据图谱与证据锚（`FirmEvidence`、`EvidenceRef`）；
- 法律投标合规目录与规则引擎；
- 评分矩阵、模拟评分、红队；
- 标书结构、模板、DOCX 渲染纪律；
- 提示词/工作流/评测集；
- UI/UX、权限、审计、交接契约。

**采购/借用：**

- LLM API（Claude/GPT/DeepSeek/Qwen）；
- OCR（PaddleOCR/商业 OCR）；
- PDF/DOCX 基础库（pdfplumber、python-docx、officecli）；
- 工作流引擎（Temporal）、数据库、对象存储；
- 电子签/CA（只做集成，不自研密码学）；
- 招标数据（数据商）。

> **全栈自研 = 自有数据模型、编排、证据、合规、UI 和评测；不是自己训练大模型、自己写 PDF 解析器、自己造数据库。**

**两种“全栈自研”口径，先对齐：**

| 口径                | 含义                                                                                             | 代价                     | 适用                    |
| ------------------- | ------------------------------------------------------------------------------------------------ | ------------------------ | ----------------------- |
| A. 自有全栈（推荐） | 代码、数据、编排、UI、评测全自有；LLM/OCR 可用商业 API，但接口可替换，核心不锁定单一供应商       | 较低；依赖供应商 SLA     | 大多数商业产品          |
| B. 自托管全栈       | 运行时也尽量开源/自托管：Qwen/DeepSeek 本地、PaddleOCR、Postgres、MinIO；商业产品只做 REA 规格源 | 准确率/运维/GPU 成本更高 | 强合规、气隙、国企/政府 |

> 无论 A 还是 B，**AGPL/无许可证代码不嵌入，REA 不搬代码**；区别只在“商品层用云 API 还是自托管”。第一版建议 A，等客户/合规要求明确后再切 B 的本地模型。

### 12.2 三条红线

1. **许可证红线**：AGPL 代码不嵌入闭源产品；无 LICENSE 的仓库不复制；商业 SDK 按条款用。
2. **商业秘密红线**：REA 只吸收可观察行为/字段/状态/错误码；不搬代码、提示词、专有文案、模板原文。
3. **法律红线**：不绕 CA/验证码/登录；不伪造材料；不做串标/价格协同；不把 AI 生成内容当已核验事实。

### 12.3 “吸收代码”这个说法要纠正

REA 能合法吸收的是**行为规格**，不是代码：

- 能吸收：页面流程、字段 schema、状态机、校验规则、错误码、导出格式、边界条件。
- 不能吸收：源码、压缩/混淆后的实现、提示词、专有文案、模板文件、后端逻辑。
- 正确做法：**净室（clean room）**——写规格的人看 Evidence，写代码的人只看规格与公开资料；Evidence 不入库；实现独立写；测试对齐规格。

> 如果目标是“全栈自研”，REA 的价值是**少走弯路**，不是**抄近路**。抄代码会把许可证、升级、维护和法律风险一起抄进来。

### 12.4 自研优先级

| 优先级 | 自研                                               | 可以买/借               |
| ------ | -------------------------------------------------- | ----------------------- |
| P0     | 数据模型、采集适配、需求图、证据库、合规规则、编排 | 招标数据、OCR、PDF 解析 |
| P1     | 生成编排、评分矩阵、DOCX 模板、审核流              | LLM、officecli、向量库  |

## 13. 非功能要求：这不是玩具

### 13.1 目标

| 维度              | 目标                     | 验证                   |
| ----------------- | ------------------------ | ---------------------- |
| 公告采集          | 10k 条/天，延迟 < 5 分钟 | 源回放 + 压测          |
| 文档解析          | 200 页 PDF P95 < 2 分钟  | 100 份真实标书         |
| 需求图召回        | ≥ 95%（人工标注）        | golden set             |
| 需求图准确        | ≥ 90%                    | golden set             |
| 合规 blocker 召回 | 100%                     | 50 份带 blocker 的标书 |
| 合规误报          | ≤ 5%                     | 同上                   |
| 单节草稿          | P95 < 30 秒              | 压测                   |
| 整包生成          | P95 < 30 分钟            | 10 份标书              |
| 可用性            | 私有云 99.9%；桌面 99.5% | 监控                   |
| 审计              | 100% 关键动作            | 审计日志抽查           |
| 租户隔离          | 0 越权                   | 安全测试               |
| 单标成本          | 可度量、可优化           | token/页数/人天        |

### 13.2 评测集

- **golden tenders**：50–100 份脱敏真实法律服务招标文件，人工标注：资格条件、评分项、废标条款、截止期、提交清单。
- **golden bids**：20–30 份历史标书，标注：事实、证据、失分点、废标点。
- **contract tests**：`AwardHandoff` 双端；旧版本/缺字段/多字段。
- **replay**：每次模型/提示词/规则变更跑回放；分数下降不能发。
- **security**：提示注入、越权、数据泄露、CA/PIN 隔离。
- **chaos**：源超时、平台 502、文件过大、OCR 失败、模型限流。

### 13.3 “不是玩具”的五个标志

1. **可回放**：任何一份标书能重放“当时用了哪个模型、哪条规则、哪个证据、谁批的”。
2. **可验证**：每条事实有证据锚；每个 blocker 有原文定位。
3. **可恢复**：长流程断点续跑；提交包幂等。
4. **可替换**：模型、OCR、数据源、交付系统都能换，契约不变。
5. **可审计**：谁在何时改了什么、为什么、依据是什么。

**证据锚规则：**

- 每个标书事实必须绑定 `evidenceId`；
- `evidenceId` 必须有 `sourceFile + sha256 + locator`；
- 过期证据不得用于资格/业绩；
- 不可核验的断言不得进入定稿；
- 客户可引用性必须显式记录；
- 证据变更使相关章节失效，需重新审核。

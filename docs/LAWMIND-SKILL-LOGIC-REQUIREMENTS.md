# 独立复审：Skill 内在逻辑 → LawMind 需求

> 截止：2026-09-08  
> 性质：对已发现 Skill **重新精读**后的产品需求，不是上一轮去重清单的摘要。  
> 前提：能找到的 Skill 几乎已经覆盖律师日常功能面。LawMind 要挖的是**内在逻辑、实现技巧、约束边界和提示词结构**，再编译成自己的产品，而不是再发明任务类型。

> 产品排序已改：开箱、交付质量、稳态见 [docs/LAWMIND-SKILL-THREE-LAWS-REVIEW.md](docs/LAWMIND-SKILL-THREE-LAWS-REVIEW.md)。本文第六节 P0 不再作为开发顺序。

## 0. 与上一轮去重的分歧

上一轮正确的是：不能把 3,571 条薄 `SKILL.md` 预装进桌面。上一轮错的是：把薄 Skill 和 Greater-China **法律原子**一起扔掉，等于丢掉了律师功能全集和推理指令集。

独立复审后的用法：

| 材料                                     | 上一轮         | 本轮                                                 |
| ---------------------------------------- | -------------- | ---------------------------------------------------- |
| 数千条薄 Skill                           | 当废料         | **需求全集**：任务类型、输入、输出、自动化等级       |
| Greater-China 25 个原子                  | 不当规范源     | **推理指令集**：要素提取、证据链、规范效力、解释方法 |
| 厚包（Anthropic / 潘睿 / copilot / LPM） | 保留 70 个单元 | **运行时语法**：配置、闸门、计划 JSON、出稿闭环      |
| LawMind 现有 6 个办件                    | 缺口列表       | 对照后重写能力表：不是加提示词，是加编译阶段         |

SkillHub 2,049 项的结构事实（用于需求，不当角色画像）：

- 任务：合同工作 715、法律分析 704、诉讼 178、读材料 157、检索 127、合规 103。尽调只有 3、质控只有 2 —— 不是律师不做，而是公开 Skill 很少写成独立包。
- 输入：自然语言提问 1,435，合同 387，公司文件 320，诉讼材料 262，证据 239。律师日常一半以上是**快问**，不是交一份合同。
- 输出：清单 485、合同稿 430、建议 395、备忘 335、诉讼文书 293、合规报告 248、风险清单 240、计算 145、**红线只有 25**。
- 方法：规则 1,436，工具调用 417，检索增强 306。绝大多数 Skill 停在 L1/L2 建议，没有脚本。

结论：公开生态已经把**律师要什么**写全了；几乎没人把**红线、计算、出稿、事项**做成可执行流水线。LawMind 的产品差在后半段编译器，不在再发明“合同审查”这个品类。

## 1. 律师功能全集（从全部 Skill 抽出）

按输出物而不是按法域。这就是 LawMind 能力表应覆盖的面。

| 功能簇     | 律师实际在做什么                 | 公开 Skill 里的完整实现                                                   |
| ---------- | -------------------------------- | ------------------------------------------------------------------------- |
| 一分钟分诊 | Slack/微信里问“这算不算问题”     | Anthropic `is-this-a-problem`：对照律所校准表，Fine / Needs a look / Hold |
| 接案与事项 | 从邮件堆变成案卷、利益冲突、期限 | LPM intake；诉讼 `matter-intake`（冲突是闸门）；Yang `new-case` 目录模板  |
| 读材料     | 生活语言 → 法律事实              | GCL `legal-element-extraction`：九类事实、四属性净化                      |
| 检索       | 命题 → 查询矩阵 → 试检 → 对位    | 元典中间层；Golden2002 法源层级；潘睿法宝核验                             |
| 分析       | 请求权 / 抗辩 / 争点             | GCL 原子：要件、类比、目的解释、证据论证链                                |
| 合同审查   | 立场 + 分层风险 + 改法           | copilot 三层四步；Anthropic 双边 playbook；潘睿红线计划                   |
| 合同起草   | 路由卡 + 待补事实 + 条款骨架     | copilot 12 类封闭路由，不无限扩类型                                       |
| 诉讼文书   | 阶段路由 + 模板/母版克隆         | 潘睿 S0–S16；要素起诉状 fill-plan                                         |
| 计算       | N/N+1、加班、期限、官费          | 潘睿劳动计算门禁；期限日历厚包                                            |
| 可视化     | 时间轴、关系、争点               | 先预览再确认再正式图                                                      |
| 出稿       | 草稿 ≠ 正式                      | 潘睿出稿前审查：PASS / 退回业务 / 问用户 / 补材料                         |
| 运营       | 预算、账单、发票、法院短信、工时 | LPM 16 项；court-sms；invoice-organizer                                   |
| 对内/对外  | 同一事实两份稿                   | GCL 角色档位；法规检索法官版/律师版                                       |

LawMind 今天产品化的只有：合同审查、函件、检索备忘、诉讼文书、写材料、邮件合同。缺的是分诊、接案闸门、要素提取、查询矩阵、计算、出稿状态机、双边 playbook，而不是“再写一个合同提示词”。

## 2. 六层操作系统（应编译进 LawMind，而不是再写长 system prompt）

所有能打的 Skill 都长成同一套，只是文件名不同。

```
L0  执业配置     用户数据在包外；占位符则停止
L1  总控路由     固定词闸门 + 标准回复骨架 + 事项指针
L2  领域 Skill   瘦 SKILL.md 只做触发与索引；细节在 references/
L3  推理原子     要素 / 效力 / 证据链 / 解释方法（编译阶段）
L4  计划→脚本    JSON 计划由模型写，确定性代码落 Word/计算/检索
L5  出稿状态机   成果类型分类 + preflight + next_owner 闭环
```

### L0 执业配置（Anthropic）

- 模板在插件内，用户配置在 `~/.claude/plugins/config/...`。更新插件不得覆盖用户 playbook。
- 仍有 `[PLACEHOLDER]` 则停止实质工作。唯一例外是 cold-start 自己。
- 公司画像全插件共享；插件自己只存 playbook、升级矩阵、集成。
- 2 分钟路径写 `[DEFAULT]`，15 分钟写真实立场。默认必须标出来，输出跑偏时告诉律师改哪一条。
- 集成打勾必须是 MCP **真调用成功**，禁止凭 `.mcp.json` 声明打勾。
- 从已签署合同抽取真实立场，并标出与口头政策的差值。
- 责任上限是四个位置，金额最不重要：直接上限、间接损害、carve-out、基数定义。
- 每一边有 “the one thing”，审查先查破局条款。
- 事项级可覆盖律所 playbook（“本案客户要求 24 个月上限”）。
- 公司法务可关事项工作区；律所默认开，禁止跨事项读取。

LawMind 现状：`playbook-tool-lock.ts` 锁的是**本轮工具表**，不是销售/采购条款政策。`playbooks/CLAUSE_PLAYBOOK.md` 是学习笔记，不是 cold-start 写成的结构化政策对象。

### L1 总控（潘睿）

执行顺序是编译器 pipeline，不是“建议你先想想”：

1. 执业档案 → 2. 语义路由 → 3. 当前事项 → 4. 成果类型分类 → 5. 完整读取 + 读取复查摘要 → 6. 法规校验摘要 → 7. 领域协议 → 8. 出稿审查 → 9. 来源边界。

标准回复骨架（提示词技巧：闸门名禁止改写）：

```
Skill 路径：总控 -> 主 Skill -> 交付链路
前置检查：[当前事项 / 完整读取 / 读取复查摘要 / 名称编号内容核验 / 现行有效]
来源边界：[已核验 / 未核验 / 缺口]
用户确认：[会改变范围、金额、诉请、授权的项]
下一步：[未过门禁不得生成正式正文或外写]
```

固定词：`完整读取`、`不得用模型记忆`、`事项隔离`、`不得静默写入`。模型爱把它们说成“我已经看过材料”，总控用死词对抗这种漂移。

### L2 渐进披露（潘睿瘦身 + code-lawyer）

厚 Skill 的 `SKILL.md` 只保留：何时用、不做边界、执行顺序、按需读取索引、输出底线。完整流程进 `references/`，按阶段读，禁止一次读全。Frontmatter `description` 才是路由器：写清触发语和 **不要用于**。

### L3 推理原子（GCL，上一轮误删）

这些应变成 LawMind `reasoning/` 的真实阶段，而不是再堆 Markdown：

| 原子                        | 内在逻辑                                                                     | LawMind 应对齐                                                                       |
| --------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `legal-element-extraction`  | 生活叙事 → 法律相关事实 → 要件事实；九类事实；客观/主观/法律评价/背景 四分法 | 任何非结构化交办的第一步。现有 `legal-graph.ts` 从检索主张建争点，**跳过了事实净化** |
| `legal-norm-validity-check` | 时间效力（阻断）→ 层级 → 冲突；VALID/AMENDED/REPEALED                        | 接到 `citation-grounding`：缺时效状态不得称正式意见                                  |
| `evidence-argument-chain`   | 主张 → 要件 → 待证事实 → 证据 → 证明力                                       | 诉讼文书和证据目录的数据结构                                                         |
| 解释原子                    | 文义 / 体系 / 目的 / 类比 / 反向                                             | 检索报告的“为什么适用这一条”                                                         |

### L4 计划驱动执行

模型禁止直接改 OOXML。共同模式：

1. 审查结论写成 `review-plan.json` / `redline-plan.json` / `fill-plan.json` / `research-plan.json`（**运行时产物**，不随 Skill 包分发）。
2. 脚本落 `w:ins`/`w:del`、批注、模板单元格、检索调用。
3. QA 查 `trackRevisions`、命中、重复命中、渲染。
4. 自动修正只允许格式和律所抬头；禁止自动改正事实、金额、诉请、法条、签署结论。

LawMind `apply_surgical_edits` 已是 L4。缺的是计划清单、命中报告、以及“文字意见不算完成”。

### L5 出稿状态机（潘睿出稿前审查）

`review_status`：`PASS` | `FIXED_PASS` | `NEEDS_BUSINESS_REVISION` | `NEEDS_USER_CONFIRMATION` | `NEEDS_MATERIAL` | `HARD_BLOCK`。每一种必须带 `next_owner`、`next_action`、`return_to_skill`。只拦截后结束视为实现错误。

成果类型至少七种：工作草稿、内部报告、给法院/客户的正式材料、飞书/协作稿、图片正式包、修订稿、Word 正式稿。`delivery-language.md` 只覆盖了“待审核稿不得写成已签发”，没有状态机。

## 3. 提示词与约束边界（可直接写成 LawMind 规则）

### 3.1 阻塞清单是一张表，不是“缺了就问一句”

copilot：立场、目的、口径缺一即停；禁止把空立场解析成中立。暂停期只许输出缺口，不许输出风险分级或可签结论。仅当用户明示“按默认口径”才继续，并记录授权来源。

Anthropic 诉讼接案：利益冲突 `not-run` 则 **STOP**，不得建 `matter.md`。三条出路：现在做冲突检索 / 标记 pending 且 playbook 允许并行 / 用户书面 bypass 并永久留在状态里。

独立需求：LawMind `intake-required-inputs` 的 Soft Ask 适用于快问和材料已钉选；**正式合同审查、正式意见、新建诉讼事项**必须升级为阻塞清单。现在的“继续不澄清”逃生口，在正式路径上应失效。

### 3.2 缺事实不得出决定性结论

- 签署三档（可签 / 有条件可签 / 不建议签）是正式结论。验收、付款、附件、授权缺口 → `结论待定`，风险点仍分级但标待确认。
- 劳动 N/N+1/2N：未读劳动合同、工资流水、解除通知前不得给金额。
- 检索：最多补问 1 轮，且只问会改变查询路径的问题；不影响路径的标假设继续。
- LPM：Confirmed / 从材料推断 / 从一般知识推断 / Unknown；冲突不自动消解。

### 3.3 路由先于正文

- 合同按标题和附件路由，不靠正文出现“保密”就当 NDA；标题与实质不符时按交易实质，双标签（主类型 + 配套协议）。
- 合同类型封闭 12 类，新类型归入现有类，禁止无限扩 taxonomy。
- 诉讼按阶段路由（侦查 ≠ 二审）。
- 路由不明时列 2–3 个候选，默认确认。
- 产品法务快问对照校准表，不匹配就说“未命中，需要人看”，禁止硬套。

### 3.4 输出分流

- 对内底稿可留策略、假设、升级理由；对外删除内部策略和攻击性语言。
- 角色档位：主办 / 法务 / 业务部门 / 协办 / 对方。对方不得获得任何底稿。
- 检索双文档：法官版汇编 vs 律师版实务要点。身份只改详略，不改法源纪律。
- 时间轴同一事件，原告标记“构成要件”，被告标记“打断要件”。底层时间线中立，标签随立场。
- 发出前做 destination check：公共频道、对方律师、客户会击穿 privilege。提供特权版 / 脱敏版 / 两份，禁止默默盖特权头再让人转发。

### 3.5 检索中间层

元典 Skill 的实现技巧比“接一个法律 API”重要：

1. 轻量研判：争点、要件、决定性事实、近邻案型排除。
2. 每个命题只验证一项判断；每个决定性争点至少 1 正 + 1 反。
3. 查询矩阵：一争点一查询；关键词 4–6 个高密度词。
4. 小样本试检 1–2 条，诊断接口误选 / 表达不适配 / 近邻混入后才扩检。
5. 无 Key 仍交付无 API 的检索方案，不得空跑。
6. 归档含原始响应；对外传输先脱敏。

### 3.6 提示词结构本身

可复用的写法，不是文案：

1. YAML `description` = 路由器（触发 + 负空间）。
2. 正文前 30 行 = 强制顺序；细节外置。
3. 闸门用固定词，禁止同义改写。
4. 失败输出必须是结构化状态，不是散文。
5. “促进交易”写进合同审查理念：目标是落地，不是机械否定。
6. 自动修正白名单与黑名单写死。
7. 配置面试：一次 2–3 个可回答问题；能贴文件就不要让律师默写；暂停用 `[PENDING]` 区别于 `[PLACEHOLDER]`。
8. 用户口述的法条、期限、门槛，写入配置前做 sanity-check。

## 4. 按任务的内在工作流（LawMind 应实现的“怎么做”）

### 4.1 合同审查（四套叠成一条流水线）

```
钉选文件
  → 阻塞清单：立场 / 目的 / 口径（或 playbook 边：销售|采购）
  → 完整读取 + 读取复查摘要
  → 按标题/实质路由到封闭类型（12 类或 NDA/MSA/SaaS）
  → 宏观交易结构 → 中观文本形式 → 微观条款
  → 先查 “the one thing” 和 Never 列表
  → 风险点：P0/P1/P2 + 推荐措辞 + 落地方式（修订/批注/仅意见）
  → 关键事实缺口？结论待定 : 可签三档
  → 法规核验（不得用记忆）
  → review-plan.json
  → 脚本落修订（最短锚定）+ QA
  → 意见书（对内）/ 给对方的建议修改稿（对外）
```

LawMind 已有最短锚定。应补：阻塞清单、双边 playbook、类型路由、计划 JSON、签署结论闸门、意见书与红线成套交付。

### 4.2 快问分诊（公开库几乎没人产品化，但输入统计是第一名）

```
问题
  → 对照律所校准表（通常 FYI / 需要干活 / 通常阻断）
  → 陷阱追问（Logo≠宣传授权；“内部工具”仍处理个人信息）
  → 一句话：Fine / Needs a look / Hold + 下一步 Skill
```

这应成为 LawMind 默认对话态，而不是每句都进 `execute_workflow`。

### 4.3 诉讼

```
冲突检索闸门
  → 接案记录（角色：原/被 决定后续风险口径）
  → 要素提取
  → 阶段路由
  → 证据论证链（缺证标待补，不许假装构成）
  → 时间轴（立场着色）
  → 文书：线性 HTML 或母版克隆
  → 出稿状态机
```

### 4.4 劳动计算

```
读合同/流水/解除/考勤
  → 关系三性
  → 争议类型
  → 工时制度
  → 引擎：N / N+1 / 2N、基数、三层封顶、加班三档、双倍工资
  → 存疑项单独列，不算进确定金额
```

金额必须由规则引擎算，模型只填槽位。

## 6. 开发需求清单（按依赖排序）

### P0 — 编译器骨架（没有这些，加再多领域 Skill 也会漂）

1. **执业档案对象**（L0）：律所/律师、立场边、标准/回退/永不、破局条款、升级阈值。未填完时正式审查停止；快问可用 `[DEFAULT]`。配置与软件更新分离。
2. **总控骨架回复 + 固定闸门词**（L1）：路径、前置检查、来源边界、确认、下一步。用户要求跳过读取或用法条记忆时，回复必须打出被拦截的闸门名。
3. **成果类型枚举 + 出稿状态机**（L5）：接到现有导出。失败必须 `next_owner`。
4. **要素提取阶段**（L3）：非结构化输入先过九类事实净化，再进 `legal-graph`。
5. **检索命题矩阵**（接到 `research.memo`）：先命题和正反查询，再调检索工具；无来源则来源边界为缺口。

### P1 — 把现有合同路径做成厚包那种交付

6. 合同阻塞清单：立场/目的/口径；禁止默认中立。
7. `review-plan` 字段对齐 surgical edits：每条含条款位置、原文、改法、P0–P2、命中状态。
8. 红线 QA：`trackRevisions`、ins/del、命中/误命中。
9. 签署结论闸门：缺口则结论待定。
10. 封闭合同类型路由（先做中国高频 12 类或 NDA/MSA/SaaS 子集）。
11. 对内意见书 / 对外修订说明分流。

### P2 — 高频但今天空白

12. `triage.quick` 校准表。
13. 劳动计算引擎（槽位 + 规则，模型不口算）。
14. 诉讼阶段路由 + 证据论证链数据结构。
15. 新建事项：冲突闸门 + 目录模板（诉讼/咨询/知产可后做）。
16. 期限计算与法院短信/发票整理（先期限，后连接器）。

### 明确不做

- 预装数千条 SKILL.md。
- 把日志/哈希链当律师可见质量。
- 复制 copilot 文案与脚本（NC）。
- 用更长的单一 system prompt 代替 L0–L5。
- 让“继续不澄清”跳过正式合同/正式意见/新建诉讼事项。

## 7. 提示词移植时的许可证与测试

- 结构、字段名、状态枚举、闸门顺序：可独立重写进 LawMind。
- 张海燕四步、何力三观、12 类主文件正文：NC 或未声明则只保留“分层 + 封闭类型”这一结构。
- 验收：同一份合同，分别跑 LawMind 当前路径、潘睿计划脚本、copilot 计划脚本；比的是阻塞是否触发、红线是否最短锚定、缺口时是否拒绝可签、出稿失败是否带回下一步。不是比谁的 Markdown 更长。

# LawMind 路线对比：单产品双面 vs 双产品（LawMind Bot）

- 日期：2026-09-21
- **想读人话版请先看 [`docs/LAWMIND-STRATEGY-MASTER.md`](LAWMIND-STRATEGY-MASTER.md)**；本文是详版。
- 目的：在「**A. 在现有工程上盖（单产品双面）**」与「**B. 另做一个 LawMind Bot（双产品，对位 Cursor : Grok Bot）**」之间给出可拍板的成本、风险与不变量影响对比。
- 前置：借鉴清单见 [`docs/LAWMIND-GROK-BOT-BORROW-REVIEW.md`](LAWMIND-GROK-BOT-BORROW-REVIEW.md)（88 条可借鉴 + 10 条不抄）。
- 后续：终局形态与商业路线见 [`docs/LAWMIND-ACCEPTANCE-LAYER-STRATEGY.md`](LAWMIND-ACCEPTANCE-LAYER-STRATEGY.md)（采信层）。
- 本文不预设结论为「省事」；B 路线里**更贵但可能更对**的分支也照实列出。

## 0. 结论速览

|                  | A1 单包双面<br>（推荐）         | A2 同机双 app 共引擎             | B1 双产品 + **厂商云电脑**        | B2 双产品 + **用户自有节点**          |
| ---------------- | ------------------------------- | -------------------------------- | --------------------------------- | ------------------------------------- |
| 一句话           | 一个应用，两个面：工作台 / 名册 | 两个安装包，同一台机器，共用引擎 | Grok Bot 形态：云端执行面         | 两个面，执行面在律师自己的机器/服务器 |
| 引擎             | 共用                            | 共用                             | 共用                              | 共用                                  |
| 执行面           | 本机工作区                      | 本机工作区                       | 厂商云 VM                         | 用户自有节点                          |
| 与现有不变量冲突 | **0**                           | 1（工作区互斥）                  | **5+**（见 §4）                   | **0–1**                               |
| 新增工程量       | 6–10 周                         | +3–5 周                          | +6–12 个月（估算）                | +8–16 周                              |
| 永久运维成本     | 低                              | 中（双发布链）                   | **高**（多租户/隔离/网络/控制面） | 中（节点运维体验）                    |
| 可逆性           | 高（是 B1/B2 的公共前置）       | 中                               | **低**                            | 中高                                  |
| 对 Day-1 主路径  | 不变难                          | 轻微变难                         | 分心风险最高                      | 轻微变难                              |
| 买卖双方         | 执业律师                        | 执业律师                         | 需另找买家（律所运营/IT）         | 可对私部署客户                        |

**核心判断：A1 不是「便宜选项」，而是唯一同时保留 B1 与 B2 两条增长路径的低后悔动作。** 从 A1 出发，往 B2 走是小步（同一引擎 + 加远程面），往 B1 走是大步；但从 B1 往回走极难，且 B1 与 B2 之间互不可达。

## 1. 先把「一个选择」拆成三条正交轴

把 A/B 当成一个二选一会失真。真正的决策是三个**互相独立**的问题：

| 轴                | 问题                                 | 可选项                       | 本树现状                                                               |
| ----------------- | ------------------------------------ | ---------------------------- | ---------------------------------------------------------------------- |
| **轴 1 · 引擎**   | 办事逻辑是一套还是两套？             | 共用 / 分叉                  | **`src/lawmind/` 已是一套**，两个面都从它走                            |
| **轴 2 · 面**     | 律师面对的「主对象」是一个还是两个？ | 单面 / 双面                  | 现在是**两个模型挤在一个面里**（会话为纲 vs 卷宗为纲），词汇混乱的根因 |
| **轴 3 · 执行面** | 办事发生在哪台机器上？               | 本机 / 用户自有节点 / 厂商云 | 本机（`lawmindd` 同一台机器，且**不监听 HTTP**）                       |

**关键事实：轴 1 在可行方案里答案永远是「共用」。** 所以「另做一个 LawMind Bot」的真实含义只能是**轴 2 与轴 3 的组合变化**，不是一个新引擎。

这也解释了 Cursor : Grok Bot：它们分开的是轴 2 与轴 3（对象模型 + 执行环境），**轴 1 完全共用**（Grok Bot 官方明确复用 Cursor 的 MCP servers / plugins / skills，共用账号与 connector 后端）。

> 因此本文把「另做一个产品」拆成 B1（动轴 3 到厂商云）与 B2（动轴 3 到用户自有节点）两个**性质完全不同**的分支——它们常被混为一谈，但成本差一个量级、合规风险差两个量级。

## 2. 四个现实候选

| 候选   | 定义                                                                                                                                       | 处置                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| **A1** | 一个安装包，两个面：桌面工作台（卷宗/交付物为纲）+ 助手名册（名册/常设工作为纲）。跑在同一进程与同一引擎上，即现有 `lawmindd` 模式的升级版 | **保留**                                                                                  |
| **A2** | 两个安装包（LawMind / LawMind Bot），同一台机器，共用引擎与工作区                                                                          | **保留（备选）**                                                                          |
| **B1** | 两个产品，执行面在厂商云 VM；代登第三方系统、跨端可达                                                                                      | **保留对比，当前不建议**                                                                  |
| **B2** | 两个面，执行面在律师自己的机器或自有服务器；可端到端加密                                                                                   | **保留（A1 之后的增长路径）**                                                             |
| ~~B0~~ | 「另写一套办事逻辑的 Bot」                                                                                                                 | **直接淘汰**：会 fork 掉最小 span 改稿、案件围栏、Guardian 不变量，代价是两份不一致的稿子 |

| --------------------------------------------- | -------------- | -------- | --------------------------- | ----------------------- |
| 抽「执行面」契约                              | 必需（1–2 周） | 必需     | 必需                        | 必需                    |
| P0 可信后台（监护/日志/心跳/单实例锁）        | 必需（1–2 周） | 必需     | 必需 **且要在云上重做一遍** | 必需                    |
| 名册面（对象/UI/职务说明书）                  | 3–4 周         | 3–4 周   | 3–4 周                      | 3–4 周                  |

## 4. 需要修改的不变量（B1 的真实代价在此）

这是本文最重要的一节。**B1 不是「多写代码」，而是要主动废止若干条你已经立下的契约。** 逐条列证据（均为本树现有文本）：

| #   | 现有不变量（原文要点）                                                                                                                                                                                                       | 出处                                                                 | B1 下的处理                                                          | A1/A2/B2 |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------- | -------- |
| I1  | 「LawMind ships as a **downloadable desktop app**. **There is no web or cloud product UI.**」                                                                                                                                | `.cursor/rules/local-desktop-ui.mdc`                                 | **必须显式改写**，并给出新的边界定义                                 | 不动     |
| I2  | 「Trust model：桌面本地 HTTP API 只绑 loopback，**只操作律师本机的工作区**」                                                                                                                                                 | `SECURITY.md` §Trust model                                           | 威胁模型整体重写（多租户 + 网络暴露面）                              | 不动     |
| I3  | 「`lawmindd` 是可选的**同机进程**，**不监听 HTTP**」                                                                                                                                                                         | `SECURITY.md` §Hardening notes (local lawmindd)                      | 远程执行面必须监听——**这条的整个前提被推翻**                         | 不动     |
| I4  | 「Licensing is **local and offline**. It is **not** a security control and **not** a remote control plane.」「No network calls, no telemetry, **no server-side revocation**」；激活码含 `machineFingerprint`，**换机器即拒** | `SECURITY.md` §License boundary、`src/lawmind/license/types.ts`      | 云产品需要账号制、多端、可能吊销——**与 I4 逐条相反**，许可模型要重做 | 不动     |
| I5  | 「History scan 只读律师选定的本机目录，不得跟随符号链接出根」等围栏                                                                                                                                                          | `SECURITY.md` §Legal lint responsibility boundary                    | 目录围栏语义要重新定义                                               | 不动     |
| I6  | 「本仓库仅 LawMind：**无 OpenClaw 网关、无多渠道核心**」「Product UI (this machine only)」                                                                                                                                   | `AGENTS.md`                                                          | 云执行面/控制面会重新引入一类网关树                                  | 不动     |
| I7  | egress 策略、matter replica（卷宗副本/同步真相源）按本机前提写                                                                                                                                                               | `docs/lawmind/LAWMIND-EGRESS-POLICY.md`、`LAWMIND-MATTER-REPLICA.md` | 均需重写                                                             | 不动     |

**读法：B1 的工程成本可以排期，但这 7 条里有 4 条（I1–I4）是「你做产品的前提假设」，不是实现细节。** 改它们的代价不在代码，而在：把「离线、本机、无控制面、无遥测、机器绑定」这套对律师极好卖的承诺，换成需要重新论证的云承诺。

特别提醒 I4：`machineFingerprint` 是**刻意**设计成换机器就拒的（`SECURITY.md` 明写 "machine-bound codes presented on another machine" 无例外拒绝）。云产品的「随处登录」与它直接对立。这解释了为什么「LawMind Bot 的订阅制」不是加个字段的事，而是要重新设计整个商业与信任模型。

## 5. 可逆性分析（哪个决策难回退）

| 决策                      | 回退难度 | 说明                                                   |
| ------------------------- | -------- | ------------------------------------------------------ |
| 抽执行面契约（A1 第一步） | **易**   | 纯内部重构，无外部承诺                                 |
| 补 P0 可信后台            | **易**   | 只增强现有行为                                         |
| 名册面（A1 第二步）       | **中**   | 有 UI 与文案承诺，但可退回单面                         |
| 切成两个安装包（A2）      | **中**   | 发布链翻倍是**永久**成本，合并回来要迁移用户           |
| 上厂商云（B1）            | **难**   | 有客户、基础设施、合规说明、许可重做；回退等于关停产品 |
| 上用户自有节点（B2）      | **中**   | 无厂商数据托管，回退只是停掉远程面                     |

**结论：A1 是低后悔动作。** 它同时是 B2 与 B1 的公共前置（因为「把执行面抽成一等契约」在四个分支里都是必需的），所以现在做 A1 无论最终选哪条都不浪费。

## 6. 触发条件：什么时候 A → B 是对的

**出现下列任一客观信号，才值得启动 B2（不必等全部）：**

1. **非桌面面出现真实需求**：律师在开庭间隙/出差时要看进度或交办（可观察：主动索要手机端或远程访问）。
2. **买家分离**：律所运营/知识管理岗愿意为「无人值守的常设工作」单独付费，而他们的需求与执业律师的改稿需求不同源。
3. **私部署客户要求多机/多席**：一次购买要覆盖多台机器、多名律师，本机单席模型不够。

**出现下列信号才考虑 B1（厂商云），且必须同时具备另两项条件：**

4. 有客户明确要求「我们不希望卷宗落在本所任何一台机器上，请你们托管」——这是**反直觉但真实存在**的企业偏好；
5. **且**有专职资源承担多租户隔离、网络控制、数据合规与云运维（不是「顺手做」）；
6. **且**已按 §4 完成 I1–I4 的显式修订评审，并接受对律师承诺的措辞变化。

**没有 1–3 就做 B，是在用主路径的 Day-1 体验去赌一个更难的卖点**，直接撞铁律 #1。

## 7. 建议

**走 A1。** 具体顺序：

1. **抽执行面契约 + 补 P0 可信后台**（`B1 B5 B10`：监护、日志、心跳、单实例锁）——这一步就兑现了 Grok 的核心用户承诺「我走开它还在办」，且全在现有树内；
2. **名册面**（`A1 A3 A4` + 常设工作生产化 `C2 C5 C9`）——此时产品已是「LawMind 工作台 + LawMind Bot 名册」的双面形态，Cursor : Grok Bot 的**架构关系已成立**，不成立的只有独立安装与云电脑，而这两项恰好是律师场景最不该要的；
3. **等到 §6 的信号出现，再决定 B2 还是 B1**——届时 A1 已把两条路的公共前置做完。

**本轮明确不做**：不 fork 引擎；不上厂商云；不为 Bot 另写一套办事逻辑；不提前把发布链拆成两条。

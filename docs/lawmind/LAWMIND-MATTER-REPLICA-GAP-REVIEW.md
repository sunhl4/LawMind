# LawMind 案件副本 — 与市面 / 国际 / 一流开源的差距评审

> 分支：`feature/matter-replica-collab`  
> 对照时点：下一里程碑收口后（Matter Cloud MVP、邀请密钥包装、CASE rematerialize、整理入卷）  
> 目的：诚实标出**产品差距**与**刻意不做**，指导合并后优先级。

## 一句话结论

LawMind 的协作单位是**案件（matter）**。相对市面网盘形状已选对；相对 iManage / NetDocuments 级 DMS 与 Yjs/Loro 级实时共编，**深度仍有差距**，但 P0 中的「无自营协议面」与「明文密钥出包」已在本分支收口为 MVP。

## 我们已经对齐或领先的点

1. **案件边界**：不把个人会话、密钥、无关案件拖进同步面——比「整库同步」更适合律师伦理墙。
2. **Word 签出**：承认修订轨不可与无锁共写并存——比网盘「冲突副本」更专业。
3. **记录管**：审批/队列类 jsonl 用 op，避免坚果云式互盖。
4. **冲突诚实**：材料 LWW + `（冲突）` 旁路；CASE 不静默覆盖——产品可信度优先于「看起来合并成功」。
5. **Solo 隔离**：Firm 门控，合并前不污染独立律师路径。

## 关键差距（按合并后优先级）

### P0 — 不补则难商业化

| ID  | 差距                                                   | 市面/开源标杆                        | 改进方向                                               |
| --- | ------------------------------------------------------ | ------------------------------------ | ------------------------------------------------------ |
| G1  | **无自营 Matter Cloud**（仅有 HTTP 客户端 + 目录中继） | Dropbox/iManage SaaS；Seafile Server | 国内对象存储 + 多租户 membership API；继续零信任密文块 |
| G2  | **密钥交换仍偏手工**（邀请 JSON 带 key）               | Keyhive、企业 KMS、1Password SCIM    | 邀请码衍生包装密钥、设备配对、密钥轮换与吊销           |

## 刻意不做（避免做成二流网盘）

- 不把 LawMind 做成浏览器版「腾讯文档律师版」。
- 不以 live Word co-authoring 为合同主路径。
- 不用 git 管卷宗二进制。
- 不以 Jazz/Electric 等云 CRDT 库替换本机 `cases/` 真相源。

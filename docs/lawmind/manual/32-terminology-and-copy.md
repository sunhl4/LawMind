# 第 32 章 术语与文案实践

这一章给要写界面文案、通知、报告的人看。核心是一件事：**律师看不懂工程语言。**

## 32.1 为什么要有这套规矩

仓库里有一份 `docs/LAWMIND-TERMINOLOGY.md`，它的背景说明写得很直接：

> 2026-09 评审实测同义词爆炸——renderer 内「在办 ×116、改稿 ×92、签批 ×91、审核 ×86、交办 ×83、复核 ×13」并存，同一工作面 Solo 叫「改稿」、Firm 叫「文书台」。

也就是说：**同一件事在不同地方有五六种叫法。**

后果不是「不专业」，而是**律师要学五六个词才能指同一件事**。这对「上手简单」那条铁律是直接伤害。

## 32.2 一动作一词

核心规则：每个动作、实体、场所在全产品**只用一个词**。近义词一律视为禁用词。

**完整词表不在这一章**，只在一处维护：

| 想看什么                                                   | 去哪                          |
| ---------------------------------------------------------- | ----------------------------- |
| 唯一真相源（术语、定义、禁用近义词、适用范围、分场景细则） | `docs/LAWMIND-TERMINOLOGY.md` |
| 手册内的速查表                                             | 第 1 章 §1.3                  |
| 代码 ↔ 用词的三个陷阱                                      | 第 1 章 §1.15                 |

这一章只讲**怎么用**（§32.3 细则、§32.4 禁词、§32.6 写作实践）和**怎么被守住**（§32.5 lint）。不要在别处再抄一张词表——抄出来的副本会各自漂移。

## 32.3 用词分场景细则

术语表里还有几条容易搞混的。**这些细则的口径也以 `docs/LAWMIND-TERMINOLOGY.md` 为准**，这里给律师视角的解释：

| 情况              | 规矩                                                                                                       |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| 「合同审查」      | 这是**业务场景名**，保留。但律师盯着稿子看的动作一律叫「审核」                                             |
| 「通过」          | 作签批结果状态可以用（「已通过」），作按钮动词一律用「签批」                                               |
| 「批准」          | 同上：`已批准` 是合法的签批结果状态；作动词（「批准发送」「需批准」）一律用「签批」，「待批准」→「待签批」 |
| 「复核」          | 禁用，已进硬拦档。界面说「审核」。稿件意见落盘仍用「复核：」，显示时改写成「审核：」                       |
| 「文书台」        | 禁用，已进硬拦档。改稿工作面 Solo / Firm 都叫「改稿」。只豁免历史动作日志对旧词的识别                      |
| 「语料 / 语料库」 | **只禁指律师自己交进来的材料时**。「演示语料」「开源语料」「厂商语料」指法源库，是诚实说明，保留           |
| 「修订」          | 作**我们自己的动作**时用「改稿」；`已修订`（改稿状态）、`合同修订稿 / 修订版`（对方来稿）、`修订记录` 保留 |

**「业务场景名」和「动作名」的区别**：「合同审查」是一个交办事项的类型；「审核」是你对着一份稿子的动作。前者可以保留，因为它是名词性的场景。

**为什么「语料」和「修订」要留口子**：一刀切的禁词表会把自己的合法用法也拦掉——那样维护者只能去破 exempt 清单，词表反倒失信。所以禁词表要写**在什么语境下禁**，不只是禁哪个词。

## 32.4 工程师语言禁词表

以下类别**不得出现**在律师可见面（界面文案、系统通知、交付报告、律师向文档）：

| 类别       | 禁词示例                                                       | 该改成                                               |
| ---------- | -------------------------------------------------------------- | ---------------------------------------------------- |
| 文件路径   | `workflow`、`lawmind/`、`cases/`、`MEMORY.md`、`*PROFILE.md`   | 「工作流」「案件档案」「记忆」「助手档案」这类业务名 |
| 机制黑话   | 「产出 Agent」「推理图覆盖率」「侧车」                         | 对应的律师语言，或删掉                               |
| 提示词机制 | 「已注入 / 未注入 / 始终注入」「system prompt」                | 「已记住 / 已写入」「系统设定」                      |
| 英文枚举   | `pending_review`、`auto_deliver`、`strict`                     | 中文状态词（待审核 / 自动交付 / 严格）               |
| 门禁术语   | gate、bypass、门禁、拦截器、中间件、e2e、token、IPC、API、JSON | 「核对」「必核」「确认」等业务语言                   |

**「侧车」（sidecar）是最典型的例子**：它在代码里是准确的（`.redline.json` 确实是侧车文件），但律师看到「侧车」只会困惑。界面上应该说「修订记录」。

## 32.5 机械拦截：`lawmind:ui-copy-lint`

有条命令专门拦这个：

```bash
pnpm lawmind:ui-copy-lint
```

它扫渲染层的文案，**分两档**执法。注释、import、以及**不含中文**的 `/api/` 路由行不计；同一行里若有中文律师文案，提到路由也不能整行跳过：

| 档位   | 数组               | 行为                     | 现存内容                                                                                                                                                                                                                                                                              |
| ------ | ------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 硬拦档 | `BANNED_PATTERNS`  | 命中即退出码 1           | **26 条**＝14 条工程师语言（路径、门禁词、提示词机制…）＋ 12 条「存量已归零」的近义词（出货、派单/下单、检查点、全盘扫描、待办中心、审批中心、批稿、AI 员工/机器人、上下文文件、智能体、文书台、复核）。英文枚举（`pending_review` 等）写在代码标识符里，本脚本按整行扫描，尚未单独拦 |
| 棘轮档 | `SYNONYM_PATTERNS` | 存量冻结，**新增即失败** | 待办 21、审批 32、批准（动词）37、修订（自己的动作）26，合计 116 处                                                                                                                                                                                                                   |

地板存在 `scripts/lawmind/ui-copy-lint-synonym-baseline.json`；某词收敛后跑 `pnpm lawmind:ui-copy-lint -- --update` 收紧。**某词降到 0，就把它从棘轮档移进硬拦档**——这是收敛的收尾动作。

棘轮档的正则里已经排除了术语表明令保留的用法（`已批准`、`已修订`、`合同修订稿 / 修订版`、`修订记录`）。加新词时先问「它在什么语境下禁」，别把保留用法一起拦进来。

**怎么判断该进哪一档**：先看这个词在 renderer 里的存量。已经归零 → 硬拦档（锁住成果）；还有存量 → 棘轮档（冻结 + 防新增）。**不许为了让 lint 变绿而调高地板**——那是把棘轮拆了。

**维护规矩是单向的**：

```text
先改 docs/LAWMIND-TERMINOLOGY.md
  → 再同步 lawmind-ui-copy-lint.mjs 的禁词清单与棘轮地板
```

**不能反过来**（先改脚本再改表），否则表的权威性就没了，两边会慢慢分叉。

**存量合法用例**登记在 `scripts/lawmind/ui-copy-lint-allowlist.json`，要写理由。这样「确实需要出现路径」的地方（比如设置页里的「工作区目录」）可以豁免。

## 32.6 好文案的几条实践

从仓库里那些写得好的文案，能提炼几条规律。

### 规律一：报错要说「下一步做什么」

对比：

| 差的         | 好的（仓库里的真实文案）                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `文件不存在` | `找不到草稿 <id>。请先 draft_document 建审查表草稿。`                                                                                            |
| `权限不足`   | `当前权限模式为只读（readonly），不能使用「xxx」。请改用只读检索/分析工具收集材料；确需起草、导出或外发时，请律师把权限模式切换为标准后再执行。` |
| `参数错误`   | `edits 必须是非空数组，每项为 { find, replace, note?, occurrences? }`                                                                            |

**规律：报错要包含「发生了什么」+「怎么办」。**

### 规律二：不确定就说不确定，并给出路径

| 场景           | 文案                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 没接类案库     | 「本机未接类案库。要查真实类案：自建 cncases 索引（本机可达即自动启用）……在此之前的检索只能给工作区线索，**引擎不会编造案号或裁判要旨**。」 |
| 法源是演示语料 | 「演示语料（非正式完整法库；正式引用请核对官方法条）」                                                                                      |
| 结果被策略收窄 | 「如实告诉律师『范围被策略收窄了』，不要让它看起来像『网上就是没有』」                                                                      |

**规律：诚实说明限制，并告诉律师怎么获得更可靠的结果。**

### 规律三：区分「没有」和「没查到」

| 情况         | 说法                                                                          |
| ------------ | ----------------------------------------------------------------------------- |
| 功能没开     | 「先例检索未开启：跨案读取需律师显式授权（……）。开启并重建索引后可用。」      |
| 开了但没查到 | 「未检索到相关法条/案例。模型不得编造条文；请换关键词或请律师提供权威文本。」 |

**规律：把「因为没开所以没有」和「查了但没有」分开说。** 这也是指标里 `null` 和 `0` 的区别（第 12 章）。

### 规律四：拒绝要解释原因，而不是只说规则

| 场景             | 文案                                                                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 本机文件夹不能改 | 「本机文件夹默认不能改写。**请使用「收进本案」复制到案件目录。**」                                                                             |
| 空修订不许导出   | 「合同审阅稿尚无待叠加修订（redline hunks=0，至少需要 1）。**禁止仅写 summary 后空修订导出。**」                                               |
| 治路径不能改     | 「该路径属于 LawMind 治理/审计数据（策略、MCP 配置、审计、会话、任务、案件真相源），不能通过写文书或文件接口修改；**请使用对应的设置入口。**」 |

**规律：先说你为什么被拦住，再给替代路径。**

### 规律五：状态词用中文，且和代码语义对齐

| 代码                                                                      | 界面                                                |
| ------------------------------------------------------------------------- | --------------------------------------------------- |
| `pending_review`                                                          | 待审核                                              |
| `approved`                                                                | 已批准                                              |
| `planned` / `drafting` / `rendered` / `delivered` / `learned` / `blocked` | 已规划 / 起草中 / 已渲染 / 已交付 / 已沉淀 / 已阻塞 |

界面标签和生命周期状态是一一对应的（`deliverableStatusLabel`）。

## 32.7 数字和指标的口径文案

第 12 章讲了「诚实 null」规则。落到文案上，有几条要求：

| 情况       | 显示                             |
| ---------- | -------------------------------- |
| 没有样本   | 显示成「暂无数据」，**不是 0%**  |
| 数据源缺失 | 明确说「这个来源从未产生过数据」 |
| 有样本     | 显示比率，并说明口径             |

而且每条指标都该能回答「这个数怎么算的」。`metrics/README.md` 就是这份口径说明。

有一条文案值得单独抄：

```text
本次机械核对 N 项，其中 M 项由确定性规则判定，K 项需您定夺。通过核对 ≠ 法律正确。
```

**最后半句是刻意加的**，它防的是「把核对通过当成质量保证」。

## 32.8 免责与边界文案

有三个地方有固定文案：

| 场景                 | 文案                                                      |
| -------------------- | --------------------------------------------------------- |
| 会议室纪要开头       | 「## 案件团队会议室纪要（内部协作用，非对外法律意见）」   |
| 导出文件落款         | 统一的律师责任免责声明（`LAWMIND_ATTORNEY_DISCLAIMER_*`） |
| 设置里的免责声明分区 | 使用边界与责任                                            |

「非对外法律意见」这半句在会议室场景是必须的——讨论内容不是给客户的。

## 32.9 写新文案时的一张检查表

```text
[ ] 用的是术语表里的词吗？
[ ] 有没有出现文件路径、英文枚举、门禁术语？
[ ] 报错说了「怎么办」吗？
[ ] 如果是「没有」，说清是「没开」还是「没查到」吗？
[ ] 如果是拒绝，给了替代路径吗？
[ ] 涉及数字，口径说清了吗？
[ ] 涉及不确定，标出来了吗？
[ ] 有没有把内部机制（sidecar、提示词、门禁）暴露给律师？
[ ] pnpm lawmind:ui-copy-lint 过了吗？
```

## 32.10 一个反例分析

假设要写一句「导出失败」的提示。三种写法的对比：

| 写法                                                                  | 问题                                                |
| --------------------------------------------------------------------- | --------------------------------------------------- |
| `Export failed: EACCES`                                               | 两个问题：英文 + 错误码。律师看不懂，也不知道怎么办 |
| `导出失败`                                                            | 太笼统。不知道是权限、是格式、还是磁盘满            |
| `导出失败：目标文件被占用。请先关闭正在打开该文件的 Word，然后重试。` | 好：说了原因、给了动作                              |

**第三种写法的信息来源**：它需要写代码的人**先把错误分类**（哪几种失败、分别怎么处理），然后才能写出这种文案。

这也是为什么好的报错文案通常出现在**踩过坑**的地方——因为那时候才知道有多少种失败。

## 32.11 已知坑（本章相关）

- **禁词表是「表 → 脚本」单向。** 别反过来改。
- **存量残留还在收敛中。** 「文书台」「复核」已归零并进硬拦档。棘轮地板只许下降。
- **别调高棘轮地板来让 lint 变绿。** 新增近义词要改文案，不是改地板。
- **禁词要写「在什么语境下禁」。** 「语料」「修订」都有合法保留用法，一刀切会把自己的文案也拦掉。
- **单行导出的文案常量也在扫描范围内。** `export const LABEL = "复核"` 会被拦——只有 `import` 行与不解出字符串字面量的 `export` 行才跳过。别想用 `export const` 藏文案。
- **「合同审查」可以保留**（业务场景名），但「审查」作动作时要用「审核」。
- **allowlist 要写理由。** 别为了过 lint 就往里加。
- **文案质量取决于错误分类的细度。** 想把报错写好，先得把失败原因分清楚。
- **不要为了让文案好看而弱化限制。** 比如「本机文件夹默认不能改写」这句必须保留「不能」——改成「建议收进本案」会让人以为可以硬来。

# 第 29 章 踩坑案例集

这一章把代码注释里记录过的真实故障整理成案例。**每个案例都是「看起来很合理但实际错了」的那种**，所以特别值得读。

统一结构：**症状 → 根因 → 怎么发现的 → 修法 → 教训。**

## 29.1 端口漂移：一次连锁失联

**症状**

Word 任务窗格报 `unauthorized`，而且**每次重启 LawMind 都复发**。后来服务换了端口，窗格改报 `Load failed`（网络错误）。两个症状都看不出真正原因。

**根因**

三层叠加：

1. **一把共享令牌服务四种客户端**（桌面 / 渲染进程 / Word 插件 / CLI）。令牌是「每进程随机、只下发一次」的，Word 插件在页面加载时取一次就不再取。重启后令牌变了，已打开的窗格必然 401。
2. **端口是持久化的**（Word 侧载清单钉死了端口）。第二个实例启动时发现端口被占，`pickPort` **静默**回退到随机端口。
3. 端口一变，所有已侧载的窗格失联，而且**窗格无处重新发现新端口**（发现端点也挂在旧 base 上）。

**怎么发现的**

真机联调时反复出现，日志里看不出异常。后来注意到「换个端口之后症状从 `unauthorized` 变成 `Load failed`」这条线索，才定位到端口漂移。

**修法**

三管齐下：

1. **派生化凭据**：`HMAC-SHA256(安装密钥, "<clientId>:<epoch>")`。同一安装密钥 + 同一客户端 + 同一代次永远算出同一个值，重启不换钥匙。加一代宽限期避免轮换时全体 401，加吊销名单支持单独吊销。
2. **端口变了自己写回已安装的 Word**（不往「下载」里丢文件）。另一个 LawMind 占着原端口时不改写。Word 连接组（设置 → 外观）只请律师重新打开 Word，不展示端口。
3. **只记来源**：反查客户端时能知道「这次改稿是从 Word 来的还是从桌面端来的」——审计以前只能记「是谁」，记不出「从哪来」。

**教训**

**「静默回退」是最危险的一类降级。** 端口被占时换一个随机端口，从程序角度看是「优雅处理」，从用户角度看是「整个功能失效而且不知道为什么」。

判断标准：**一个降级如果会让用户看到和真实原因完全无关的报错，它就必须被暴露出来。**

## 29.2 CORS 头漏写：前端报网络错误，后端全绿

**症状**

界面上报「无法连接本地服务」，但服务端日志一切正常——**甚至已经 200 并把 zip 写完了**。审计里能看到 `status: "error"` 且 `durationMs` 只有 4–8ms（不是超时）。

**根因**

某条路由**手写 `res.writeHead(...)` 时忘了带 CORS 头**。渲染进程对本服务是跨源（开发态 `127.0.0.1:5174`，打包后 `file://`），浏览器在几毫秒内直接拦掉响应，前端拿到的是 `TypeError: Failed to fetch`。

而走 `sendJson(res, ..., c)` 的路由不会有这个问题——工具函数自动带了头。

**怎么发现的**

前端报错和后端日志完全对不上，排查了很久。后来对比「正常的路由和异常的路由有什么不同」，才发现是手写 `writeHead` 的那几条。

**修法**

1. 注释里写「手写 `writeHead` 时必须带 `...c`」。
2. **加一条结构守卫测试**：用正则扫服务端所有手写 `writeHead`，要求必须带 CORS 载体。

第二条是关键。注释里已经写了这句话，而**写代码的人还是漏了**——因为「写了注释」不等于「有人检查」。

**教训**

**光在注释里写「不要忘」是没有用的。** 能被机器检查的约束就该交给机器。这条 bug 最后是靠一个正则测试守住的。

另外记住这个症状组合：**前端几毫秒内失败 + 后端 200 + 日志全绿 = 大概率是响应头问题。**

## 29.3 监督进程先抢锁：`lawmindd` 从来不 tick

**症状**

「关窗后继续办件」这个功能实际是坏的——关掉窗口后，后台什么也不做。

**根因**

监督进程先抢了锁，然后 fork 子进程；子进程也抢同一把锁，必然失败并「让位」。结果是**真正该干活的 tick 子进程从来没启动成功**。

**怎么发现的**

两个函数各自单测都通过。**是端到端测试（`daemon-supervision.spec.ts`）抓到的。** 注释里专门写了一句话：

> 两个函数各自单测都对，拼起来才错。

**修法**

锁和 pid 的所有权明确归 tick 子进程，监督进程**故意不清**它们。

**教训**

**单元测试覆盖不到「两个模块拼起来」的错误。** 这类错误的特征是：每个部分的行为都符合自己的规格，但组合起来的时序错了。

所以有真机端到端测试这条线，而且它测的正是「关窗 → 后台继续跑」这种跨进程时序。

## 29.4 守护定时器 unref：进程立刻「正常退出」

**症状**

守护进程启动后立刻退出，日志里 `[lawmindd] 启动` 之后紧跟「退出 clean exit_code=0」。看起来像「启动成功然后干干净净地结束了」。

**根因**

守护模式下那个 30 秒的 tick 定时器是**唯一的存活句柄**。`unref()` 之后事件循环随即空掉，进程正常退出。

**修法**

守护模式下**不 unref**；非守护模式才 unref（避免阻塞应用退出）。

**教训**

「正常退出」未必正常。没有错误码的退出可能是最迷惑人的——因为所有日志都是成功的。

## 29.5 `localhost` 不等于 `127.0.0.1`：Word 报「请检查网络连接」

**症状**

Word 任务窗格报：

```text
很抱歉，无法加载该加载项。请确保您具有网络和/或 Internet 连接。
```

**根因**

`localhost` 在 macOS 上同时解析到 `::1`（IPv6）和 `127.0.0.1`（IPv4），而 WebKit（Word 任务窗格用的就是它）**通常先试 `::1`**。服务只绑了 IPv4，那条路是死的。

**修法**

服务同时监听两个协议族（`127.0.0.1` 和 `::1`）。仍然是回环，不对局域网暴露。

**教训**

**报错文案可能完全指向错误的方向。** 「请检查网络连接」让人去查防火墙和代理，而真正的问题是 IPv6 没监听。

遇到「网络类」报错时，先确认「它实际连的是哪个地址」。

## 29.6 CSP 拦掉内联脚本：凭据为空，所有请求 401

**症状**

Word 任务窗格的 base 与凭据都为空，所有请求 401。

**根因**

凭据写在了页面里的内联 `<script>` 里。Word 任务窗格启用 CSP，`script-src` 会把内联脚本拦掉，于是那个变量根本没被赋值。

**修法**

改成同源提供一个 `config.js` 文件。

**教训**

这类问题的表现是「功能完全不可用」，但原因是「一个变量没赋值」。**CSP 违规通常在控制台里有提示**——排查前端「变量是空的」问题时，先看控制台有没有 CSP 报错。

## 29.7 Word.js 的队列式 API：不 load 就读不了

**症状**

落改时报「属性…不可用」。

**根因**

Word.js 是**队列式 API**：属性/集合必须先 `load()` + `context.sync()` 才能读。不 load 就走，Word 直接抛错。

**修法**

固定了落改顺序：

```text
load 修订轨设置 → sync → 打开修订轨 → sync
→ 逐个锚点 search/load/sync → 恢复律师原本的修订轨设置 → sync
```

**「恢复律师原本的修订轨设置」这步容易被漏**——你不能改完就走人，把律师的 Word 设置改了。

**教训**

第三方插件 API 的「怪脾气」要用注释固化下来。这条注释救的是后来改这块代码的人。

## 29.8 只读工作副本：`applied: 0` 而且不报错

**症状**

导出后 Word 里没有任何修订痕迹，但程序报告「成功」。

**根因**

从 Finder / 项目目录拷过来的 Word 文件经常是**只读的**（权限 0444）。officecli 无法往只读副本写 `w:ins`/`w:del`，返回 `io_error`，结果是 **0 处应用**。

**修法**

落改前 `chmod 0o644`。而且拷贝前还有一次——因为之前失败过的运行可能留了个只读的同名文件。

**教训**

**「0 处应用」这类结果必须当成错误处理。** 它比「失败」更危险，因为看起来像成功。

顺带一条：这类问题的首次症状是「改完没变化」，而不是报错。

## 29.9 加密信封的明文穿透：一个降级攻击

**症状**

（这是代码审查发现的，不是线上故障。）

**根因**

早先的实现里，如果输入**不是**加密信封格式，代码会**原样放过**（当作明文处理）。

这意味着攻击者把密文换成明文，系统照收——**所有封装材料的保密性归零**。

**修法**

改成抛错：

```text
not a sealed envelope (refusing plaintext passthrough)
```

**教训**

**「兼容性处理」和「安全漏洞」有时是同一行代码。** 「不是信封就当明文」看起来是宽容，实际是给攻击者开了门。

判定原则：**如果一种输入格式只可能来自攻击者，那就应该拒绝，而不是兼容。**

## 29.10 材料块不验哈希：任何能写中继的人都能往卷宗塞东西

**症状**

（同样是审查发现的。）

**根因**

早期版本里，接收材料时直接用中继给的字节，**不比对清单里的 sha256**。

**修法**

每个块重算哈希比对，不符就记审计 `collab.integrity_rejected` 并拒收。大文件分块重组时再验一次。

**教训**

**「内容寻址」只有在真的验证时才成立。** 按哈希命名但从不校验，等于没做内容寻址。

这条配合 29.9 一起看：一个防「换内容不换名」，一个防「换密文为明文」。

## 29.11 误报率恒为 0：所有判断项都被自动升级

**症状**

（自查发现的。）判断项棘轮看起来工作得很好——每一项都「可升级」。

**根因**

判定条件写错了：

> 棘轮只在「恰好一项报项 **且** cleanDelivery」时才计入误报，两个条件互斥，于是 `firedClean` 恒为 0、误报率恒为 0，**每一项都会被判可升 blocking**。

**修法**

修判定逻辑，并在测试里加了三条不变量（和 `isAutonomyUnlocked` 保持一致）。

**教训**

**「指标一直很好看」和「指标算错了」长得一模一样。** 这类 bug 最难发现，因为它的表现是「一切正常」。

防御方式：给关键指标加**不变量测试**——不是测「值对不对」，而是测「不可能出现的组合不会出现」。

## 29.12 验收总览的计数偏高：字段名写错

**症状**

律师看到的「阻断项计数」比实际多。

**根因**

代码写成 `!c.ok`，而 `AcceptanceCheck` 的字段其实叫 `passed`。`c.ok` 永远是 `undefined`，`!undefined === true`，于是**每一项 blocker 都被算成未通过**（连已通过的也计）。

**修法**

改成 `!c.passed`。

**教训**

- TypeScript 下这种错本该被类型检查拦住——说明当时那块代码的类型不够严。
- **律师可见的计数出错是双重问题**：算错了，而且没人会想到去核对一个「看起来合理」的数字。

## 29.13 `facts_grounded` 恒为 0：一个惰性检查项

**症状**

（实测发现的。）推理门的「事实充分度」检查从来没起过作用。

**发现过程**

用真实工作区实测：136 份 `drafts/*.reasoning.json` 里——

- 争点数为 0 的有 **117 份（86%）**
- `facts > 0` 的有 **0 份**
- `evidence > 0` 的有 **0 份**

结论写在注释里：「这一层在真实使用中基本是惰性的。」

**处理方式**

当时没有删掉这个检查，而是降成 warning，并把实测数据留在注释里。

后来的改法遵守「判断交给模型」：未被引用的材料不写入争点事实，只在交付风险里列出短摘录，文案是自行判断是否写入。`facts_grounded` 仍是 warning。升成 blocker 会在模型还没引用材料时拦住交付。

**教训**

这是本书里我最推荐的工程实践之一：**发现一个检查项是惰性的，就把实测数据写下来、把它降级、并写清升级条件。** 而不是留着它假装有用，或者直接删掉。

## 29.14 编辑样例被截断：「为什么改」丢了

**症状**

改稿范例注入之后，模型对例子「照搬」而不理解。

**根因**

首版把 600 字的两侧原文原样塞进提示词，结果**提示词打包器在范例块中间截断**，把末尾的「律师说明」（最值钱的「为什么改」）挤掉了。

第二版把说明移到每例末尾——**又被截断挤掉**。

**修法**

两件事：

1. **存得宽、注入得省**：存储上限 600 字，注入上限 220 字。
2. **字段顺序也是设计**：律师说明写在**标题行**（每例最靠前的位置）。

**教训**

- 「截断」不是简单的信息损失，**它会系统性地丢掉位于末尾的最重要信息**。
- 如果你有一个「必然被截断」的字段，那它的位置就应该在开头。

## 29.15 自动化反复重派同一份材料

**症状**

「邮件合同审阅改稿」每 120 分钟派一次同一份附件，反复撞同一道门禁。

**根因**

那一件已被独立审稿门禁停在 `guardian_exhausted`，但：

1. 门禁停下后**只在对话正文里留了一句话**，律师在「在办 / 待拍板」看不到「这一件等着我处置」。
2. 自动化不知道「这件已经因为门禁停过」，于是重派。

**修法**

两部分：

1. **门禁停下必须产生一个律师可见的待处置项**（而不是只留在对话里）。
2. **派发台账**记住「这件因为门禁停过」，不再重派。

**教训**

**「状态收口」和「状态可见」是两件事。** 轮次结束了不等于律师知道有东西等他处理。

判断标准：**任何「等律师处理」的状态，都必须出现在律师会看的那个界面上。**

## 29.16 谈话写了等于没写

**症状**

律师在对话里说了案由和当事人，但打开工作台卷宗看不到。

**根因**

`apply_intake_brief` 原本只打了一个 `confirmedAt` 时间戳，而谈话里读到的案由、当事人留在 `intake-brief.json` 里。**工作台卷宗看的是 `matter.json`。**

注释里直接引了同类故障的例子（Claude Code 的 issue #55750：「已落盘但模型/界面看不到」），并给了一句总结：

> 说明这类「写了等于没写」最伤信任。

**修法**

加一层「写穿」：把抽取到的值提升到 `matter.json`，三条原则——

1. 只提升抽取器真正读到的值，绝不编造。
2. 只提升卷宗里还没有的字段，不覆盖律师手输的。
3. 立场不明时不猜我方立场。

**教训**

**「数据写进去了」和「用户看到了」是两个不同的验收标准。** 前者的测试很容易过，后者的测试才反映真实体验。

## 29.17 当事人上限 8：第 9 个人静默消失

**症状**

共同诉讼有 10 个被告，第 9、10 个填不进去，而且**没有任何提示**。

**根因**

`MATTER_PARTIES_CAP` 是 8，超出部分被静默丢弃。注释写得很直接：

> 共同诉讼（多被告/多第三人）常超 8 人，旧值 8 会把第 9 人起静默丢弃。上限只防病态输入，不应当成为「填不全当事人」的原因。

**修法**

上限改成 32。

**教训**

**静默截断是一种设计缺陷，不是容错。** 如果必须有上限，至少要让用户知道被截了。

## 29.18 重写幅度测错了对象

**症状**

「改稿幅度」这个指标看起来正常，但它回答的不是想问的问题。

**根因**

注释里的原话：

> 此前只有 `draft-revision` 一条路径产出样本，而**律师最常用的直接改稿路径不产出** —— 于是「改稿幅度」实际测的是助手，与它要回答的问题不符。

也就是说：想问「律师把我写的稿改了多少」，实际测的是「后台修订助手把稿改了多少」。

**修法**

加 `source` 字段区分两种来源（`assistant_revision` / `lawyer_edit`）。

**教训**

**指标名和指标实际测的东西可能不一致**，而报表上看不出来。所以每个指标都该写清口径（这个仓库的 `metrics/README.md` 就是干这个的）。

## 29.19 采纳服务的并发丢记录

**症状**（设计阶段发现。）

`adopt` 的「读-改-全量重写」会用旧快照覆盖并发 `suggest` 的 `append`，**静默丢记录**。

**修法**

两层锁：进程内一个互斥队列 + 跨进程一把 `O_EXCL` 文件锁，让 append 和重写共用同一把锁。

**教训**

**「追加」和「全量重写」混在同一个文件上，不锁就一定丢数据。** 这是 JSONL 存储的经典陷阱。

## 29.20 退出离线模式后偏好被抹掉

**症状**

律师开了离线模式，后来又关掉，发现联网偏好回不来了。

**根因**

`PATCH /api/policy/workspace` 曾经**静默地把 `allowWebSearch` 写成 `false`**。

**修法**

改成只写「总模式」（`egressMode`），联网偏好一律在读取时按 `egressMode` **推导**。

注释里的原则：

> `egressMode` 与 `allowWebSearch` 的关系是**上限 vs 偏好**：本模式为 offline 时联网强制关闭，但不改写 `allowWebSearch`，所以退出离线模式后律师原偏好自动恢复。

**教训**

**「临时压制」不应该实现成「永久改写」。** 很多「设置了一个开关，另一个设置就回不来了」的 bug 都是这个模式。

## 29.21 判断项升级通道的静默覆盖

**根因**（注释记录的推理）

`lawyer` 类判断项的定义是「不判，只升级」。如果升级卡片不存在就把这些项从提示词里摘掉，那么：

> 这些项**既不被任何判定器判、也不会出现在任何卡片上**——它们会**安静地消失**。

**修法**

加一条开关专门管这件事（`judgmentEscalation`），而不是让「没有卡片」等价于「不需要」。

**教训**

**「因为没有通道所以静默丢弃」是最隐蔽的一类 bug。** 一个东西从系统里消失，通常不会报错。

## 29.22 两份清单要手工同步

**症状**（结构性风险）

`protected-workspace-rels.ts` 和 `electron/fs-bridge.mjs` 是两份**手抄的常量清单**，靠注释约束同步。

原因：Electron 主进程是 `.mjs`，不能 import TS。

**现状**

工程研究笔记曾把它列为「真正值得加一条『两份清单一致性』单测的地方」。**这条测试现在已经有了**：`apps/lawmind-desktop/electron/fs-bridge.test.ts` 的 `fs-bridge mirrors engine constants` 逐项比对拒写文案、机器可读错误码、可写根白名单与受保护路径归类。它的注释写得很直白——「没有这层守卫时，只改一边不会有任何测试变红，结果是『引擎拒绝、桌面放行』这类最难查的不一致」。

**教训**

**因为技术限制而复制的常量，是最容易漂移的地方。** 如果必须复制，至少要有测试比对两份——这个案例的后半段正好是「后来真的补上了那条测试」。

## 29.23 内置技能 37 份，种子清单曾少 2 个

**症状（已关闭）**

仓库里有 37 份内置正文，种子清单曾经只有 35 个 id。`client-talk-intake` 和 `legal-event-extract` 不在 `BUILTIN_SKILL_SEED_IDS` 里。

**现状**

这两个 id 已补进播种名单。`ensure-builtin-skill-seeds.test.ts` 要求名单和 `builtin/*.md` 的 id 一致。回合本身只读目录，不读种子名单。

**教训**

两份清单之间的一致性，只要没有测试，就一定会漂。

## 29.24 从这些案例里提炼的五条

把这 23 个案例读完，能提炼出五条通用规律：

### 一、静默降级最危险

端口漂移到随机口、只读文件导致 0 处应用、只读上限静默截断、密钥不可用降级成弱链——**凡是「悄悄换成次优方案」的地方，都是最难排查的地方。**

对策：降级必须可见，而且报错要指向真因。

### 二、注释挡不住回归，测试才能

CORS 那条注释写了，人还是漏了；最后靠正则测试守住。两份常量清单写明了「必须同步」，但没有测试。

对策：**能被机器检查的约束，全部交给机器。**

### 三、「看起来正常」的数据最危险

误报率恒 0、计数偏高、`facts` 恒 0、指标测错对象——这类问题全都表现为「一切正常」。

对策：给关键指标加不变量测试与口径说明。

### 四、写了不等于用户看到了

谈话写穿、门禁停下只在对话里留一句话、审计记了但界面看不到。

对策：把「用户可见」当成独立的验收标准。

### 五、单测覆盖不到组合错误

监督进程抢锁、CORS 头、守护定时器 unref——这些都要真机端到端跑才暴露。

对策：保留真机 E2E 套件，而且让它测**跨进程时序**这种事。

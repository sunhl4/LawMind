# 第 40 章 性能与规模实践

这一章讲「什么样的使用方式会快、什么会慢」，以及慢的时候查哪里。

## 40.1 哪些操作快、哪些慢

按设计意图分三类：

| 类别                         | 例子                         | 设计目标                 |
| ---------------------------- | ---------------------------- | ------------------------ |
| **必须快**（打开界面就走的） | 今日一屏、案件快照、材料列表 | 同步、不扫审计、不算哈希 |
| **可以慢**（用户点了才跑的） | 检索、起草、导出             | 可以跑几秒到几分钟       |
| **重活**（要显式触发）       | 重建索引、历史扫描、深度研究 | 有开关或明确入口         |

**判断一个功能属于哪类，看它有没有被刻意做成「廉价」的**：

| 功能       | 廉价化的做法        | 注释依据                                                |
| ---------- | ------------------- | ------------------------------------------------------- |
| 案件快照   | 同步、不扫审计      | 「Sync, no audit scan」                                 |
| 材料列表   | 不算 SHA 哈希       | 「No SHA hashing — pulse/open-dossier must stay cheap」 |
| 工作台今日 | 纯读、不写文件      | —                                                       |
| 相似案件   | 有限条数 + 分数阈值 | —                                                       |

## 40.2 打开界面慢

**先看案件数和材料数。** 案件多时列表渲染可能慢；材料多时枚举目录可能慢。

**可以做的**：

1. 材料按需放进案件（不要把所有历史文件都倒进 materials）。
2. 归档已结案的案件（减少列表长度）。
3. 检查是不是索引没建好。没索引时工作区检索不会扫全库，只会补记忆文件里的字面命中，并在结果里写明要去设置 → 工作区重建。

## 40.3 一个回合跑很久

**先看它现在在做什么**：

```text
GET /api/sessions/:id/live-turn
```

**常见的三种「慢」**：

| 现象         | 原因           | 怎么办                                              |
| ------------ | -------------- | --------------------------------------------------- |
| 反复检索     | 检索工具在空转 | 有专门的空转门禁（回执会给「换个做法」的建议）      |
| 一直在跑工具 | 工具多         | 用 `update_plan` 明确步骤；每轮工具上限已被策略拒收 |
| 卡在等审批   | 审批没处理     | 看「待我拍板」                                      |
| 模型本身慢   | 供应商         | 换模型或错峰                                        |

**注意**：工具预算的软上限到了不会打断你（硬顶只防空转）。

## 40.4 上下文用得快

**看用量分解**（`GET /api/sessions/:id/context-budget` 或界面的用量表）。

按桶排查：

| 桶大      | 原因           | 怎么办                                              |
| --------- | -------------- | --------------------------------------------------- |
| 钉选      | 钉了大文件     | 只钉必要的；或者让它先摘录要点                      |
| 工具结果  | 读了很多大文件 | 用 `read_folder_documents` 批量读（它内部会控制量） |
| 摘要      | 压缩次数多     | 用「承前分叉」另起一段                              |
| 律师/助手 | 对话本身就长   | 同上                                                |

**一个技巧**：如果一件事办完就结束了，用「承前分叉」把它留在旧会话里，新会话只带摘要。

## 40.5 检索慢

| 情况         | 原因                          | 怎么办                            |
| ------------ | ----------------------------- | --------------------------------- |
| 工作区检索慢 | 索引没建好或正在重建          | 设置 → 工作区里重建；空结果非全库 |
| 法源检索慢   | 网络 + NPC 节流（1.5 秒间隔） | 正常；hybrid 模式会依次试多条车道 |
| 深度研究慢   | 它本来就要跑多轮              | 用 `breadth` / `depth` 控制规模   |
| 材料检索慢   | 首次会做增量入库              | 之后会快                          |

NPC 的节流和缓存是**有意的**（不给人家站点添麻烦）。所以「查法条要等一两秒」是正常的。

## 40.6 导出慢

Word 修订轨导出要调 officecli，超时设的是 120 秒（`120_000`）。

**影响因素**：

| 因素               | 影响                                        |
| ------------------ | ------------------------------------------- |
| 原合同大小         | 大文件慢                                    |
| 改动处数           | 每处要定位一次                              |
| 二进制 `.doc` 基线 | 要经过转写（可能还要装 Word / LibreOffice） |
| 多处命中需要消歧   | 每处要试多个后顾宽度（8/12/16/24/32/48）    |

**如果经常超时**：先看是不是原文件太大，或者改动处太多（考虑分批）。

## 40.7 大工作区的注意点

| 项           | 建议上限                    | 超过会怎样                              |
| ------------ | --------------------------- | --------------------------------------- |
| 案件数       | 几百                        | 列表渲染变慢                            |
| 单案件材料数 | 几百                        | 材料列举有 80 条展示上限，遍历上限 4000 |
| 单文件大小   | 50MB（材料）；200MB（拖入） | 超大文件被略过                          |
| 审计文件     | 不限                        | 按天分文件，读取时可限制天数            |
| 对话历史     | 靠压缩控制                  | 压缩后仍长就建议分叉                    |

**有几个硬上限是设计好的**（不要随手改大）：

| 上限         | 值   | 位置                            |
| ------------ | ---- | ------------------------------- |
| 材料列表展示 | 80   | `MATTER_MATERIALS_LIST_CAP`     |
| 材料遍历     | 4000 | `MATTER_MATERIALS_WALK_CEILING` |
| 当事人       | 32   | `MATTER_PARTIES_CAP`            |
| 历史扫描根   | 3    | `MAX_SCAN_ROOTS`                |
| 历史扫描文件 | 2000 | `MAX_SCAN_FILES`                |
| 后台任务保留 | 200  | `MAX_JOBS`                      |
| 委派活跃数   | 5    | policy                          |
| 委派深度     | 3    | policy                          |

## 40.8 并发

| 层             | 并发                                   |
| -------------- | -------------------------------------- |
| 工具批次       | `getMaxToolUseConcurrency()`（默认 4） |
| 工作流步骤     | 同上                                   |
| 抽取（审查表） | 默认 4，上限 16                        |
| 检索适配器     | 并行（`Promise.allSettled`）           |
| 同一会话的回合 | **串行**（回合门）                     |

**同会话回合串行是有意的**（第 3 章那个回合门）。所以不要指望「同一个会话里两个回合并行」。

## 40.9 慢的时候先看什么

按这个顺序：

1. **它在干什么？** `GET /api/sessions/:id/live-turn`。
2. **有没有卡在门禁或审批？** 看「在办 / 待我拍板」。
3. **上下文是不是很满？** 看用量表。
4. **索引是不是陈旧？** 设置 → 工作区（「查找」组只在需要时出现），或 `pnpm lawmind:doctor`。
5. **服务有没有降级？** `doctor.process.degraded`。
6. **是不是限流了？** `doctor.rateLimit`。

**这六步能覆盖绝大多数「怎么这么慢」的情况。**

## 40.10 三条「不要为了快而做」的事

这个仓库里有几处刻意**不优化**的地方，值得知道：

| 看起来可以优化         | 为什么不做                         |
| ---------------------- | ---------------------------------- |
| 材料列表加哈希校验     | 会让打开变慢；校验只在副本发布时做 |
| 案件快照扫审计日志     | 会让工作台变慢；审计是另一条线     |
| 把检索结果全塞进上下文 | 会挤爆预算；只放需要看的           |

**共同逻辑**：**性能优化不能牺牲「该验的要验」和「该慢的要慢」。** 比如材料哈希校验在大文件传输时是必须的，只是不能放在「打开案件」这一步。

## 40.11 已知坑（本章相关）

- **NPC 有 1.5 秒节流和 5 分钟缓存。** 查法条慢一点是正常的。
- **同会话回合是串行的。** 不要期待并行。
- **材料列表不算哈希。** 想校验走案件副本那条路。
- **索引不在时不会全表扫描。** `search_workspace` 先尝试重建。重建后索引仍不在，或检索抛错时，结果带 `indexMissing`，并说明其余命中只是记忆文件的字面补充。
- **导出超时 120 秒。** 大文件或改动多时可能不够。
- **图片不做全库 OCR。** 所以「搜图片里的字」搜不到，除非走按需抽取。
- **不要随手抬那些硬上限。** 它们防的是病态输入和内存爆掉。
- **「怎么这么慢」先看六步**，别一上来就怀疑代码。

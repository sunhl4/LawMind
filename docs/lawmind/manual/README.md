# LawMind 功能与实现手册

本手册逐项讲解 LawMind 的**每一个律师可见功能**，以及该功能**在代码里如何实现**。它不是营销材料，也不是全部 `docs/` 的目录复制：每个功能都给出「律师侧怎么用 / 边界在哪」与「实现侧调用链、关键文件、数据结构、门禁、测试」。

**规模**：79 个 md 文件（71 章 + 5 附录 + 总目录 + 总索引 + 改动定位表），约 **36.8 万字**（汉字 315,251 + 标识符 53,018），全部经 `markdownlint-cli2` 零告警。数字是 2026-09-24 的快照。

- **找不到入口？** 先看 [`INDEX.md`](./INDEX.md)——按「问题 / 模块路径 / 命令 / 术语 / 坑」五张表反查。
- **改了代码要动手册？** 先看 [`MAINTENANCE-MAP.md`](./MAINTENANCE-MAP.md)——按「改动类型 → 该改哪章」定位，含逐章职责边界与改动清单。
- 面向读者：一方面给**律师 / 交付实施**（每章的「怎么用」与速查，以及第 25、26、27、31、33、38、41、42 章），另一方面给**工程师 / 二次开发者**（各章「实现」与第 43–71 章的实现精读）。
- 路径口径：全部使用**仓库根相对路径**（例如 `src/lawmind/agent/turn-orchestrator.ts`）。
- 所有章节均已完成（对照仓库代码逐节核对）。本手册的定位是「读到就能动手」，所以写清了失败模式与「不要这么做」。

## 写作约定

- 涉及代码事实时给出**仓库根相对路径**；引用函数名用行内代码。
- 「已知坑」只写代码里能验证的（多来自源码注释里的真实故障记录），不写猜测。
- 术语遵循 `docs/LAWMIND-TERMINOLOGY.md`。
- 本手册是**新增的独立目录**；除两处例外，不改动仓库里其他文档。两处例外都有明确理由：① `apps/lawmind-docs/docs/.vitepress/config.mts`（加手册的站上入口）；② 手册正文里如实记录的既有不一致，**改的是手册的描述、不去改被描述的代码**（比如技能 37 vs 35 的漂移只写进 `INDEX.md` 5.3 与第 11 章，不动播种名单）。
- 维护本手册时：内容有变先改对应章节，再跑 `npx markdownlint-cli2 "docs/lawmind/manual/*.md"`。**改了代码不知道动哪章，先查 [`MAINTENANCE-MAP.md`](./MAINTENANCE-MAP.md)。**
- **改了章号或小节号时**，跑一次 `python3 docs/lawmind/manual/check-crossrefs.py`（在 `docs/lawmind/manual/` 下跑）：
  - **① 悬空必须为 0**（引用了不存在的小节）。
  - ② 跨章与 ③ 熵差只是提示——它们查不出「小节号存在但指的是另一件事」。**真正有效的是抽查一批**：读被引用小节的标题，看它和引用句是不是同一件事。2026-09-23 那轮抽查修掉了 22 处语义错位，② ③ 都报不出来。

## 与文档站的关系

`apps/lawmind-docs/scripts/sync-docs.mjs` 会把整个 `docs/lawmind/` 目录同步进 VitePress 站，所以本手册**自动发布会**，不需要改同步脚本，也不占用「现行文档清单」那 9 篇的契约。

站上入口有两处（2026-09-23 加入 `config.mts`）：导航顶层的「手册」指向本文件的 `README`；侧栏「功能与实现手册」组放总目录与 `INDEX`。**71 章没有逐章列进侧栏**——那会把侧栏撑成电话簿；章级跳转交给本文件下面的目录与 `INDEX.md`。

核对方法：

```bash
pnpm lawmind:docs:dev     # 会先 sync，然后在文档站里应能看到 docs/lawmind/manual/
```

# 第 41 章 效果评估与持续改进

这一章讲「怎么知道用了之后到底有没有变好」，以及怎么让系统越用越贴。

## 41.1 先明确一件事：衡量什么

这个仓库对「衡量」有明确立场：

- **不发明安全分、质量分**（第 12 章）。
- **没有样本的比率是 `null`，不是 0%**。
- **指标必须能追溯到已落地的事件**。

所以评估的思路是：**看真实发生的事，而不是看一个综合分数。**

## 41.2 五个可观察的核心量

| 量         | 含义                         | 在哪看                     |
| ---------- | ---------------------------- | -------------------------- |
| 一次通过率 | 交办后没被驳回/退回的比例    | 北极星快照、成绩单         |
| 改写率     | 律师改了多少（有样本才有值） | 北极星快照                 |
| 交付自主度 | 自动交付 vs 人签的比例       | 交付事件统计               |
| 门禁拦截   | 机械门禁拦了多少次           | 产品指标（`gate_failure`） |
| 真稿对照   | 与律师自己写的稿比           | 真稿门（有夹具才 RUN）     |

**看的地方**：

```text
GET /api/metrics/north-star
GET /api/metrics/north-star-trend?windowDays=30
GET /api/metrics/lawyer-dashboard
GET /api/metrics/team-growth
```

或者设置 → 系统健康 → 交办成绩单。

## 41.3 怎么读这些数

### 一次通过率高说明什么

说明**在你配的口径下**，产出基本符合预期。但要注意两件事：

- 分母是「已交付的任务」，不是「所有交办」。
- **通过不等于法律正确**（第 12 章那句「通过核对 ≠ 法律正确」）。

### 改写率低说明什么

可能是好事（模型写得合你的口味），也可能是坏事（你懒得改直接收了）。**这个指标要结合你自己的判断看。**

而且注意：改写率只在**每个可用周都有样本**时才参与趋势结论（第 12 章的诚实规则）。

### 门禁拦截多说明什么

**不一定是坏事。** 说明门禁在起作用。要看拦的是哪一类：

| 拦什么         | 含义                     |
| -------------- | ------------------------ |
| 空修订         | 说明模型在「假装改完了」 |
| 引用完整性     | 说明引用对不上来源       |
| 必核清单未完成 | 流程没走完               |
| 验收章节缺失   | 产出结构不对             |

**拦截率突然升高**通常意味着某个环节退化了（比如换了模型、改了技能）。

### 「暂无数据」说明什么

说明这个来源从来没产生过数据——**这是需要排查的信号，不是「一切正常」**。

第 12 章反复强调这一点，因为它是最危险的失败模式。

## 41.4 三条自我体检的路径

### 路径一：看交卷核对

打开改稿工作面，看「交卷核对」（机械门禁、独立审稿、引用）。它是**按稿**的，不是统计。

**它的价值**：告诉你这份稿离「可以交」还差什么。

### 路径二：跑一遍门禁

```bash
pnpm lawmind:gate --all --strict          # 交付验收
pnpm lawmind:ops matter-consistency       # 案件一致性
pnpm lawmind:doctor                       # 工作区体检
```

这三个是**确定性的**，不依赖统计样本。

### 路径三：看趋势

```bash
pnpm lawmind:north-star-trend --window 90
```

注意它的诚实规则：

- 样本不足的一周报 `null`。
- 可用周数不足时**不给趋势结论**（需要至少 3 个可用周、每桶至少 5 次交付）。

## 41.5 怎么让系统越用越贴

按「见效速度」排序：

### 第一步（当天见效）：配偏好与口径

| 做什么                            | 效果                         |
| --------------------------------- | ---------------------------- |
| 首跑偏好选准                      | 影响所有草稿的文风与风险表述 |
| 写 `playbooks/CLAUSE_PLAYBOOK.md` | 影响合同类的审查口径         |
| 配`agentMandatoryRules`           | 每轮都注入的硬规则           |

**这一步见效最快**，因为它直接改提示词的内容。

### 第二步（一两周见效）：确认记忆

用一两周之后，记忆库里会攒下建议。确认那些对的、忽略那些错的。

**注意批量采纳只管低风险风格项。** 案件事实类的建议要一条条看。

### 第三步（一个月见效）：校准风险与深度

如果发现系统总是太保守或太激进，改两处：

- 偏好里的「风险取向」。
- playbook 里的具体条款立场。

### 第四步（长期）：用自动办件接管重复劳动

把每周每月都要做的事变成自动化。但记住六项确认要认真填。

## 41.6 一次「效果复盘」怎么做

建议每月抽一个小时：

```text
1. 看北极星趋势（有样本的部分）
   - 一次通过率、改写率的走向
   - 哪一周明显异常

2. 挑三份最近的稿，人工过一遍
   - 结构对不对
   - 引用能不能回溯
   - 有没有该标待核实而没标的

3. 看门禁拦截的分类
   - 哪一类最多
   - 是不是某个技能/模型变了

4. 看记忆库
   - 有多少建议没处理
   - 有没有确认了但其实不对的

5. 定下个月的三个改进点
```

**第 2 步最重要**，而且它不能自动化——**自动化核对代替不了你自己看一遍**，这也是这个产品的一条立场。

## 41.7 一份「效果不好」的排查清单

如果觉得效果不满意，按这个顺序查：

| 症状             | 先查                                                 |
| ---------------- | ---------------------------------------------------- |
| 风格不对         | 偏好配了吗？playbook 写了吗？                        |
| 结构不对         | 交付物类型判对了吗？（看状态条）                     |
| 引用不可靠       | 法源接了吗？演示语料的水印出现了吗？                 |
| 总是要补材料     | 指令里给了材料吗？形态信号够吗？                     |
| 太保守/太激进    | 风险取向；playbook 里的立场                          |
| 结论泛泛         | 是不是没绑到具体案件？（案件上下文能显著提升具体性） |
| 反复问同样的问题 | 记忆库里的建议确认了吗？                             |
| 越用越慢         | 案卷、材料、索引（第 40 章）                         |

## 41.8 三条不要做的事

| 不要做               | 因为                                                             |
| -------------------- | ---------------------------------------------------------------- |
| 为了好看的数字改口径 | 「指标一直很好看」和「指标算错了」长得一样（第 29 章案例 29.11） |
| 用单一分数评价效果   | 系统刻意不给安全分/质量分                                        |
| 拿示例文件凑门禁     | 真稿门和人类基准门要真数据才有意义                               |

## 41.9 关于「团队级」的评估

律所版有团队成长看板（`team-growth-dashboard`），五个指标：

| 指标           | 口径                           |
| -------------- | ------------------------------ |
| 主力一次过率   | 相对基线 ↑ ≥10pt               |
| 改写率         | 相对基线 ↓                     |
| 学习处理率     | ≥40% 的建议被采纳或驳回        |
| 路由命中率     | 默认承办人解析成功比例         |
| 强制互审覆盖率 | 应该互审的稿子里实际互审的比例 |

**可以存基线**（`POST /api/metrics/team-growth/baseline`），之后对比。

注意「学习处理率」的分母是**建议总数**——它衡量的是「有没有在处理建议」，不是「建议对不对」。

## 41.10 已知坑（本章相关）

- **「暂无数据」是要排查的信号**，不是「一切正常」。
- **一次通过率高不等于法律正确。**
- **改写率要看方向。** 低可能是好事也可能是没细看。
- **门禁拦截率升高通常是退化信号。**
- **趋势需要足够的周数和样本**，否则不给结论。
- **自动化核对替代不了人工看稿。** 第 2 步不能省。
- **别为了数字改口径。**
- **别拿示例文件凑门禁。**
- **「学习处理率」衡量的是处理动作，不是处理质量。**

# 第 39 章 兼容、迁移与演进

这一章讲「版本变了之后旧数据怎么办」，以及这个仓库处理兼容的方式。

## 39.1 三条兼容原则

从代码里能总结出三条：

1. **真相源格式向后兼容。** 旧的工作区要能被新版本读。
2. **新增字段「有才加」，不无条件加。** 否则历史数据会验不过（审计链那条注释就是活例子）。
3. **失败要可见，不能静默丢数据。** 宁可报错也不能假装成功。

## 39.2 有版本号的地方

按「**程序拿它做什么**」分三档——这比只看有没有版本号更有用，因为只有第一档会真的拦住你：

| 位置              | 版本常量                       | 现在是                           | 程序拿它做什么                                    |
| ----------------- | ------------------------------ | -------------------------------- | ------------------------------------------------- |
| Word 改稿清单一族 | `WORD_REVISION_PACK_VERSION`   | 2                                | **比较**：`overlayVersion >= 本常量` 才认旧清单   |
| 立场库            | `STANCE_SCHEMA_VERSION`        | 1                                | **比较**：读到不等于它的 `schemaVersion` 就当空库 |
| 索引 schema       | `SEARCH_INDEX_SCHEMA_VERSION`  | 3                                | **只写不校**：写进 index meta，新鲜度判据里没有它 |
| 法条参数表        | `STATUTE_PARAMS_VERSION`       | 3                                | **只展示**：用在 lint 的回执文案里（`参数库 v3`） |
| 学习队列          | `FILE_VERSION`                 | 1                                | **只写不校**：写进 json，读取时不比它             |
| 校准特征口径      | `FEATURE_VERSION`              | 1                                | **只写不校**：写进拟合产物，无消费方比对          |
| 诉讼费分档表      | `LITIGATION_FEE_VERSION`       | 1                                | **纯人工标记**：全仓只有定义，没有任何读取点      |
| 策略文件          | `schemaVersion`                | 1                                | 值靠字面量校验（不是引用常量）                    |
| 工作日设置        | `DESK_SETTINGS_SCHEMA_VERSION` | 1                                | 只出现在类型声明里（`typeof`）                    |
| 路由默认          | `ROUTING_DEFAULTS_VERSION`     | 1                                | 只出现在类型声明里（`typeof`）                    |
| 案件团队名册      | `TEAM_ROSTER_VERSION`          | 1                                | 只出现在类型声明里（`typeof`）                    |
| 合同修订包        | `SCHEMA_VERSION`               | 1                                | 只出现在类型声明里 + 写入                         |
| 导出格式          | 格式标记字符串                 | `LawMind audit export format: 2` | 解析时匹配这个前缀                                |
| 审计回放          | `schemaVersion`                | 1                                | 值靠字面量校验                                    |

**这张表最该记住的一句**：**只有头两行是「抬版本号会改变行为」的**。其余的抬了也白抬——程序不看。比如 `SEARCH_INDEX_SCHEMA_VERSION` 从 3 抬到 4，索引该陈旧还是陈旧：**新鲜度只看 `lastRebuildAt` 与 24 小时窗口**（`computeSearchIndexFreshness` 只吃 `ready` 与 `lastRebuildAt`，压根不碰 schema）。要强制重建得用开关或删索引。

**改数据结构时先在这里找找有没有对应版本号**，有就该考虑要不要抬；但**同时要看清它属于哪一档**——第二、三档的常量抬了不产生任何强制力，真正的兼容还得靠「新增字段有才加」（39.1）那条纪律。

**注意「工作流」这一类没有版本号。** 工作流模板（`agent/collaboration/builtin-workflow-templates.ts`、`workspace-workflow-templates.ts`）的类型定义里没有 `version` 字段——所以改模板结构时没有版本常量可抬，只能靠「新增字段有才加」来保兼容。这是本表里**唯一一处「应该有但没有」**的地方。

## 39.3 已经做过的迁移

### MEMORY.md 的过期口径

**背景**：新装的工作区里带着 2025 年的模板口径（比如「调用外部模型前告知预估消耗」「禁止将案件材料发送至外部服务」）。这些现在不对了。

**难点**：不能整份重写——律师自己写的积累会丢。

**做法**（`memory/memory-md-migrate.ts`）：靠一份 6 条特征串（`STALE_MARKERS`）识别哪些是**库存内容**，只替换那些行。

```text
STALE_MARKERS 示例：
  发送邮件、修改文件、外发文书
  调用外部模型前告知预估消耗
  禁止将案件材料、客户信息发送至外部服务
  两种模型都返回结果时
  通用模型：用于背景整理
  专用法律模型：用于法条提取
```

**可学的点**：迁移的判据是「识别要改的那部分」，不是「整份替换」。

### 邮件密钥 v1 → v2

**背景**：早先的邮箱密钥是明文存的。

**做法**：读的时候自动迁移成加密存储（临时文件 + rename 原子替换）。

**诚实的边界**（注释原文）：

> 明文不再滞留该路径；闪存块级擦除不可移植，见 SECURITY 报告残余说明。

也就是说：逻辑上明文没了，物理上 SSD 上可能有残留。**这种事写出来比藏着好。**

### 律师档案 §八 轮转

**背景**：`LAWYER_PROFILE.md` 的「八、个人积累」会无限增长。

**做法**：超过 120 条时把最早的挪到 `memory/lawyer-profile-archive.md`。**不删除**，按时间追加。

**关键点**：轮转**不改变注入行为**（模型只看 800 字指纹），只保证档案本身体积有界。

### CASE.md 工作进展轮转

超过 80 条时把最早的挪到 `cases/<id>/progress-archive.md`，原位留一行：

```text
- _（更早 N 条已轮转省略；完整历史见 progress-archive.md）_
```

### 审计字段的「有才加」

**背景**：审计链的 `canonicalPayload` 后来需要包含 `matterId` / `actorName`。

**难点**：老事件没有这两个字段。如果无条件加进 payload，**既有的每一条审计链都会验签失败**。

**做法**：条件包含——只有协作类事件（带 `matterId`）才把它们纳入哈希。

注释原话：

> 无条件加进 payload，既有的每一条审计链都会验签失败 —— 对合规特性是灾难性回归。

**可学的点**：改动**校验和**的输入结构是最危险的一类改动。

### 会话工具的清理

`session-delete-cascade.ts` 处理「删会话时把侧车文件一起清理」。侧车包括中途指示、中途钉选、实时进度等——它们不在会话 JSON 里，容易漏。

### 投影修复

`repairMatterProjections` 处理 JSON 与 CASE.md 的漂移（第 7 章）。

## 39.4 索引 schema 变化

索引版本现在是 3（加材料表时升过一次）。

**升级后要注意**：

1. 旧索引可能不兼容 → 需要重建。
2. 应用启动时如果索引不存在会后台重建。
3. 显式重建需要 `LAWMIND_ALLOW_INDEX_REBUILD=1`。

**好消息**：索引是派生数据，重建不丢信息（真相源是 Markdown / JSON）。

## 39.5 废弃字段与遗留物

代码里能看到的「历史残留」有几类，遇到时不要以为是 bug：

| 名称                              | 现状                                                            |
| --------------------------------- | --------------------------------------------------------------- |
| `shouldCheckpointToolBudget`      | 恒返回 `false`；`skipToolBudgetCheckpoint` 只为恢复旧会话保留   |
| `continue_tools`                  | 旧的「继续」卡；只在恢复旧会话时出现                            |
| `legacy_update_draft_body`        | 旧的改稿路径警告                                                |
| `highSecurityMode`                | 策略里的旧键，等价 `egressMode: "offline"`                      |
| `needs_matter`（Word 插件）       | 旧状态；现在改成 ad-hoc 直跑                                    |
| `mailContractFastPathAllowNames`  | 废弃函数（返回 `undefined`），因为「Playbook 不再冻结允许清单」 |
| `LEGACY_SHARED_CLIENT = "shared"` | 历史共享令牌，仅开发/E2E                                        |
| `executeCampaignSerial`           | 标了 `@deprecated`                                              |
| `scoreCase`                       | 标了 `@deprecated`                                              |
| `useMatterSessionTimeline`        | 标了 `@deprecated`                                              |
| `history.log` 之类                | —                                                               |

**判断方法**：看到 `@deprecated` 注释或名字里带 `legacy`/`_OLD`/`老` 的，先确认是不是兼容用的。

## 39.6 两处「结构性兼容问题」

这两个不是字段级的，是结构级的，值得单独提。

### 两份清单手工同步

`runtime/protected-workspace-rels.ts`（TS）和 `electron/fs-bridge.mjs`（JS）是两份手抄常量。

原因：Electron 主进程是 `.mjs`，不能 import TS。

**风险**：改一处漏另一处会出现安全口子。**有守卫测试**：`electron/fs-bridge.test.ts` 逐项比对（见第 29.22 与 34.10）。

### 两套 schema 的细微差异

`adapters/matter-storage/schema.ts` 和 `schemas.ts` 是两套 zod 定义，有差异：

| 字段                         | 差异                                                              |
| ---------------------------- | ----------------------------------------------------------------- |
| `currentReviewStatus`        | `schema.ts` 允许 `redacted`，`schemas.ts` 不允许                  |
| `queueItemSchema` 的额外字段 | `schemas.ts` 多了 `dependsOn`/`blockedBy`/`blockedReason`/`phase` |
| `approvalSchema.requestedAt` | `schemas.ts` 有 `min(1)`                                          |

按注释说 `schema.ts` 是「W3 真相源」，1:1 对应 `core/contracts.ts`。所以 `schemas.ts` 更像是另一条线的产物。

**实践建议**：改数据模型时两处都要看。

### 内置技能与种子清单的漂移

37 份正文 vs 35 个 id（缺 `client-talk-intake`、`legal-event-extract`）。

**没有测试拦**。而「注册」是「已消化」五项要求之一。

## 39.7 怎么加一个新版本号

如果你改了某个带版本的数据结构，按这个清单走：

```text
1. 抬版本常量（比如 SEARCH_INDEX_SCHEMA_VERSION 从 3 到 4）
2. 想清旧数据怎么办：
   a. 能直接读（向后兼容）→ 什么都不用做
   b. 需要迁移 → 写迁移函数
   c. 无法迁移（派生数据）→ 重建
3. 迁移函数的三条要求：
   - 只改该改的部分（像 MEMORY.md 迁移那样）
   - 原子写（临时文件 + rename）
   - 失败要报错，不能静默跳过
4. 加测试：旧格式能读 / 迁移结果正确 / 幂等（跑两次不出问题）
5. 在 CHANGELOG 或迁移说明里记一行
```

**幂等很重要**：迁移可能被跑两次（比如第一次中途崩了）。第二次应该不出问题。

## 39.8 关于「不许破坏历史链」

这类约束在系统里出现不止一次：

| 场景     | 约束                                    |
| -------- | --------------------------------------- |
| 审计链   | 无条件加字段会让历史链全部验签失败      |
| 会话历史 | 工具调用配对不能破（坏了模型 API 会拒） |
| 迁移     | 不能整份重写（会丢律师手写内容）        |
| 删除     | 删会话要级联清侧车                      |
| 审计文件 | 不要删中间某天（链会断）                |

**共同点**：这些数据都是**追加型、有序、有校验**的。改动它们的规则是「只能追加或就地修改，不能重排或删除中间」。

## 39.9 期次与路线怎么看

仓库里有两份「宏观进度」文档：

| 文档           | 内容                               |
| -------------- | ---------------------------------- |
| `GOALS.md`     | 当前期次、未完成项、每期的落地清单 |
| `CHANGELOG.md` | 历史期次归档                       |

**读法**：

- `GOALS.md` 的「当前期次」是活的（有勾选状态）。
- 带 `[x]` 的是已落地切片；带 `[ ]` 的是未完成。
- 有些 `[ ]` 是**外部依赖**（比如等律师放真稿、等证书），不是工程没做——文档里会明确写「故不勾」。

**一个有用的观察**：`GOALS.md` 里那些「工程侧已落地但等外部输入」的项（真稿门、公证），说明这个仓库对「完成」的定义是**端到端可用**，不是「代码写完」。

## 39.10 已知坑（本章相关）

- **改动校验和的输入结构最危险。** 审计那条注释是活例子。
- **迁移要幂等。** 可能被跑两次。
- **迁移只改该改的，不整份替换。**
- **「明文不再滞留该路径」不等于物理擦除。** SSD 上可能有残留，这类边界要写出来。
- **两份清单手工同步，无测试。**
- **两套 schema 有差异。** 改数据模型两处都看。
- **索引版本变了要重建**（但它是派生数据，不丢信息）。
- **看到 `legacy` / `@deprecated` 先确认是不是兼容用的**，别当死代码删。
- **`GOALS.md` 里的 `[ ]` 有些是外部依赖**，不是没做。

# LawMind 产品方案

> 本地优先的律师工作台，也是能独立完成法律任务的 Agent。

## 1. 产品概述

LawMind 是一款装在律师电脑上的法律 Agent。律师用自然语言交办，它读取案卷、检索法源、分析材料、起草文书，最后交付一份可以直接使用的 Word、Excel、PPT 或 PDF 文件。

它面向中国大陆执业律师，可以同时处理合同、诉讼、顾问单位邮件、案卷整理和期限管理。LawMind 要让一个律师在一台电脑上，把过去需要几个人配合完成的活做到能交付。

案卷留在这台电脑上。模型若也部署在本机，完成任务所用的上下文不会离开这台电脑，数据绝对保密。

### 1.1 工程体量

LawMind目前的 TypeScript、JavaScript和CSS一共 **70余万 行**（3,186 个文件）。

其中能编译运行的代码约 65 万行，含测试。去掉测试之后，生产代码是 365,443 行：

|                            |    行数 | 组成                                   |
| -------------------------- | ------: | -------------------------------------- |
| 本地工程（`src` + `apps`） | 712,812 | 源码、测试、样式                       |
| 法律引擎（不含测试）       | 225,100 | 1,021 个文件，67 个一级模块            |
| 桌面应用（不含测试）       | 140,273 | Electron 窗口、本机服务、律师界面      |
| 生产代码合计               | 365,443 | 引擎 + 桌面，1,637 个源码文件          |
| 测试                       | 193,440 | 1,202 个测试文件，另有 34 条端到端脚本 |

引擎 的22.5 万行里，主要是这些部分：

- **Agent 运行时。** 办件识别、多轮工具调用、上下文压缩、隔离子工。律师说完一句，系统自己拆步骤、调工具、写文件，中途不按步数停下来问要不要继续。
- **法律能力面。** 79 个工具，23 类办件，27 类交付物规格，40 个内置 Skill。合同审查、诉讼文书、检索、收案、期限、邮件，都有对应的入口、材料和验收，不是同一段提示词换个标题。
- **证据账本。** 引用、金额、条款、Word 修订分开记账。下一节的纠错层就建在这本账上：模型可以提议，没有独立来源就不能写成确定句。
- **文书工艺。** 以原稿为基线的 Word 修订、最短改动、审查表、一次改多份文书。导出之后还会读生成的 `.docx`，不会整句删掉再整句插入。
- **办案对象。** 收案状态、利益冲突、期限、邮件、自动办件、记忆采纳。这些对象有自己的状态和写入规则，不靠对话历史记住“这案子接了没有”。

桌面的 14.0 万行是另一套应用：对话、案卷、Word 审阅面、在办列表、设置等。律师打开的是安装好的 LawMind，不是浏览器里的页面。渲染进程不能直接上外网，读写工作区文件走本机文件桥。

1,202 个测试文件和 34 条端到端脚本已经算进这 70 余万行里，没有再单列成生产代码。它们覆盖合同审查、收案、修订导出、审批、邮件和长任务恢复，用来守住上面那套系统。

代码没有搭在开源 Agent 框架上。运行时依赖里没有 LangChain、AutoGPT、OpenHands、OpenClaw、LlamaIndex、CrewAI、AutoGen。第三方库负责 Word、Excel、PPT、PDF、OCR 和邮件。Agent 循环、工具治理、上下文压缩、子工、证据账本、修订管线、收案状态机等都是本工程原创代码。

相比于只包一层模型接口和若干提示词的法律演示，常见体量是几千行到一两万行。LawMind 的本地工程是 70 余万行，其中引擎单独是 22.5 万行。多出来的这些代码，用来把收案、审查、改稿、核对和批准接成一条能重复跑的链。

### 1.2 量子信息启发的证据纠错（本工程的绝对原创创新）

长文写作有一个容易被忽略的问题：错误会顺着上下文往后传。模型前面把金额写错，后面就会拿这个错数继续算；前面把演示材料当成现行法，后面就会拿它当依据。让模型自己再检查一遍，效果有限，因为写和查用的是同一个上下文。

LawMind 在引擎侧另记一本账。模型对关键事实的写法先记成“读法”，每个读法有质量权重。只有原文句子或工具结果，才能把一个读法标成已核实。账上有四类持续检查，分别盯引用、金额、Word 修订和合同条款。哪一类出了问题，引擎先看几盏红灯是不是同一处笔误造成的，能解释就修那一处；解释不了就写成“待核实”，不硬猜。

这套做法借的是量子纠错和量子信息里的几条纪律。

| 量子启发         | 在 LawMind 里的用法                                                | 解决什么                                 |
| ---------------- | ------------------------------------------------------------------ | ---------------------------------------- |
| 多个读法并存     | 一个事实先保留几种写法和权重                                       | 不在第一句就定死                         |
| 纯度与测量       | 胜出的读法既要足够集中，又要有独立来源，才写成确定句               | 不确定就写“待核实”                       |
| 稳定子           | 引用、金额、修订、条款四类一直核对                                 | 机械错误定点拦住                         |
| 综合征译码       | 用一组最小的故障解释全部红灯                                       | 同一处笔误导致的多盏红灯一起修           |
| 来源只计一次     | 同一段原文、同一次检索只算一份证据                                 | 子工复制同一段原文，不会变成两条独立证据 |
| 弱测量与保形校准 | 一句措辞只是弱读数；多轮、多条独立通道才升级；预测集只有一个才确定 | 一句话不翻红，过度自信被压住             |

这层已经接在每一轮的证据记账上，并有消融、律师任务套件、法律行业基准和抽查测试。模型可以更换，这本账留在引擎里。接一个“检查引用”的工具只要几天；把读法、来源、稳定子、译码、弱测量和保形校准连成回合内的闭环，是这 22.5 万行里不容易拆走的一块。

### 1.3 和通用 Agent、法律 AI 的区别

通用 Agent（Claude Code、Codex、Cursor 这一类）能读写文件、跑命令、拆子任务，环境操作能力很强。把它直接交给律师，会缺四样东西：法律工作从收案到归档怎么走、一份起诉状或审查意见必须有哪些章节、引用和金额由谁核对、Word 修订能不能逐处接受。律师仍然要自己写提示词、自己拼工具、自己验结果。

法律 AI 产品（Harvey、Legora、Spellbook 以及国内的法律问答和合同审查产品）懂法律、有模板、有工作流，但多数以云端、文本、固定流程为主。律师要把文件上传到平台，交付多停在意见或 PDF，改稿还要回 Word 重做。本机文件夹、邮箱和 Word 原稿通常不在同一个环境里。

LawMind 把主要注意力放在最后一段：在律师自己的电脑上，把一件法律活从交办做到可交付文件。它有自己的 Agent 运行时，有收案、审查、期限、邮件这些办案对象，有证据账本，也有 Word 原生修订。通用 Agent 更通用，法律 AI 的法律数据和品牌更强；LawMind 的本地工程有 70 余万行，把这几层接在同一台电脑上。

| 维度      | 通用 Agent             | 法律 AI 产品       | LawMind                                  |
| --------- | ---------------------- | ------------------ | ---------------------------------------- |
| 任务入口  | 律师写提示词、拆步骤   | 选模板、走预设流程 | 自然语言交办，系统识别办件               |
| 长任务    | 有循环，没有法律任务图 | 固定流程或单点     | 父助手、隔离子工、80 步预算、可恢复      |
| 法律工作  | 无                     | 部分覆盖           | 收案、案件、期限、审查表、证据目录、邮件 |
| 证据核定  | 模型自检               | 可能附引用         | 四类账本，回读写进文件的结果             |
| Word 修订 | 自己处理 OOXML         | 多为文本或 PDF     | 原稿上修订，最短改动                     |
| 运行环境  | 本机                   | 云端为主           | 本机桌面；发出去要批准                   |

### 1.4 一次交办是什么样

以合同审查为例。律师把合同钉选到对话里，说：“按买方立场审这份采购合同，重点看责任上限、验收、付款和知识产权；出审查意见，同时出修订稿。”

系统识别为合同审查，读原稿和对方的修订版，按本所剧本逐条分级，生成审查表，对原文做最短改动，最后出一份带 Word 修订轨的审阅稿。律师在中栏的 Word 审阅面里逐处接受或拒绝，签批后导出。律师只交办一次，中间不需要选流程，也不需要逐步确认。

诉讼材料、顾问单位邮件、案卷整理走同一条路径：律师说清楚要做什么，Agent 自己拆步骤、调工具、找依据、写文件。下面按需求和功能把这条路径拆开。

## 2. 需求

### 2.1 用户与场景

LawMind 的主要用户是独立执业律师。他们的工作有几个共同点：材料多、时间碎、交付标准高，而且很多活没法拆给别人。

**合同审查。** 客户发来几十页合同和对方的修订版。律师要读懂两份文件，按己方立场找风险，分出必须改、建议改、可选，还要把修改落到 Word 修订轨里。审查意见和修订稿一起交，修订稿能被同事或对方逐处接受。

**诉讼材料。** 律师手里有聊天记录、转账截图、合同、律师函、传票，需要先做时间轴和证据目录，再写起诉状或答辩状。材料里的日期、金额、当事人称谓不能串，事实要能回到原句。

**顾问单位邮件。** 合同经常作为邮件附件进来。律师希望系统能识别、能审、能出修订稿，但发信必须自己点头。

**旧卷宗整理。** 转所或新执业时，本机文件夹里堆着几年的案卷。律师希望按案件归位，同时把自己过去接受过的改法沉淀下来，而不是每次从零交代立场和表述。

这些场景对产品的要求是：能接住自然语言交办，能连续做到文件出来，关键事实能核对，案卷留在本机。

### 2.3 边界

没有法律任务的闲聊不是主路径。产品是本机桌面应用，不是云端工作台。系统可以起草、核对、提示，正式意见和对外发送由律师决定。引擎拦住的是金额、引用、修订这一类机械错误；法律判断仍由律师负责。没有来源时，系统会写明没有，不编一个看起来像法条的句子。

## 3. 功能

### 3.1 合同审查与改稿

合同审查是 LawMind 做得最深的一条线，按四步走：分级、审查表、改稿、出 Word。

律师把合同钉上，说：“按买方立场审这份采购合同，重点看责任上限、验收、付款和知识产权；出审查意见，同时出修订稿。”系统按合同审查处理，中间不再问要不要继续。

**按本所剧本做三色分级。** 律师把自己的审查标准写成 playbook，系统逐条判断，输出 GREEN、YELLOW、RED。模型给出每条条件的结论、原文引用、位置和材料路径，引擎再把引文拿回原文件核对。引用对不上、位置对不上、材料路径对不上，都会降成“未核对”。没给结论的条件也按未核对，不按通过算。RED 只能由律师在界面里降档，模型没有自行放行的入口。工作区里没有剧本时，结果会标明这是通用标准，不冒充本所立场。

**审查表。** 可以套尽调、证据、条款矩阵，也可以自己加列加行、分组、从本案材料导入。`extract_batch` 按材料批量抽取，每一格带出处；抽不动就写“无法判断（证据不足）”，不猜。同一格出现多个候选值时，把候选交回来，要求明确选择，不允许模型挑一个了事。律师标记为锁定的行，批量重抽时不会被覆盖。已经核过出处的结论可以直接推进文书正文；没有出处的行不进入正文，单独列成“未能取得的项（诚实标注，未作推断）”。

**改稿。** 修改以查找和替换的形式进来，引擎按原文和改后文本重新计算最短改动。一处修改里没动的字，留在修订轨之外。锚点太宽，或者同一处在正文里出现多次却没有声明全部替换，系统会跳过这一处；跨多份文书时，任一份不通过就整批停止、一行都不写。命中 0 处的文书会记进变更清单，避免律师以为那一份也改过了。

**出 Word。** 审阅稿以原合同为基线，写入真正的 `w:ins` / `w:del`，保留原格式和原有修订，只叠加新修订。修订作者可以配置，时间按原稿和导出时刻排布，避免同一批修订出现倒序。律师在中栏按作者着色查看，逐处接受或拒绝；接受后标记留着以便导出，拒绝则从稿里拿掉。导出之后，引擎再读实际生成的 `.docx`，检查插入和删除的数量、有没有“整句删、整句增”，以及修订文字的字体、字号、加粗是否和旁边的原稿一致。有一项不通过，这次导出就不算完成。

合同审查还可以启动一个五角色专案组：条款结构、风险与责任、合规、义务时间线、引用核验。各角色串行执行，汇总安全分和发现项。单个角色失败不会推翻整组，但会如实标出来。

### 3.2 文书起草与交付

系统内置 27 类交付物规格，覆盖律师函、回函、起诉状、答辩状、代理词、法律意见书、内部备忘、案件时间线、证据目录、会议纪要、保密协议、检索研究备忘、劳动补偿计算、程序期限计算、核算对照、审查表、租赁合同、商务合同、合同审查意见、诉讼策略提纲、ESG 报告、研究报告、合规备忘录、学习型简报、培训课件等。

每一类规格都定义了必须有哪些章节、缺了是阻断还是提醒、哪些占位符必须在渲染前清空、默认要追问什么、用哪个模板、风险等级多高。高风险交付物还可以开推理门禁，要求争点、权威和事实结构完整，权威之间的冲突要先处理掉。

起草的路径是：解析指令，需要时做结构化检索并留下研究快照，按规格生成章节，多轮修订，最后验收并渲染。验收检查必要章节、占位符、引用完整性和推理结构。研究型文书必须有可核对的研究快照，不能拿演示语料写成现行法。渲染输出 Word 或 PPT；Excel 走表格工具；PDF 通过本机 LibreOffice 转换，没安装时提示用 Word 或 WPS 另存。

模板可以上传、注册、启用和停用。中文法律文书有自己的版式：标题层级、首行缩进、脚注、页码和表格。备忘录、研究报告和诉讼文书不用同一套版面。

### 3.3 诉讼材料

诉讼材料往往是一堆杂文件，不是一份整齐的合同。LawMind 先把材料读成卡片：每份一段摘要，加上关键字段、建议记入时间轴的事件、建议放进审查表的行。文件多的时候用摘要，不把每份都拆成一个子工；只有某一份要连读、连查、再写，才单独派子工。

然后从传票、短信、合同、聊天记录里抽取法律事件，写入案件时间轴。时间轴是两阶段的：先给出候选，律师或系统确认后再落盘，避免把无关日期塞进案子。同一天的重复事件会合并。

在时间轴和材料卡片之上，可以生成证据目录，也可以按诉讼文书规格起草起诉状、答辩状或代理词。起草时检查请求权基础、程序节点和证据缺口。缺事实的地方标“待核实”，不编造。这个标记留在稿子里，律师能看到哪里还要补材料。

### 3.4 收案与案卷

律所的工作从“接不接”开始。LawMind 把这一段做成显式状态：待处理、冲突待扫、等律师决定、接受或婉拒。

必须齐备：候选当事人、利益冲突扫描、风险告知、AI 使用告知、本案负责人、律师的接受或婉拒。模型可以填候选人和来源，不能自己把状态推成“已接受”。只有接受之后才允许外发。婉拒不改写成别的案子，案件仍停在收案，等律师删除或另建。

冲突扫描是确定性的名称匹配，不是模型“感觉有没有冲突”。它覆盖全部案件，包括已结案件和前客户，以及工作区记忆。每一条命中写明来自哪一卷、哪一个字段。空扫描不能当成“没有冲突”。有命中时，接受委托必须写书面理由。命中不会自动拒绝，只把记录推到律师面前。

收案通过后可以生成委托包：委托代理合同、授权委托书、风险告知书、AI 使用告知与同意、报价单，五份 Markdown，并可导出 Word。每份顶部标明“草案 · 须律师核对”。Markdown 是正文来源，Word 从当前 Markdown 重新渲染。文件已经存在时要确认才覆盖，避免把律师改过的稿冲掉。

案卷本身包括当事人、案由、阶段、案号、法院、审级、诉讼地位、开庭时间和标的金额。标的按文书原文记录，不自行换算、不自行加总。期限和义务从传票、短信、通知里抽取，写入工作队列和提醒；开庭会排在上诉期之前，避免同一段文字里的两个日期写反。谈话记录可以整理成需求、案由和证据缺口，确认后再写入档案。每一次这类写入都有编号，写错可以按编号撤销。

跨案工作台把今天该做的、已经过期的期限、没回的邮件、还没归案的材料放在一起。

### 3.5 检索与研究

检索结果分三档：

| 层级     | 含义                             | 系统怎么用                   |
| -------- | -------------------------------- | ---------------------------- |
| 样例     | 工作区里的启发式匹配，或演示语料 | 标明；不得写成“现行有效”     |
| 本地语料 | 本机的开放法规语料               | 可以引用，并注明是哪一层来源 |
| 实时     | 已配置的商业库或官方法源         | 可以标成实时检索             |

没有配置实时法源时，检索会说明“未接权威库”，并给出启用路径。没有类案索引时，说明“未接类案库”，不编案号或裁判要旨。工商查询没接端点时，不把没查过的登记写成已核实。研究型文书如果只拿到演示语料，直接拒绝起草。

可用的来源包括：本地开放语料、国家法律法规数据库、北大法宝（自备密钥）、元典开放平台、通用 HTTP 端点、本地类案索引、CourtListener，以及公开网页和律师给出的 URL。深度研究会做多轮检索，留下研究快照；研究备忘、检索报告、合规备忘录都可以作为交付物。引用会分成已锚定和待核实。长文研究可以先确认大纲再展开。

### 3.6 邮件与自动办件

邮件支持 IMAP、SMTP 和 Microsoft Graph。系统可以读本案信箱、列出附件、把附件落到工作区，并识别哪些附件是可审的合同。`.docx` 可以直接出修订稿；旧版 `.doc` 能读正文，要出修订轨需要先另存为 `.docx`；PDF 和图片走分析和审查意见，不假装能在扫描件上打 Word 修订。

准备外发只写入待发信，不发送。真正发送必须律师批准。批准绑住收件人、主题、正文和附件，其中任何一项变了都要重新批。发信前还会看这案子有没有接受委托、是否撞上伦理墙、收件人范围和附件格式。

自动办件可以按天、按周、跑一次，或每 N 分钟跑一次（5 分钟到 7 天）。也可以由事件触发：本案文件变化、新来信的发件人或标题、本机 webhook 里的一段文字。条件必须是具体的一段文字，至少两个字，不接受“全部”“每条”“任何”，避免一条规则把邮箱里所有信都拉去跑模型。同一条件最少隔 15 分钟。预设包括邮件合同审查、收件箱摘要、续签监控和客户周报。每次运行有历史和失败原因。自动办件不会绕过外发审批。

### 3.7 多 Agent 协作

律师默认只跟一个父助手说话，不在多个“人格”之间来回切。复杂的活由父助手派隔离子工。

子工看不到父对话，所以任务必须写全。它有自己的上下文，默认最多 8 轮工具调用，只把有边界的摘要交回父会话，避免一份长材料把主对话撑满。角色有三种：审，交结论和依据；写，交条款片段；探查，只读目录。几件互不依赖的长任务可以在同一次回复里并行，每支的名字必须不同。做完可以按编号续跑，不用另开一支把前面的工作丢了。

子工还会回报自己看见了哪些事实、哪些在视野边上、哪些没连上。没看见不等于材料里没有。

团队版可以按角色委派、咨询、请人复核、发通知。委派有深度限制，避免助手互相调用停不下来。子任务停在澄清或批准时，状态是等律师，不算失败。在办看板把正在跑的、等批准的、等澄清的、等复核的、排队的和失败的放在一起，失败带原因。律师不需要猜它停在哪。

### 3.8 记忆与个性化

记忆按八个范围存放：律所、律师、客户、案件、剧本、对方、项目、助手。写入走采纳：先给建议，律师看到写到哪里、改了什么，再决定采纳、驳回或批量采纳。引擎自动写入的条目也能撤回。批量采纳默认先预览，没确认就一行都不写；其中一条失败，不把整批作废。

系统还会从本机已经接受的修订里学习。按条款类型归类，同一种改法如果前后说法冲突，留最新的一次。出现次数达到 5 次，才进入待确认。提取时只读修订轨，不把合同正文发给模型。可以跨案件看律师在同一类条款上的立场。一次改动不会被当成“已经学会”。

文风、常用表述和常用模板按任务取用，不把整份画像塞进每一次提示。风格只影响怎么写，不代替法律判断。律师纠正过的地方会留下记录，供以后校准。

### 3.9 本机与安全

请求的 Host 必须是回环地址，用来挡住把本机服务骗到外网去的做法。每个客户端的凭据单独派生，可以吊销，也可以换代。界面不能直接访问外网。工作区里的策略文件和密钥文件不能被工具覆盖。工作区以外的文件，要当次授权才能读正文。

权限分四档，由执行层拦住，不是写在提示词里的建议：

| 模式 | 能做什么                 |
| ---- | ------------------------ |
| 标准 | 已配置的工具             |
| 严格 | 写入和外发更紧           |
| 只读 | 检索、分析、查看，不改稿 |
| 研究 | 只读，再加上结构化研究   |

真正离开这台电脑的动作是发信，必须律师批准。没接受委托的案件不能外发。团队版和私有化版默认开着伦理墙，冲突没处理完就扣住外发。改原稿走修订轨，不直接覆盖原文件。外部接进来的工具，写入类默认不暴露，除非明确允许；允许了也仍要批准。渲染、改稿、跑分析、跑本机命令这类动作，可以放进独立进程。

产品使用情况默认只记在本机。离线模式下连本地记录也关掉。审计记录用来排查和看文件有没有被改过，不拿来证明“这份法律意见是对的”。

### 3.10 交付与导出

交付可以是 Word、带修订轨的 Word、PDF、Excel 或 PPT。Word 审阅面按作者着色，逐处接受或拒绝。Excel 能读多表、写表。PPT 能生成、逐页预览，也能把改过的文字写回去。PDF 依赖本机 LibreOffice；没安装时说明原因，请律师用 Word 或 WPS 另存。

导出前的检查包括：必要章节是否齐全，占位符是否清空，验收项是否通过，引用是否锚定，研究类文书有没有快照，是否已经签批。有一项挡住，就不能当成已经可以发出。

## 4. AI 工具使用说明

### 4.1 模型怎么接

系统内置 5 家供应商，接口都是 OpenAI 兼容协议：

| 供应商                  | 默认地址                                    | 什么时候用   |
| ----------------------- | ------------------------------------------- | ------------ |
| 阿里云 DashScope / 通义 | `dashscope.aliyuncs.com/compatible-mode/v1` | 国内直连     |
| OpenAI                  | `api.openai.com/v1`                         | 通用         |
| DeepSeek                | `api.deepseek.com/v1`                       | 默认，成本低 |
| Moonshot / Kimi         | `api.moonshot.cn/v1`                        | 上下文长     |
| 智谱 AI                 | `open.bigmodel.cn/api/paas/v4`              | 国内直连     |

也可以填自己的地址，接本地模型、单位网关或聚合服务。主对话、子工、检索、决策可以各用一个模型。例如主对话用能力更强的，子工用成本更低的，检索用上下文更长的。

安装后第一次打开，会进连接向导：选供应商，填密钥，密钥留在本机（优先系统钥匙串），需要的话再填地址和模型名，验证能连通，然后选工作区目录。之后在设置里可以换。模型列表里能看到上下文长度、标签，以及上次验证花了多久。

选云端模型时，完成这一轮任务所需的上下文会发给该供应商。要把上下文也留在本机，就接本地模型。

### 4.2 工具怎么用

系统注册了 79 个工具，但默认只向模型展示 12 个核心工具，其余通过 `list_more_tools` 按这次任务再取。钉了表格、开了某个 Skill、接了 MCP，这一轮才会多露出对应的工具。角色和权限也会裁掉用不上的。工具表一次塞满，模型更容易调错；流程写死，模型又只能在几个按钮里选。LawMind 用一小张稳定的核心表，再加上按任务披露。

每个工具带着治理信息：风险等级、要不要绑定案件、是只读还是要律师批准才写、能不能重试、要不要放进隔离进程。

五类工具：

| 类别 | 代表                                                             | 用来做什么       |
| ---- | ---------------------------------------------------------------- | ---------------- |
| 检索 | 查法条、查类案、深度检索、查本所旧稿、读文件夹、做材料摘要       | 找依据、读材料   |
| 案卷 | 看案件、读案卷、改当事人和案号、抽期限、改审查表、整理材料       | 把事实写进案子   |
| 起草 | 规划任务、写文书、改草稿、最短改稿、导出正文、导出修订稿、派子工 | 把文件做出来     |
| 分析 | 读文档、读表格、对比两份文件、计算、跑分析、出图、按剧本分级     | 算清楚、分出风险 |
| 系统 | 准备待发信、发信、请律师批、记期限、列模板、读技能、更新计划     | 批准和收尾       |

一次合同审查，工具大致这样走：

```text
read_folder_documents / digest_materials   读原稿和对方修订版
  → search_statute / search_case_law        核法条和类案
  → triage_against_playbook                 按剧本三色分级
  → review_table_update                     生成和填写审查表
  → apply_surgical_edits                    对原文做最短改动
  → render_tracked_draft                    出带修订的 Word
```

诉讼材料是另一条：

```text
digest_materials → extract_legal_events → apply_legal_events
  → draft_document → render_document
```

标准模式能用已配置的工具。严格模式收紧写入和外发。只读模式只能看和查。研究模式在只读之外加上结构化检索。危险动作要批准，或者放进隔离进程。

### 4.3 交办怎么写

说清五件事：做什么，材料在哪，站在哪一方，要什么文件，不要动什么。

> 按我方承租人立场审这份租赁合同，重点看押金返还、维修责任、提前解约和争议解决。出审查意见，分必须改、建议改、可选；同时出修订稿，不要改租金金额和租期。

这句话里有任务、材料、立场、交付形态和禁忌，系统可以直接开工。

“帮我看看这个合同”也能开始，但会多几轮追问，首稿更依赖猜测。材料可以钉选、拖进输入区，或指向本机的一个文件夹。几十份文件适合先做摘要；原稿和对方修订版要说明哪份是哪份。敏感材料可以先用只读模式看，再决定要不要写入。

### 4.4 过程怎么看

对话里能看到几层信息。

- **意图。** 状态条写着“本轮按合同审查处理”。理解错了可以改。
- **轨迹。** 调了什么工具，读了多少材料，停在哪里。
- **引用。** 哪些结论有来源，哪些是待核实。
- **上下文。** 长任务离预算还有多远。
- **稿子。** 从草稿、已修改、待审、已批准到已导出。
- **待决定。** 只有真要律师拍板时才打断，例如发信、改原稿。

不要等它每一步来问要不要继续。工具调用默认有 80 步预算，五十步的审查可以一口气做完。到了上限，已经做好的稿和已经核对的事实都还在，缺的部分标“待核实”。长任务可以转到后台，有进度和失败原因，也可以中止。本机服务中断之后，任务有恢复路径。

### 4.5 交付怎么审

先看审查意见里的“必须改”，再看“待核实”。待核实的每一条，决定是补材料还是删掉这句结论。然后打开中栏的 Word 审阅面，逐处接受或拒绝，检查标题、编号、字体、页眉页脚和签署页。签批后导出。要寄出就进入待发信，核对收件人和附件再批准。

文书类交付还有验收：必要章节是否齐全，占位符是否清空，引用是否锚定，推理结构是否完整。有一项挡住，就不能导出。

### 4.6 自动办件和记忆怎么用

自动办件在设置里配：

1. 选预设（邮件合同审查、收件箱摘要、续签监控、客户周报）或自己写。
2. 定频率：每天、每周、一次，或每 N 分钟。
3. 需要的话写触发条件：本案文件、某类来信、本机 webhook。条件要具体。
4. 看清它会做什么、不会做什么。
5. 在结果收件箱里看每次运行。
6. 信仍然一封一封批。

记忆库里先看待采纳的建议，看它要写到哪里、前后差在哪，再采纳、驳回或批量采纳。自动写进去的可以撤回。同一种改法要出现 5 次，才会变成待确认的习惯。

### 4.7 限制

模型会犯错。法律判断和事实理解都可能错，引擎拦住的是金额、引用、条款和修订这些对得上原文或工具结果的项，判断仍要律师看。商业法源要自备密钥，类案要本机索引，没接上就不要当成已经查过。扫描件和手写识别有限，低质量扫描要人工核对。材料多、检索多的任务不是几秒能完，可以放在后台。团队协作是加在单人路径上的，默认仍然是一个律师、一个助手。和律师原稿的盲评还没有足够的同题双稿，没有样本就不报通过。

## 5. 技术与评测

### 5.1 运行结构

LawMind 分四层。上面说的 70 余万行里，能编译运行、且不含测试的部分是 36.5 万行，分成引擎和桌面两大块。

桌面壳负责窗口、菜单、文件对话框、系统通知、更新和深度链接。它不把引擎编进界面进程，只通过本机 HTTP 或子进程调用。

本机服务和引擎在同一个进程里。会话、任务、草稿、审核、案件、模型和记忆的写入都从这里进引擎。界面通过这个地址调用它。进度和状态走服务端推送：对话、全局事件、任务进度各一条。

引擎是 `src/lawmind` 那 22.5 万行：Agent 循环、工具、办件识别、证据账本、交付物验收、检索、策略和审批。

界面是 React，提供对话、工作台、文书台、在办、文件和设置。它不能直接访问外网，也不能直接读磁盘，工作区文件经本机桥接。

数据在本机工作区。案件、交付物、审批、队列和期限在每个案件自己的目录里；草稿和修订提案、导出文件、审计分开存放。记忆以 Markdown 为准，案件状态用 JSON 记录；读的时候优先 JSON，没有再退回 Markdown。

### 5.2 一轮是怎么跑完的

律师说出任务之后，系统先看这句话、钉上的文件、案件类型和上一轮在办什么，判断这是合同审查、诉讼文书、检索还是别的。结果是一句“本轮按合同审查处理”。识别错了可以改。显式点名的办件优先于猜测。

然后装配这一轮要用的内容：岗位要求、案件里已经确定的事实、相关记忆、钉上的材料、用得上的 Skill、这一轮允许的工具。Skill 按任务注入，不把 40 个全文一次塞进提示。

模型流式输出，需要时调用工具，工具结果回到对话，计划更新，继续或结束。只读工具可以并行；要批准的工具不会和别的写操作抢同一轮。上下文按模型窗口算预算。对话长了就压缩历史，金额、引用、条款、修订单独钉住，压缩之后再注回去。超长文档保留开头、结尾和命中的段落，中间省略并标明省略了。读不完的文件夹用偏移继续读。换了一个新任务，旧计划会清掉。

复杂的一支派给子工。子工默认 8 轮，只回摘要。应用重启或服务中断后，没做完的任务可以恢复。完成、待批、失败会进系统通知，点进去就到对应的对话或稿子。

### 5.3 怎么知道它没有跑偏

评测看的是 Agent 有没有按设计跑，不是界面好不好看。

真循环回放里，模型的回复是写好的脚本，回合、工具表、门禁、审批和压缩是真的。测试看下一次请求：该出现的工具在不在，不该出现的有没有被拿掉，压缩之后引用还在不在，律师中途改的方向有没有进到下一轮。脚本用完必须失败，不能偷偷补一句“已经做完了”。

影子回放拿已经结案的稿和引擎稿对比，看交付和检索有没有退步。压缩保真看长对话压过之后，金额和引用还在不在。

和律师原稿的对照要求同一道题两份稿、评分的人不知道哪份是 LawMind、至少 10 案，律师稿不占优的比例达到 80% 才算过。没有样本就标未完成，不报一个通过。外部评测在独立仓库里，这里不引用没有复现的榜单分数。

没有实时法源，就显示样例或语料。没有类案索引，就显示未接。没有配模型，就显示未配置。

## 6. 落地

### 6.1 安装包

macOS 提供 dmg 和 zip，覆盖 Apple 芯片和 Intel。Windows 提供安装包、便携版和 zip。Linux 提供 AppImage 和 tar.gz。包里带 Node 运行时和 OfficeCLI，律师不用再装一套环境。应用内更新走 GitHub Release，可以关掉自动检查。

### 6.2 版本

| 版本         | 给谁       | 多出来的能力                                                   |
| ------------ | ---------- | -------------------------------------------------------------- |
| 独立律师版   | 个人执业   | 单人能用的能力都开着；可以和另一位律师共办一案；默认一个父助手 |
| 律所协作版   | 小团队     | 伦理墙、强制同行复核、多助手名册、危险工具强制审批             |
| 私有化部署版 | 律所或企业 | 合规审计导出、安全物料清单、私有部署和统一网关                 |

许可是离线签名，校验不联网，也不回传使用情况。试用 30 天。过期只在界面上提醒，不拦住本机上的交办和导出。

### 6.3 怎么铺开

先给个人律师：安装，配模型，选工作区，就可以做合同审查、文书、检索和案卷整理。看四个数：一次交办、中途不用改指令就完成的比例；首稿不用大改就采用的比例；从可以审到签批要多久；交付之后律师又做了实质修改的比例。没有样本就空着。

再到小团队：委派、复核、在办，以及伦理墙和同行复核。看委派有没有做完、复核卡了多久、一个团队能同时推进多少案子。

最后是律所和私有化：部署在自己的环境里，模型走统一网关，策略和审计按单位要求开。看部署成本、策略是否命中、律师是否还在用。

### 6.4 风险

| 风险                 | 影响                   | 怎么处理                                                   |
| -------------------- | ---------------------- | ---------------------------------------------------------- |
| 模型能力波动         | 交付质量不稳           | 模型可以换；金额、引用、修订由引擎核对；用回放看有没有退步 |
| 法源买不到或没接上   | 一部分检索不可用       | 标明是样例、语料还是实时；没有就说没有                     |
| 律师不放心直接用     | 稿子被搁置             | 引用能回读，修订能逐处接受，待核实单独列出                 |
| 客户材料外泄         | 合规问题               | 案卷在本机；本地模型时上下文不出本机保证绝对安全           |
| 功能铺得宽           | 每个场景都不够深       | 合同审查是主线，其他文书沿用同一套规格和导出               |
| 还没有足够的人类对照 | 说不清和律师一稿的差距 | 盲评规则已经定好；样本不够就不报通过                       |

## 7. 术语

| 术语     | 含义                                           |
| -------- | ---------------------------------------------- |
| 办件     | 一类律师工作，例如合同审查、诉讼文书、劳动计算 |
| 交付物   | 有章节、有验收、能导出的成品                   |
| 钉选     | 把文件或文件夹固定为这一次交办的材料           |
| 收案     | 从“有人来问”到“决定接不接”                     |
| 在办     | 正在跑，或等律师处理的任务                     |
| 修订轨   | Word 里的插入和删除                            |
| 最短改动 | 修订只盖住真正改过的字                         |
| 因子账本 | 引用、金额、修订、条款四类事实的记账           |
| 门禁     | 导出前没通过就不能当成完成的检查               |
| 待核实   | 有结论，但没有对得上的来源                     |

LawMind 不替律师签字。读材料、查依据、改格式由它做；判断、策略和对客户的责任留在律师那里。

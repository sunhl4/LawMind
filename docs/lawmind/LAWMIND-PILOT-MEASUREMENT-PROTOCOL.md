# LawMind 试点测量协议（预注册）

> **状态**：**预注册** —— 本文件在**看到任何试点数据之前**写定（2026-09-22）。
> **目的**：让「这套东西有没有让律师更省事」成为一个**可证伪**的命题，并**预先**约定
> 观测口径、成功／失败判据、以及每种结果之后做什么。
> **纪律**：一旦进入观测期，§2 与 §4 **不得修改**；确需修改只能追加版本（§7），
> 并在报告里标注「此前序列不可比」。

---

## 0. 为什么必须预注册

三句实话：

1. 数据出来之后，人（包括我）会无意识地挑一个好看的口径。预注册是唯一低成本的对抗手段。
2. 事后改口径不会被发现 —— 因为没人记得改前是什么。所以口径必须**带版本号落盘**。
3. 本次观测的目标**不是「证明有用」**，而是让「**没用**」这个结论也能被得出。
   若拿不到这个能力，后面所有投入都无法排序 —— 你只能靠感觉决定先做哪个。

---

## 1. 观测单位与窗口

- **观测单位**：一个工作区（= 一位律师／一家所）。跨所对比**不做**（见 §5）。
- **窗口**：**≥ 8 周**，且**至少有 4 周达到周样本门槛**（§2.4）。
- 为什么不是 4 周：周样本波动大，4 周的趋势与噪声无法区分；8 周是能同时容纳
  「习惯养成」与「口径稳定」的最短窗口。
- **基线**：观测开始前已有的历史数据；若无历史，则**头 2 周只作基线**，不计入判定。

---

## 2. 三条判据（今日口径 · 冻结）

| #   | 判据           | 方向    | 计算定义                                                                                              | 事件来源                              |
| --- | -------------- | ------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------- |
| 1   | 一次通过率     | 升 = 好 | `firstPassOk / (firstPassOk + firstPassFail)`；`firstPassFail` 含 `rewrite`                           | product-events `first_pass`/`rewrite` |
| 2   | 机械核对逃逸率 | 降 = 好 | `lawyer_edit` 逃逸数 ÷ 交付数；交付数 = `first_pass` + `rewrite`                                      | product-events `lint_escape`          |
| 3   | 改稿幅度中位   | 降 = 好 | 每周 `rewrite_amplitude` 的 `absCharDelta` **中位数**（字符），**且仅取 `meta.source="lawyer_edit"`** | product-events `rewrite_amplitude`    |

- 实现与测试：`src/lawmind/metrics/north-star-trend.ts`（23 例，含诚实约束）。
- 复算命令：`pnpm lawmind:north-star-trend -- --workspace <dir> [--window 90] [--json]`。
- 为什么第 3 条用**中位数**：该分布重尾，一次整稿重写能把均值拉飞；中位数回答的是
  「**通常**改多少」，那才是「越用越省事」要测的东西。
- 为什么第 3 条**必须按 `source` 过滤**：同一个 kind 下有两种语义不同的样本 ——
  `lawyer_edit`（律师在文书台直接改稿 = **本判据要测的编辑负担**）与
  `assistant_revision`（助手后台修订 = 模型行为指标）。混在一起算中位数，
  得到的既不是律师负担也不是模型行为。见 §7 的 v1.1 变更记录。

### 2.4 样本门槛（三条共用）

| 规则                     | 取值                   | 为什么                                                                     |
| ------------------------ | ---------------------- | -------------------------------------------------------------------------- |
| 单周报比率的门槛         | ≥ 5 次交付             | 一周 1 次交付时，「100%」与「0%」信息量相同 —— 都等于没有信息，故报 `null` |
| 改稿幅度进入结论的条件   | **每个可用周都有样本** | 只算后半段会引入采样偏差，曲线看着像「越改越少」，实际只是覆盖变了         |
| 给出趋势方向所需可用周数 | ≥ 4 周                 | 少于 4 周的方向大概率和噪声无法区分                                        |

不足门槛时**一律明说原因**，不报 0%、不给方向 —— 这是刻意的纪律，不是没算。

## 3. 判定规则（方向）

把三项各自折算成「改善／恶化／未动」后**投票**（比率容差 0.5 个百分点，幅度容差 1 字）：

| 投票结果     | 方向        |
| ------------ | ----------- |
| 全部「改善」 | `improving` |
| 全部「恶化」 | `worsening` |
| 全部「未动」 | `flat`      |
| 有分歧       | `mixed`     |

**`mixed` 必须原样报出，不许挑好看的那一项。** 这是本协议最容易被绕过的地方 ——
报告里出现「虽然逃逸率上升，但一次通过率明显改善」这类句子，即可判定为**违反本协议**。

---

## 4. 口径冻结清单（观测期内不得改动）

冻结到**函数名／键名**一级。改动任一项即视为**新一次观测**：

| 冻结对象                      | 具体内容                                                              |
| ----------------------------- | --------------------------------------------------------------------- |
| `metrics/north-star-trend.ts` | 分桶（ISO 周）、两个门槛常量、三项计算、`directionOf` 的投票与容差    |
| `metrics/north-star.ts`       | v2 口径：交付分母 = `first_pass` + `rewrite`；逃逸只计 `lawyer_edit`  |
| `policy/judgment-tiering.ts`  | 判定主体解析（`off`/`shadow`/`on` 语义、`posture` 与 edition 的对应） |
| `policy/edition.ts`           | 各 feature 的默认值（改默认值等于改了不同人的产品）                   |
| `lint/` 规则集与触发词        | 新增规则只在观测期**结束后**进入（见 §6）                             |

**必须改时**：在 §7 追加一行（版本／日期／原因／影响），并在当期报告里标注
「**此前序列不可比**」。不允许只改代码不记版本 —— 那样两条曲线会被误当成同一条。

## 5. 明确不成立的推论（禁止的解读）

- ❌ **跨所／跨律师横比能力高低** —— 测到的主要是案件难度分布与个人风格，不是产品差异。
- ❌ **用本协议结果推断行业基准** —— 单工作区纵向数据没有这个信息量。
- ❌ **显著性检验／置信区间** —— 样本量撑不起，硬做出来的是伪科学。
- ❌ **把某一周的升降当结论** —— 只看 §3 的方向判定（且有 §2.4 的门槛）。
- ❌ **用「一次通过率」宣称法律正确性** —— lint 通过 ≠ 法律正确（见 `src/lawmind/lint/types.ts`）。
- ❌ **用「改稿幅度下降」宣称律师更省时间** —— 它只说明改得少了，不度量耗时。

## 6. 每种结果之后做什么（预先承诺）

这一节是预注册的**主要价值**：先承诺动作，避免结果出来后再编解释。

| 结果                         | 预先承诺的动作                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------ |
| `improving`（≥2 项实质改善） | 继续投判断层与素材层；把该工作区的口径沉淀（playbook／先例／改稿范例）作为**留存设计**主线 |
| `flat`                       | **不追加功能**。先查「是不是没用起来」（装机、公证、性能、入口），而不是「功能不够」       |
| `worsening`                  | **立刻停手查回归**（优先怀疑最近一次改版），**冻结新功能**直到查清                         |
| `mixed`                      | 拆开定位是哪一项恶化，逐项归因；**禁止**用改善项对冲恶化项来宣称成功                       |
| 样本不足（< 4 可用周）       | 结论是「**证据不足**」，**不是**「没变差」。**不得**据此宣称任何能力                       |

> 附：`flat` 与「样本不足」的区分至关重要。前者是**有证据的没变化**，后者是**没证据**。
> 两者在报告里必须是不同的句子。

## 7. 变更记录

| 版本 | 日期       | 变更                                                                                | 影响                                                                                            |
| ---- | ---------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| v1   | 2026-09-22 | 预注册：三条判据 + 样本门槛 + 投票规则 + 冻结清单 + 动作                            | 首次生效                                                                                        |
| v1.1 | 2026-09-22 | 判据 3 改为**仅取 `meta.source="lawyer_edit"`**（律师直接改稿），并补上该路径的埋点 | **观测尚未开始**，故不产生「序列不可比」；若不改，判据 3 测的是助手改稿量，与它要回答的问题不符 |

> v1.1 的由来（值得记下来，因为它是"预注册"本身发现的问题）：拿到第一份真实诊断包后核对数据源，
> 发现 `rewrite_amplitude` 事件**只由「提交给助手后台修订」那条路产出**，
> 而律师最常用的**直接在文书台改稿**路径不产出样本 ——
> 也就是说判据 3 实际测的是「助手改了多少」，而它本该测「律师的编辑负担」。
> 已给两种来源打上 `meta.source` 区分，并让判据 3 只认 `lawyer_edit`。
> **这正是预注册的价值：问题在收集数据之前暴露，而不是收集八周之后。**

## 9. 与产品内既有口径的关系

- Doctor 的「交付北极星」区与 `pnpm lawmind:release-readiness` 的
  `## Delivery North Star (does it help the lawyer?)` 节展示**同一份**趋势；
  证据不足或方向为 `worsening`／`mixed` 时，发行报告会把它**计入 knownRisks**。
- 发行报告里水平值样本低于门槛时给提醒但**不撤数字**（口径归 `north-star.ts` 的 v2 决定，
  趋势模块不越权改算）。

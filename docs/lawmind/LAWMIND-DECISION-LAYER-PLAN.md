## 0. 出发点：飞轮有写入端，没有读取端

实施任何新东西之前，先固定这个事实（逐行核实）：

| 事实                                                                                     | 证据                                                                     |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `escape-candidates.jsonl` / `escape-corpus.jsonl` / `escape-stance.jsonl` **一直在写盘** | `metrics/lint-escape-candidates.ts:25` `distributeLintEscape`            |
| 写入被产品路径调用                                                                       | `engine/reviewing.ts:86`、`:200`                                         |
| **全仓没有任何一处读它们**                                                               | 全仓 `rg` 只有 `engine/reviewing.ts` 的 import 与 writer 自身；无 reader |

也就是说：**第十四期设计的「lint 逃逸飞轮」转了三个季度，产物堆在磁盘上，没有消费端。** 规则候选没有回流、语料没有进 benchmark、立场候选没有进立场库。

这决定了 P0 的形态——**不是去造新数据，是把已有数据接上电。**

## 1. 目标与非目标

### 目标

1. 让「LawMind 现在判错了多少」从**没有数字**变成**有数字、可复现、可追踪**。
2. 让飞轮闭合：逃逸 → 规则候选 → 法律顾问验收 → 规则包。
3. 判断层逐步从「运行时推理」迁到「编译产物」，运行期零出网、零边际成本。

### 非目标（明确不做，防做歪）

- 不引入任何外部决策模型作为 P0–P4 的前置。
- 不把概率写进 `matters/<id>/*.json` 当真值。
- 不降级任何既有确定性门禁（`permissionMode` / `clarificationGate` / `approval`）。
- 不自动落盘规则——所有规则候选走 `memory/adoption-service.ts` 的待确认队列。
- 不在没有法律顾问验收的情况下把新规则从 advisory 升到 blocking。

## 2. 阶段总览

| 阶段   | 产出                                                           | 为什么在这个位置                     | 依赖                    |
| ------ | -------------------------------------------------------------- | ------------------------------------ | ----------------------- |
| **P0** | 决策语料导出器 + 逃逸读取端 + 数据体检报告 + 方案 A 确定性收口 | 编译器要有原料；先消灭纯数据缺口     | —                       |
| **P1** | 飞轮接线（逃逸 → 规则候选 → 待确认 → 规则包）                  | 越用越准的唯一实现路径               | P0 **且需真实办件数据** |
| **P2** | LLM 调用受约束 + 聚合回代码；三路径分歧记录（shadow）          | 零新供应商零出网即可拿到不确定性信号 | P0                      |
| **P3** | firm-specific 校准器（覆盖编译器够不着的部分）                 | 越用越准，且贴本所口径               | P0/P1 **且需数百样本**  |
| **P4** | 把 `isAutonomyUnlocked` 棘轮从「交付」推广到「判断」           | 机制已存在，只需扩域                 | P2/P3                   |
| **P5** | 评估外部判定器（仅当异质第三票）                               | 到这一步它才是净收益                 | P0–P4                   |

**顺序理由**：前四步每一步的产物都是**你自己的资产**，且后一步复用前一步的产出。接外部模型不产生资产，只是把「未知」从一层变两层。

**P0 实测修正（见 §3.5）**：P1 与 P3 依赖真实办件数据，而当前工作区为零。所以**能立刻开工的是 P0-4 与 P2**（两者都不依赖历史数据）；P1/P3 的排期由「有没有真实工作区跑过完整闭环」决定，不由工程决定。

2. 所有样本都没有正文片段——只有计数，没有语料。

**结论一：飞轮不是「转得慢」，是从未产生过任何一条记录。**

全仓 `find -name 'escape-*.jsonl'` 为空，`workspace/lawmind/lint/` 目录不存在。也就是说第十四期设计的
「lint 逃逸飞轮」——`LAWMIND-LEGAL-COMPILER-ROADMAP.md` §1.8 把它写成「把『越用越像这位律师』从口号
变成可度量的收敛过程」的那一个机制——**在真实工作区里产出为零**。

这里必须区分两个原因，别急着下结论：

- **结构原因（已确证）**：写入端只在审核路径（`engine/reviewing.ts` 的 `recordLintEscape` / `reviewDraft`）
  触发，而 `recordLintEscape` 在 `lintHits <= 0 && !lawyerEdited` 时**直接 return**——不写任何东西。
  所以「一切正常、律师没改」的交付根本不产生逃逸行。这是对的（没有漏网就不该记），但意味着
  **飞轮的产出量完全取决于「出过问题的交付数」**，而这个工作区样本极少。
- **口径原因（未能排除）**：本工作区是开发/演示工作区，可能从未走过完整的人工审核+交付闭环。
  真实律所工作区是否同样为零，**本报告无法回答**——这需要真实使用数据。

**结论二（更可操作）：P2/P3 在没有真实使用数据之前无法起步。**

- P3 校准器需要几百个样本，现在有 2 个、且零正文。
- P1 规则编译需要漏网语料，现在是零。
- 所以 **P1/P3 的排期不由工程决定，由「有没有真实办件跑过完整闭环」决定。**

**结论三（对计划的修正）**：`LAWMIND-DECISION-LAYER.md` §11 把 P0 定义为「先补测量」，这个判断成立，
但测量结果指向的下一步**不是继续加工程**，而是：

1. **让审核路径真的跑起来**（哪怕是内部演练）：飞轮只在真实交付后才有燃料。
2. **优先做 P2（约束 + 分歧）**——它不依赖历史数据，零样本也能开工。
3. **P0-4 方案 A 的确定性收口**优先级上升——因为它是**唯一不依赖任何数据**的一档。

> 这一条修正本身就是 P0 的价值：**在写一行业务代码之前，先把「有没有原料」问清楚。**

#### 4a 为什么**没有**把 `facts_grounded` 升为 blocker

计划写的是「严重级别按 `required` 生效」。**实测后否决**——升上去是回归，不是修复。证据链（每一环都跑过）：

1. `buildLegalReasoningGraph({ intent, bundle })` 的签名里**没有案件事实**，所以 `facts` 理论上只能来自检索 bundle。
2. bundle 里唯一的「案件事实」来源是 `memo`（← CASE.md）与 `workspace`（← CLIENT_PROFILE），由 `createWorkspaceAdapter` 产出——**而它返回 `claims: []`**（实测断言）。
3. `buildIssueTree` 只从 `claim.sourceIds` 反查 sources ⇒ 这些来源**永远不会被引用**。
4. 会产生结论的适配器（model-adapters / brave-web / url-dossier）只发 `statute` / `web`（见 `model-adapters.ts` 的 `toSources`）。
5. 于是 `factsTotal` **恒为 0**（实测：真实形状的 statute+case bundle → `factsTotal = 0`）。
6. 而 `acceptanceGateStrict` 在 solo / firm / private_deploy **三档全部默认开启**（`policy/edition.ts:36`）。

> 所以升为 blocker = `minFacts >= 1` 的高危 spec（`letter.*` / `litigation.*` / `contract.review`）在**所有 edition 下必然拦截渲染**。那是产品级故障。

**实际采取的做法**（三者都做了，且都可测）：

- **补数据侧**：`facts` 不再写死 `[]`，改为按来源 kind 的**显式 IRAC 映射**填充；`IRAC_SOURCE_KIND_COVERAGE` 导出为单一真相源，并用测试锁定「三个集合互斥且覆盖全部 `SourceKind`」——新增 kind 忘了归类会被测试拦住。
- **让检查可诊断**：`factsGroundedHint()` 区分「结论没引用事实材料」与「检索根本没返回事实材料」——后者明说这是**结构性缺口、不代表本次稿件有质量问题**，避免让律师以为是自己材料没给。
- **把决策写成代码里的显式理由 + 升级前提**（`FACT_GROUNDED_SEVERITY_FOR_REQUIRED_SPECS`），并加一条**反向回归测试**：断言未通过时 `severity === "warning"` 且 `report.ready === true`。将来有人「顺手改成 blocker」会先撞到这条测试。

**升级前提**（满足任一即可安全升为 blocker，届时同步改那条反向测试）：
a. 某适配器开始产出**并被结论引用** `contract` / `memo` / `workspace` 类来源；或
b. `buildLegalReasoningGraph` 通过新增的 `caseFacts` 入参拿到案件事实。

> 这是继 P0 之后第二个「计划被实测修正」的条目。`facts_grounded` 的问题**不是**漏写一个 `blocker`，而是**判据维度缺失**：它要求的东西，当前数据流根本不产生。

#### 4b 修掉的两类误报

| 情况                                 | 旧行为 | 问题                                 | 新行为           |
| ------------------------------------ | ------ | ------------------------------------ | ---------------- |
| 两条结论引**同一条**法条、置信度差大 | 报冲突 | 分歧在**推论**不在**权威**，报错对象 | 不报             |
| 两条**不相关**结论各引不同权威       | —      | 真正的权威冲突反而**没有**判据       | 报（同主题时）   |
| 主题识别不出                         | —      | —                                    | 不报（宁缺勿滥） |

新判据需同时满足：**同一法律主题**（`detectLegalTopic`）× **依据不同权威** × **置信度差 > 0.3**。`authorityIds` 改为填两条结论权威来源的**并集**（原先填「共享来源」——即分歧不在的那一方）。

#### 4c 补上的判据维度

旧实现 `scanPrivilegeTip(text)` 只看正文，于是「同一段对内策略，发给助理」与「发给对方律师」被判同一等级。**特权风险本质是「内容 × 收件人」的联合函数**——脱离收件人判特权，必然在真正危险的那条路径上低估。

新增 `assessOutboundPrivilege({ text, audienceKind, attachmentNames })`，出站门禁改用它。**只加严不放松**（有测试锁定）：旧实现返回 warn 的场合仍为 warn；额外在「所外受众 × 特权外观附件名」时升级——这条路径旧实现**完全看不到**。

刻意**不**把 `internal` / `client` 当所外：对所内同事与委托人披露工作成果是该走的路，误报只会变成噪声，最终让律师把整个提示关掉。

#### 4d 三份副本的实际漂移

| 条款类型 | habit-extract          | stance/capture         | stance/self-check（旧）          |
| -------- | ---------------------- | ---------------------- | -------------------------------- |
| 管辖     | `管辖\|争议解决\|仲裁` | `管辖\|争议解决\|仲裁` | `管辖\|争议解决\|仲裁\|人民法院` |

即「同一段文字属于哪类条款」**取决于调用哪个模块**——不报错，只让立场统计与自检结果对不上。`stance/capture.ts` 的注释甚至写着 _"Duplicated … do not import (cycle risk)"_（该 cycle 风险经核实不存在：`clause/` 不回指 `stance/` 或 `historical-scan/`）。

合并结论：**表合并，但放宽与否按用途显式区分**——

- 分类用途（红线分类、习惯聚类）**必须窄**：取**首个**命中，把 `人民法院` 并进「管辖」会让「赔偿责任……由人民法院判决」被误分类成管辖、污染立场聚类。故 `detectClauseTypeKeyword` / `detectStanceClauseType` **不放宽**。
- 自检用途**可以宽**：只问「正文是否谈到该类条款」，多一条 info 级提示无副作用。故显式调用 `clauseTypeMentionedIn(..., { includeForumMentions: true })`。

这个差异以前是「两份表默默不一致」，现在是显式、可测、有理由的一条。另加反漂移测试：直接读三个消费方源码，断言它们**引用**共享表且**不再内联**条款正则表。

`engine/reviewing.ts:169-190`：

> 它 lint 的是**审核时传入的 draft**，也就是**律师改完之后提交的那一版文本**。

| outcome         | 精确含义                                                   |
| --------------- | ---------------------------------------------------------- |
| `lint_findings` | **最终稿**仍有 blocker/warning                             |

> 因为 lint 读的是改后文本，缺陷已经被改掉了。

也就是说 `rule_miss` 只能表示「最终稿无机械缺陷但仍被改过」（可能只是口径/风格），
**不等于**「编译器漏掉了实体缺陷」。已在 `metrics/decision-samples.ts` 与
`metrics/escape-flywheel-semantics.test.ts`（7 例）中改正并锁定。

#### 3.7.3 实测出的两条真实规则缺陷

#### ① 盲区：定金超限的**金额形态**抓不到（最重要的发现）

合同最严重的实体缺陷是定金 **310,000 / 标的额 1,032,000 = 30.04%**，超民法典第 586 条的 20% 上限。
规则 `statutory.deposit_cap` **静默放过**了它，因为：

```text
规则匹配：定金[^。]{0,24}?(\d+)%      ← 只认**显式百分比**
真实合同：定金 310,000 元              ← 只给金额，从不写「30%」
```

> **编译器最该拦的那一条，恰好是它抓不到的那一条。**

而这正是飞轮**看不见**的那一类（§3.7.2）——缺陷在提交前既没被规则发现、也没被改掉，
所以两条证据链互相印证了这个盲区的严重性。

已固化为 `lint/deposit-cap-coverage.test.ts`（5 例，精确复现命中条件的确切形状：
必须「定金」与百分比同句且相隔 ≤24 字、跨句号不命中、无「定金」二字完全不看）。
**未修**——修它需要判定「哪一个是标的额」，属于需要法律顾问复核的判据设计
（路线图 §1.5 铁律）。它现在是一条规则候选。

#### ② 误报：把**合同类**规则用在信函上

反向问题：`consistency.party_pair`（要求正文同时出现甲方与乙方——那是**合同**的主体成对性检查）
会因为一封催告函的**摘要**写了「乙方」而报 warning。同正文、仅摘要措辞不同：

| 摘要                                     | 结果                               |
| ---------------------------------------- | ---------------------------------- |
| 「催告乙方按约交付设备」                 | `consistency.party_pair` (warning) |
| 「致苏州朗行电子科技有限公司的履约催告」 | 零命中                             |

这里还有一条更基础的口径发现：**linter 的输入是 `draftTextFromUnknown(draft)`**
——`title + summary + 各 section 的 heading + body` 拼起来的**全文**，不只是正文。
所以「给信函写个含乙方的摘要」这种完全正常的写法会踩到合同规则。

两个方向合起来说明同一件事：**lint 的规则是按「起草合同文本」标定的**，
用在「讨论合同的文书」（意见书、信函）上会系统性误报。

### 3.8 方向修正：管道该修成**素材**，不是闸（2026-09-21）

上一节跑通了一轮，但真正重要的修正发生在这之后——**它改变了 P1 及之后的方向**。

#### 3.8.1 问题的提出

> 「管道其实是硬设置。硬设置鲁棒性会差些——这正是可能限制模型能力的地方，
> 并不是让模型更聪明更好地完成任务。」

这个判断在代码里有**活证据**，而且是 §3.7 刚实测出来的：`consistency.party_pair`
（要求正文同时出现甲方与乙方——那是**合同**的主体成对性检查）会因为一封催告函的
**摘要**写了「乙方」而误报。**模型本来写得好好的，硬规则凭空插一脚。**

同一批实测还给了反向证据：合同里最严重的实体缺陷（定金 30% 超 20% 上限）被
`statutory.deposit_cap` **静默放过**。所以同一个硬设置体系：

> **该拦的没拦住，不该管的乱插嘴。**

#### 3.8.2 修正是「三类」，不是「硬 vs 聪明」

定金那个案子说明：**模型失败的不是判断，是算术。** 它在猜下一个 token，不在算除法。
所以正解既不是加正则、也不是"让模型更聪明"，而是第三类：

| 类       | 是什么             | 该有多少             | 例                                                       |
| -------- | ------------------ | -------------------- | -------------------------------------------------------- |
| **闸**   | 责任边界，有拦停权 | **极少**             | 现在只有 `send_email` 一个                               |
| **算**   | 算术/查表/日期     | **少，但每个都该做** | 把「定金占比 30.04%，超上限 10.04 个点」**算好塞给模型** |
| **范例** | 律师改过的样子     | **越多越好**         | 「保留权利」→ 通牒式                                     |
| **判断** | 其余全部           | **绝大多数**         | 争点拆解、论证、条款取舍                                 |

定金的正解是第二类：**把该算的算好，交给模型判断**——这不是限制模型，是喂素材。

#### 3.8.3 真正的资产是「范例」，而我原来的方向偏了

**承认偏差**：P4 棘轮的目标是让判断项「从 advisory 升 blocking」——
**那字面上就是在增加硬闸的数量**，正对着用户担心的方向。

而查到的事实是：**「给模型看范例」这条通道早就在生产里跑了**：

```text
turn-orchestrator-prompt.ts:931
  loadGoldenExamplesForDrafting(...)  →  formatGoldenExamplesPromptBlock(...)  →  memory_hit
```

系统已经会把「黄金范例整稿」检索出来注入上下文，让模型照着学。**它唯一没接的是：
律师日常改稿产生的 (改前, 改后) 对照。**

两条通道此前是分开的：

| 通道 | 触发                       | 存什么                                       | 注入                 |
| ---- | -------------------------- | -------------------------------------------- | -------------------- |
| 偏好 | 律师审核                   | 压成 **≤160 字一句话** → `LAWYER_PROFILE.md` | 每轮进 system prompt |
| 范例 | 律师**显式**标「质量范例」 | **整稿** JSON → `golden/`                    | 检索后注入节选       |

而 `extractChangeSpan` **已经拿到了完整的成对文本**，却立刻被
`formatEditLearningCandidates` 压成 160 字的描述。**信息在压缩时丢了**：

```text
范例（保留）：「…保留解除合同及要求赔偿损失的权利」
             → 「…现要求贵司于 2026 年 10 月 5 日日前完成全部交付…」
             能看出场合、力度、落款规矩
偏好（压缩）：「催告函要有明确期限和解除后果」
             场合没了、示范没了
```

#### 3.8.4 落地

**新增** `src/lawmind/learning/edit-examples.ts`（24 例测试）+ 接线：

| 落点                                    | 动作                                                             |
| --------------------------------------- | ---------------------------------------------------------------- |
| `learning/edit-examples.ts`             | 新增：`toEditExamples` 过滤 → `recordEditExamples` → 检索 → 注入 |
| `learning/draft-edit-learning.ts`       | `captureDraftEditLearning` **同时**走两条通道（原偏好通道未变）  |
| `evaluation/golden-recall.ts`           | 抽出 `scorePayloadAgainstQuery`——**两个通道必须同权打分**        |
| `agent/turn-orchestrator-prompt.ts`     | 与 `goldenHints` 并列，以 `memory_hit` 注入                      |
| `server/lawmind-server-route-review.ts` | 正文 PATCH 传出 `deliverableType` / `matterId` / `reviewNote`    |
| `.gitignore`                            | 增 `workspace/edits/`                                            |

**四类设计约束**（都有测试锁定）：

1. **与 `golden/` 分开存。** `golden/` 的语义是「律师**判定**这条是典范」；
   改稿只是「律师动过手」——很多改稿在**修缺陷**，不是示范。
   混存会让坏例子挤掉好例子，也让 `golden/` 的含义变模糊。
2. **存得宽、注入得省。** 存储上限 600 字/侧，**注入上限 220 字/侧**。
   这是实测出来的：首版把 600 字原样塞 prompt，结果打包器**在范例块中间截断**，
   把末尾的「律师说明」——最值钱的「为什么改」——挤掉了。
   修法不只是缩小，还要**把最短最值钱的字段放最前面**（说明现在写在标题行）。
3. **只加不改。** 原有偏好通道完全未动（返回类型、待确认队列、`LAWYER_PROFILE` 落盘都不变）。
   范例是**第二条**通道，不是替代。
4. **素材，不是闸。** 注入文案有测试断言**不得出现**「必须 / 一律 / 禁止 / 不得」；
   检索不到 → 整块不注入 → 什么都不影响；写入失败不得影响偏好通道的返回值。

**归因不确定性（诚实）**：`before` 是**系统自己当时的稿**，`after` 是律师终稿。
两者的差不一定全是"口径偏好"——也可能是律师在改**系统写错的事实**。
所以注入文案明说「不要照搬其中的事实或当事人」，且**不**把 `after` 当成"正确答案"。

#### 3.8.5 这对后续排期的影响

| 原方向                          | 修正后                                                  |
| ------------------------------- | ------------------------------------------------------- |
| P1 = 攒样本**编译规则**（加闸） | P1 改为**攒范例对**（加素材）；规则编译只做**误报收敛** |
| P4 = 让棘轮解锁**更多硬闸**     | P4 优先级**下降**——它是"加闸"机制，与本节方向相反       |
| 批量跑的目的 = 够样本编译       | 批量跑的目的 = **够范例**，顺带量出哪些规则在误报       |

> **一句话**：同一个批量跑，产出从「规则包」改成「范例库」。
> 这也解释了为什么这一节比 §3.7 重要——它改的不是数据量，是**方向**。

#### 3.8.6 第二类落地：「算好的事实」

§3.8.2 的三类里，第二类（**该算的算好，喂给模型**）已落地为
`src/lawmind/reasoning/derived-facts.ts`（24 例测试）+ prompt 接线。

**为什么先做这一类**：它是三类里唯一能**同时**解决盲区与误报的——

|                   | 加规则（闸）               | 算好喂给模型（素材）         |
| ----------------- | -------------------------- | ---------------------------- |
| 定金盲区          | 要再加一条正则，还是可能漏 | **算出来就不漏**             |
| `party_pair` 误报 | 只会更多                   | **不新增规则，无误报**       |
| 要顾问验收吗      | **要**（判据扩张）         | **不要**（是算术，不是判据） |
| 模型升级后        | 可能变成累赘               | 自动升值                     |

**第一条事实：定金上限占比**。同一份真实合同，规则与派生事实的对照：

```text
规则 statutory.deposit_cap：**未命中（静默放过）**
  （它只匹配 `定金…(\d+)%` 显式百分比，而合同只写金额）

派生事实：
  定金 310,000 元 占合同标的额 1,032,000 元 的 30.04%；
  民法典第586条载明的上限为标的额的 20%（即 206,400 元），
  当前占比高出 10.04 个百分点，金额上高出 103,600 元。
  算式：310000 ÷ 1032000 = 0.3004 → 30.04%
        1032000 × 20% = 206400
        310000 − 206400 = 103600
  出处：民法典第586条
  原料：合同标的额「1032000 元」、定金「310,000 元」
```

**三条硬约束**（都有测试锁定）：

1. **事实，不是结论。** 只说数字与出处，不下法律判断。有测试断言产出里
   **不得出现**「违反 / 无效 / 必须 / 不产生定金效力」。
   区别在可追溯性：`30.04% > 20%（民法典第586条）`是可复核的；
   「该条款无效」是断言，错了没人看得出来。
2. **必须给算式。** `arithmetic` 字段把中间步骤写出来——**这是「素材」与「神谕」的分界**。
   模型看到 `310000 ÷ 1032000 = 0.3004` 才能自己判断；只给「30.04%」它只能照抄。
3. **算不出来就什么都不说。** 找不到「合同总价款/标的额」这类明确标记时**不猜**。
   猜错一个标的额会产出一个看起来权威的错误数字，比没有事实更糟。

**与门禁的关系：无。** 产出只作 `memory_hit` 素材，不进任何门禁；
任何异常一律吞掉；算不出就是空数组；永不抛。

**两个实测抓到的 bug**（都由新测试锁定）：

| 症状                                                   | 根因                                                                                                                                     |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 真实合同一条事实都算不出                               | 标记用 `exec` 只找**第一次**出现，而「## 第二条 定金」这种**章节标题**先命中且后面没有金额，于是整个计算被放弃、真实的那条规定反而没读到 |

**端到端断言**：`agent/edit-examples-prompt.test.ts` 验证算好的事实

#### 3.8.7 第二类扩展：四类事实（本轮完成）

#### 边界与克制

- **`penalty_asymmetry` 刻意不判「不公平」。** 把「5% 对 0.05%」说成「100 倍不利」是**错的**——
  一侧基数是合同总价款、另一侧是逾期金额。基数不同时比倍数没有意义。本模块只给出可比性材料。
- **`payment_sum` 的百分比分项不参与合计**（没有绝对值无法相加），且产出里**明说**这一点，
  不让模型以为合计已完整。
- **体裁表精确匹配优先于前缀匹配**——见上表第 4 条 bug。
- 全部四类都**只作 `memory_hit` 素材**，不进任何门禁；异常一律吞掉；算不出就是空数组。
- **prompt 预算是真实约束**：这个块约 445 tokens，是本轮最大的一块素材。
  三个素材通道（黄金范例 / 改稿范例 / 派生事实）共用同一份 tail 预算——见 §9 风险 D10。

#### 3.8.9 这一轮又抓到的四处误报（同一个根因）

扩展过程中，**四处误报的根因完全相同**：用「标记后 N 字」的窗口取值，
窗口跨过句号之后就把**下一个条款**的数字算到本标记头上。

| 症状                                                        | 具体                       |
| ----------------------------------------------------------- | -------------------------- |
| 「已含于总价款内）」抓到下一条的 722,400 元                 | 造成假的「总额前后不一致」 |
| 「第二条 定金」这个**标题**抓到下一条的金额                 | 已在 §3.8.7 修过           |
| 付款条款结尾的「已含于总价款内」把 722,400 贴上「价款」名目 | 假标签                     |
| 「合同总价款的 5% **支付违约金**」被算成付款比例            | 造成假的「比例合计 10%」   |

**根因处理是收敛的，不是逐点打补丁**：抽出 `sentenceAfter` / `sentenceAround` / `sentenceBefore`
三个句子级原语，所有「标记 + 取值」都改走它们。并明确分工：

- **取值**用 `sentenceAfter`（值必须在标记**之后**）；
- **判语境**用 `sentenceAround`（语境可能在前面，如「甲方逾期付款的，每逾期一日按……5%」）；
- **取名目**用 `sentenceBefore`（名目总在数字**前面**）。

而只做「取本句」还不够——第一版修法就栽在这：合同常把单价与总价写在**同一句**里
（「……单价 86,000 元，合同总价款为 1032000 元。」），取本句的**第一个**金额会拿到单价。
所以必须是**标记之后到句末**。同理，**数量**常写在单价**之前**（「供应 12 台，……，单价 86,000 元」），
故数量用 `sentenceAround`。

**语境闸而非语义猜测**：把违约金费率排除出去，用的不是「猜它像不像费率」，而是两条纯事实的判据：

- 句子含「违约/逾期/滞纳/罚息/赔偿」→ 排除（这是费率）；
- 句子含「误差/偏差/不超过/不低于/浮动」→ 排除（这是容差）；
- 必须出现在含「支付/付款/退还/结算」的句子里 → 才计入。

**名目可有可无**（实测）：强制要求付款名目会漏掉真比例——
「2 验收合格后支付 65%。」没有名目，但它确实是付款比例。

#### 3.8.10 素材块健康（D10 收口的可观测半点）

`material-blocks.ts` 的 `summarizeMaterialBlockHealth()` —— **丢弃可测，不只写在文案里**。

**为什么必须可测**：D10 之后素材是「一个受预算约束的片段，超预算整块丢弃」，
而丢弃此前只体现在 prompt 文案（「本次因篇幅未展开：质量范例」）——
**律师看得见，系统看不见**。于是无法回答一个真实问题：

> 某个通道是不是**长期**被丢？如果黄金范例 80% 的回合都被丢，
> 要么预算太小，要么这个通道不值得留 —— **这需要数字，不是印象**。

**口径三条**（都有测试锁定）：

| 口径                                               | 说明                                                                                                            |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `presentCount = 纳入 + 丢弃`                       | **只有「本来有内容」的回合才进分母**。某通道本来没内容（没改稿范例）不算「被丢」。                              |
| `dropRate` 在 `presentCount === 0` 时为 **`null`** | 不编造 0%。参照 `metrics/north-star.ts` 的「Missing samples stay null」。                                       |
| `worstChannel` 需要**样本足够**                    | 阈值 `MATERIAL_HEALTH_MIN_SAMPLES_PER_CHANNEL = 5`；样本少时只报 `anyDropped`，不给比例（太少时比例剧烈跳动）。 |

记录点：`recordMaterialBlockEvent()` 在**真实 prompt 路径**里调用（不是测试专用口）。
新增产品指标 kind `material_block`（`product-metrics.ts`），`outcome` 为
`complete` / `dropped`，`meta` 携带 `included` / `dropped` / `droppedCount` / `chars`。

**`meta` 为什么用逗号连接的名字而不是数组**：`ProductMetricEvent.meta` 的类型是
`Record<string, string | number | boolean | null>`（不含数组）。为一个观测字段放宽
共享事件类型的 blast radius 不划算；名字集合很小、解析也直接。

**端到端**：`agent/edit-examples-prompt.test.ts` 断言**走真实 `prepareTurnPromptContext`
之后**指标确实落盘 —— 因为这一整轮的教训正是「数据在盘上、没人读」。

**`lawmind:round` 里看不到这个指标是正常的**：它走的是 **engine 管线**
（`createLawMindEngine`）而不是 **agent turn**，而素材注入在后者。
CLI 会如实说「尚无观测数据」，不折算成 0。

#### 2.1 的设计要点：**默认行为零变化**

`response_format: {type:"json_object"}` 只保证「是 JSON」，不保证「字段名对、枚举在集合内」。
所以 `router/model-route.ts` 至今需要 `isTaskKind()` 在**返回后**再校验一次——
这意味着「模型编了一个 kind」与「模型没答」在行为上**不可区分**（都走 null 回退）。

升级到 `json_schema` + `strict: true` 能把「结构上不可能返回非法值」变成协议保证。
但 OpenAI 兼容端点对它的支持**并不统一**，硬上会让不支持的一侧直接 400。

因此本模块**不猜厂商能力**：

| 模式           | 行为                                                             |
| -------------- | ---------------------------------------------------------------- |
| `auto`（默认） | 只对 `KNOWN_STRICT_SCHEMA_HOSTS` 启用 strict                     |
| `on`           | 无条件尝试；400 拒绝时**在同一次调用内**降级重试并记入进程内缓存 |
| `off`          | 一律 `json_object`                                               |

**`KNOWN_STRICT_SCHEMA_HOSTS` 目前是空数组**——即落地后的默认行为与升级前完全一致。
这是刻意的：能力矩阵要逐个实测（发一次请求确认 200 + 符合 schema），不能凭印象填。
`LAWMIND_LLM_JSON_SCHEMA=on` 可主动开启探测。

两个细节：

- **降级不消耗采样预算**：strict 被拒时 `attempt -= 1`，因为那是**我们的能力判定错了**，
  不是模型输出失败——让这次重试吃掉一次采样额度会让所有首次探测都白跑一轮。
- **被拒主机记进进程内缓存**：否则每次调用都想试一次，延迟直接翻倍。
  可用 `listStrictSchemaRejectedHosts()` 观察当前进程的能力判定。

#### 2.2 的核心转变：模型不做结论，代码做结论

旧口径让模型**直接输出 `verdict: pass|fail`**——等于把「可过」这个结论交给一次生成完成。
问题不是它会答错，而是**没有可审计的中间步骤**：律师看不到哪几项判过了，
复盘时也无法区分「模型认为都覆盖了」与「模型没看清问题就给了 pass」。

新口径把职责切开：

- 模型只做**逐项**判断（`items[].id` + `supported`）——可枚举、可交叉核对、天然独立；
- `verdict` 由 `aggregateGuardianItems()` 在代码里聚合。

聚合规则（`legal-guardian.ts`，全部有测试锁定）：

| #   | 条件                                 | 结果                                                    |
| --- | ------------------------------------ | ------------------------------------------------------- |
| 1   | 任一 checklist 项 `supported: false` | fail + `checklist_not_covered`                          |
| 2   | 任一 checklist 项**未被回答**        | fail + `checklist_unanswered`（**缺答即 fail**）        |
| 3   | `supported: true` 但 `note` 非空     | fail + `checklist_note`（保留可见性，不吞掉）           |
| 4   | 回答了检查单里没有的 id              | fail + `checklist_unknown_item`（防「编一个通过的项」） |
| 5   | `summaryGaps` 非空                   | fail（全文级缺口）                                      |
| 6   | 以上都不成立                         | pass                                                    |

第 2 条是 fail-closed 的关键：**缺答不等于通过**。模型漏答一项时，
宁可判 fail 让律师看，也不要静默放行。

第 4 条同样重要：模型若报了一个检查单里不存在的项，**不静默丢弃**——
那正是「编造一个通过的项」的形状，必须记为缺口。

**向后兼容**：`parseGuardianVerdict()` 先试新形状，不成形状时回退
`parseGuardianReviewerJson()`（旧 `{verdict, gaps}`），语义不变（仍是 fail-closed）。
自定义提示词的部署与历史 sidecar 重放都能继续工作。

#### 2.3 最关键的一点：三路径是**零额外成本**拿到的

`routeAsync` 原本的流程是「模型成功就用模型、失败才算关键词」。
改造后：

```text
keywordIntent = route(input)        // 同步正则纯函数，本来就不贵
modelIntent   = await routeWithModel(...)   // 已经在跑，不额外花钱
                                 // 第三条：runTriageRules(input) 同步正则
```

三条路径**都不需要额外调用**——所以分歧信号是白拿的。
这也解释了为什么「分歧驱动」在 LawMind 里比「接一个概率模型」划算得多：
后者是新增一次网络调用，前者是把已有结果互相校验。

为什么这比概率更贴合 LawMind：

| 性质        | 分歧驱动                           | 概率模型             |
| ----------- | ---------------------------------- | -------------------- |
| 阈值        | **不需要**                         | 要定、要调、会被忘掉 |
| 训练        | **不需要**                         | 需要                 |
| 供应商      | **不需要**                         | 需要                 |
| 可解释性    | 「正则说合同审查、模型说法律检索」 | 「模型给了 0.73」    |
| fail-closed | **结构性**（不一致→升级）          | 取决于阈值           |

判定口径刻意**不做加权、不设阈值**：

- `kindAgreement`：所有**给了 kind** 的路径一致（0 或 1 条意见时视为一致——那是「不可判」不是「通过」）。
- `missingOpinions`：没给 kind 的路径。**缺答不算分歧**，但记下来——
  某条路径长期缺答本身就是「它对该类输入不可用」的证据。
- `divergenceKey` 只由分类集合的**排序结果**决定，便于聚合「同一类分歧出现了多少次」。

#### 2.4 升级姿态默认 `shadow`（两个契约的调和）

P2.3 说「只记录不改行为」，P2.4 说「分歧就升级」。两者不冲突，靠姿态分层：

| 姿态             | 行为                                       |
| ---------------- | ------------------------------------------ |
| `off`            | 不记录                                     |
| `shadow`（默认） | 记录 + **算出**本该升级成什么，但不交出去  |
| `escalate`       | 记录 + 把 `requiresConfirmation` 置为 true |

默认 `shadow` 的理由：直接默认升级会让律师在早期被大量「正则与模型打架」的卡片淹没。
**先把升级路径算出来并记录，等分歧数据证明它不是噪声再开启。**

升级描述符（`buildRouteDivergenceEscalation`）有三条设计约束：

1. **不替律师选路**——只摆出「三条路径分别是什么」，文案明写「不会替您选一条路继续」。
2. **律师可读**——kind / riskLevel 翻成中文（`合同审查` / `高`），
   并有测试断言描述符里**不出现 snake_case 工程标识**（对齐 `requires-action.ts` 的既有口径）。
3. **未知 kind 原样展示**，不硬翻（不编造中文名）。

**接线方式**：`escalate` 下用**既有**的 `requiresConfirmation` 通道，而不是新造一种卡片类型。
该字段已经是「这件的办理口径需要律师确认」的既有表达，且已贯通到 UI；
新造卡片类型要动 `AgentTurn` 与 `buildRequiresActionsFromTurn`，而
`routeAsync` 只跑在 **engine 管线**（`engine/planning.ts`）而不在 agent turn 路径上
——跨层传一个描述符会牵动 task store schema，代价远大于收益。
选既有通道是**刻意的工程判断**，不是省事。

#### 两个实测抓到的同类 bug：无参调用读不到 `process.env`

两个bug 形状完全一样，都是「可选参数被当成默认值」：

| 位置                              | 症状                                                                | 修法                                                |
| --------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------- |
| `resolveRouteDivergencePosture()` | 主开关 `LAWMIND_ROUTE_DIVERGENCE=0` 失效（姿态仍被解析为 escalate） | 先问 `isRouteDivergenceShadowEnabled()`，主开关优先 |
| 同一个函数                        | `opts?.env?.X ?? ""` 在**无参调用**时永远拿不到 `process.env`       | 顶部显式 `const env = opts?.env ?? process.env`     |

第二个尤其阴——`opts?.env?.LAWMIND_...` 看起来像「优先 opts、回落 env」，
实际上 `opts?.env` 为 undefined 时整条链直接短路成 `""`，**生产路径（无参调用）静默失效**，
而带参调用的单测全过。两处都有测试锁定。

#### 一个真实的发现：分诊 `tier` 与路由 `riskLevel` 是**不同概念**

跑 shadow 用例时撞到的：`"查一下违约责任"` 让关键词与模型都判 `research.legal`(medium)，
而 `triage/rules.ts` 的 `simple-green` 判 `low`。于是 **kind 一致但 risk 经常不一致**。

这不是 bug，而是「分诊档位」（要不要先澄清）与「风险档」（要不要拍板）本就不同义
——只是此前没有任何东西把这种概念层不一致**变成可计数的对象**。
现已作为一条测试锁定，它也预告了 shadow 数据会包含真实信号（以及真实噪声）。

### 6.5 P3 落地结果（2026-09-20）

**落点**：`src/lawmind/metrics/firm-calibrator.ts`（新增，21 例测试）。

#### 产出的是「机制」，不是「可用的校准器」——这是刻意的

按 §3.5 的实测结论，本仓当前**只有 1 条可用样本**（门槛是 40 条，每类 ≥ 5）。
在这种数据上「拟合成功」比拟合失败更危险，所以本次交付的是：

- 完整的**特征抽取 + 标签派生 + 拟合 + 预测**管线；
- **冷启动门槛**（`COLD_START_MIN_SAMPLES = 40` / `COLD_START_MIN_PER_CLASS = 5`）；
- 未达门槛时返回 `status: "insufficient"` + 具体原因，**且 `predictEditProbability` 返回 `undefined`**。

最后一条是安全关键：**不返回「大概 0.5」**。给一个默认概率会让调用方以为有信号，
而那正是最危险的失败模式。参照 `metrics/north-star.ts`：
_Missing samples stay null — do not invent a 0% story_。

#### 特征（`FEATURE_VERSION = 1`，来自 `QualityRecord` 的既有字段）

| 特征                   | 来源                                             |
| ---------------------- | ------------------------------------------------ |
| `citationValidityRate` | `QualityRecord.citationValidityRate`             |
| `issueCoverageRate`    | `QualityRecord.issueCoverageRate`                |
| `riskRecallRate`       | `QualityRecord.riskRecallRate`                   |
| `reviewLabelCount`     | `reviewLabels.length`                            |
| `ruleHitCount`         | `reviewLabels` 中以「引用」开头的条数            |
| `snippetCharCount`     | 预留（当前恒 null）                              |
| `latencyLog`           | `log(latencyMs)`（做对数变换，原始毫秒跨数量级） |

**缺失特征保持 `null`，不编造 0**；拟合时用训练集均值填充，
均值与标准差**存进拟合产物**（`predict` 时必须复用，否则标准化口径不一致）。

`FEATURE_VERSION` 与 `lint/statute-params.ts` 的 `effectiveFrom` 是同一思路：
**特征是模型的一部分**，改了特征定义，旧拟合结果就不再有意义——产物必须能自证来历。

#### 为什么改成完整 logistic 回归，而不是原计划的「温度缩放 / Platt scaling」

Platt scaling 拟合的是 `p = sigmoid(a·s + b)`——**需要先有一个分数 s**。
而这个 s 只能来自手写的特征权重，那就是我在**替数据决定**什么重要。

在样本充足时这是不必要的假设；在样本不足时（我们现在的状态）它更危险——
一个手调权重的分数看起来像有依据，实际是我拍脑袋的偏好，且**不会随数据修正**。

所以改成：对标准化特征做完整 logistic 回归，权重**全部由数据学**。
样本不足时它自然拒绝输出，而不是输出一组我编的权重。

#### 确定性与可复现（法律软件的硬要求）

固定初始值 0、固定 600 步、无随机。有测试断言**同一份数据两次拟合得到完全相同的
权重、截距、均值、标准差**——参数要能写进审计并可在半年后复现。

#### 偏置声明（写进产物，不只是文档）

拟合产物的 `warnings` 必含两条，且有测试锁定：

1. `trainMetrics` 是**训练集**表现，**不是泛化估计**；样本量接近门槛时它几乎必然偏乐观。
2. 标签只来自走到拍板/审核的动作；**被静默放行的样本不在训练集中**，
   模型在「明显无需干预」的稿子上会**偏高估风险**（判成需要改动）。

第 2 条是无条件写死的——不靠调用方记得。`describeCalibrationFit()` 也明确标注「训练集准确率」。

#### 与「买一个概率模型」的区别

本模块产出的是**你自己的参数**：特征权重与校准系数拟合自**本所历史**，
零出网、零供应商、零边际成本，且**随使用增长**（厂商模型只随厂商升级）。
代价是冷启动——所以它是 P3，不是 P0。

| ------------------------ | --------------------------------------------------------------- |
| 特征抽取 / 标签派生      | **已落地**，可跑                                                |

## 7. P4 · 棘轮推广

`delivery/progressive-autonomy.ts:11` 的 `isAutonomyUnlocked` 已经实现「测量换信任」：`firstPassRate` + `lintEscapeRate` 双序列达标才解锁，且**刻意防了「橡皮图章一次通过」**（单靠 first-pass 不够，必须有逃逸序列对照）。

**P4 的动作只是扩域**：把这个棘轮从「交付类 × 律师」推广到「判断 × 判断项」。一个判断项能从 advisory 升 blocking，当且仅当：

1. 它的逃逸率序列达标（有数据、有对照）；
2. 样本量达标；
3. 退化时自动回锁。

**不需要新机制**——这正是把 P0 的数据接起来之后自然得到的东西。

### 7.5 P4 落地结果（2026-09-20）

**落点**：`src/lawmind/delivery/judgement-ratchet.ts`（新增，27 例测试）。
`delivery/index.ts` 已导出。

#### 升级判据选 precision（不是 recall）——因为危害结构翻转了

一个判断项从 advisory 升 blocking，意味着它**获得拦停交付的权力**。此时危害翻转：

| 阶段     | 漏报代价                       | 误报代价                                                     |
| -------- | ------------------------------ | ------------------------------------------------------------ |
| advisory | 律师没看到提示（他自己会看稿） | 无（只是多一行提示）                                         |
| blocking | 同上                           | **律师被迫处理一个不存在的缺陷**，多来几次就学会绕过整套机制 |

所以升级看的是**误报率**（`firedClean / firedSamples` 的代理），
而 `escapeRate` 作为**对照序列存在性检查**保留——这正是 `isAutonomyUnlocked`
那句 _A rubber-stamp first-pass series alone is not enough_ 的同一理由：
只看误报会退化成「越少报越好」，与「别漏」直接冲突。

阈值默认比交付侧更严：`maxFalsePositiveRate = 0.10` vs 交付侧的 `maxLintEscapeRate = 0.15`，
因为误报会直接挡住律师的路，而逃逸只是少一条提示。

#### 三条不变量与 `isAutonomyUnlocked` 逐条对应

| 不变量       | 交付侧（既有）                     | 判断项侧（本模块）                                     |
| ------------ | ---------------------------------- | ------------------------------------------------------ |
| 缺序列不解锁 | `lintEscapeSamples === null` 拒    | `missedAndEdited === null` 拒                          |
| 空序列       | `lintEscapeSamples === 0` **也拒** | `missedAndEdited === 0` **可通过**（有意的差异，见下） |
| 样本量达标   | `minSamples`                       | `minSamples`                                           |
| 退化自动回锁 | 纯函数                             | 纯函数                                                 |

**那处有意的差异**：交付侧「空序列」与「缺序列」都拒（没有逃逸就说明没人真的在审）；
判断侧空序列是**合法数据**——「该项从未漏报」就是好战绩，而 `null` 才是「没有这个维度」。
两者语义不同，所以不能照抄。有两条测试分别锁定。

**另外多加了一条硬前提**（计划 §4 铁律的落地）：`advisorAccepted`。
法律顾问未验收的项**一律拒绝**，且优先于任何统计判定——
依据 `lint/statute-params.ts:3`：_Wrong params are worse than no lint_。
一个判错的规则拿到拦停权，比它不拦更糟——它会教律师不信任整套核对。

#### 归因保守性：宁可少算，不要算错

`deriveJudgementItemSeries` 只在**一个判断项独占该任务的报项**时才把
`cleanDelivery` 记为它的误报。理由：决策样本的记录粒度是**任务**，
不是「判断项 → 律师动作」的因果链；一次交付里多个项报过时无法确定律师的改动针对哪一个。

代价是可用样本变少。这个取舍是刻意的：**判错的规则会拿到拦停权**，
所以宁可样本不够而拒绝升级，也不要靠猜测的归因升级。

#### 一处脏数据防御

若 `firedClean > firedSamples`（上游聚合错了），比例会 >1。概率量 >1 在 Doctor 里无法解释，
所以夹到 `firedSamples`（比例 = 1.0）。**这不掩盖问题**——1.0 仍会超上限被拒，
只是把它变成可读的形状。有测试锁定。

#### 能力状态（诚实）

| 项                                       | 状态                                                 |
| ---------------------------------------- | ---------------------------------------------------- |
| 棘轮判定（纯函数 + 三条不变量 + 硬前提） | **已落地**                                           |
| 批判决 + 按原因分组 + Doctor 摘要        | **已落地**                                           |
| 从决策样本派生序列                       | **已落地**（含独占归因保守性）                       |
| **在本仓产出可升级项**                   | **未达成**——无任何项有战绩（与 P0/P1/P3 同一处卡点） |

> 同前：**机器建好了，燃料还没到。** 但棘轮的价值恰恰在于——
> 数据到了的那一天，升级决定是**算出来的**，不是开会拍出来的。

## 8. P5 · 外部判定器的唯一正当位置

**前置条件（缺一不可）**：

1. P0–P4 已完成，资产已攒起来；
2. 已确认缺的是**异质独立性**（不是准确性——准确性由编译器 + 校准器解决）；
3. `egressMode: offline` 时它必须不可用。

**正当用法只有一个**：作为 P2.3 分歧驱动的**第三条独立判定器**。Jev 是另一家厂商、另一种训练目标（RLCD vs RLHF）、另一种模态（不生成），**独立性天然高于两个同源模型**，所以它的分歧信号信息量最大。

> 这也是唯一能诚实说出口的引入理由。**「它更快更便宜」不构成理由**——编译器路线在运行期是零成本，比它更便宜。

### 8.5 P5 落地结果（2026-09-20）

**落点**：`src/lawmind/models/decision-model.ts`（新增，27 例测试）；
`policy/workspace-policy.ts` 增四个配置键。

#### 为什么是「端口」而不是「接入 Jev」

计划 §8 的引入理由只有一条：当 P2.3 的第三条独立判定器。而分歧驱动的价值来自**独立性**
——这恰恰意味着 LawMind 需要的是**「一个足够异质的第三方判定者」这个能力**，
不是 TypeSafe 这个供应商。所以本模块定义 `DecisionModel` 端口，`createTypesafeDecisionModel`
只是第一个实现。有本地/自持等价物时（计划 §10 方案 C）换适配器即可，不动调用方。

端口只暴露**类型化问句**（`noul` / `choice` / `score`，对齐 Jev 原语）
——它不是又一个聊天模型，判定器不能自由生成文本。

#### 四条硬约束（全部有测试锁定）

| #   | 约束                               | 实现                                                                                |
| --- | ---------------------------------- | ----------------------------------------------------------------------------------- |
| 1   | **默认 `off`**                     | 三态 `off\|shadow\|on`，未写或 `off` → 返回 `null`；**不存在「配了 key 就自动开」** |
| 2   | **`egressMode: offline` 一票否决** | 在**读取任何其他配置之前**判定；连凭据都不读                                        |
| 3   | **凭据不全不产出半配置端口**       | baseUrl / apiKey / model 缺任一项 → `missing_credentials`                           |
| 4   | **不可用时不许编造**               | 端口返回 `undefined`，不返回默认答案（同 `firm-calibrator` 的「不返回大概 0.5」）   |

第 2 条值得单独说明：`LAWMIND-EGRESS-POLICY.md` §4 明确写着
「**模型 API 仍会出网**」——那是既有口径（对话模型是产品必需，无法一并封）。
但本模块**刻意不沿用那个豁免**：外部判定器是**新引入**的出站通道，
没有任何理由让它继承「离线仍出网」的通行证。
离线部署（律所内网全不出站）下它必须是死的，这与「离线模式 + 本地模型」的承诺一致。

#### 响应解析：只收合法值

第三方响应的形状不可信，所以逐项校验：

- `noul` 概率与 confidence 夹到 \([0,1]\)；
- **`choice` 的选项必须落在调用方给的 `options` 内**（防「编一个选项」）——
  与 `guardian` 的 `checklist_unknown_item` 同一原则；
- `score` 必须落在 `scale` 内；
- 问句里不存在的 id、type 不匹配的答案 → 丢弃；
- `answers` 里出现 `null` / 字符串 / 数组 → 跳过（实测抓到的崩溃，已修）。

任何失败（网络、超时、非 200、解析失败）→ `undefined`。
**第三方判定者不可用是正常状态，不是异常**，绝不能让调用方因此崩溃或降级到假数据。
空问句集时**不发请求**（零成本短路）。

#### 为什么不接进任何判定路径

计划 §8 的前置条件是「P0–P4 已完成 **且** 已确认缺的是异质独立性」。
前者已达成，**后者尚未确认**——因为 P2.3 的分歧数据还没有（工作区零记录）。

在拿到分歧数据之前接入，等于把一个**可测量**的缺口（正则与模型在哪类输入上打架）
换成一个**不可测量**的第三方承诺（它在中文法律语料上会怎么错，没人测过）。
所以本次只交付**端口 + 门禁 + 适配器**，由调用方在条件满足后显式接。

#### 诚实清单

1. **没有对该 API 做过真机验证。** 端点形状（`POST /v1/systemone`、
   `answers[].{id,type,probability,choice,score,distribution,confidence}`）来自公开文档与第三方
   评测，**不是**我实测的结果。首次启用前必须发一次真请求核对。
2. **无法验证其校准质量。** 厂商自评基准的参照标签由其他模型生成，第三方评测只有小样本。
   本文引用它，但没有把它当可信数字用——这也是为什么它排在最后一档。
3. **审计口径**：端口 id 形如 `typesafe.jev-latest`，进分歧记录以便区分「这票来自谁」。
   但**未做**审计链集成——按 `audit/hash-chain.ts:18`，canonical payload 是恰好六个字段，
   新增顶层字段会破链；接入时必须走 `detail` 或 sidecar。

### 9.1 实测发现：全量套件有 3 个时区边界 flake（**与本轮改动无关**）

2026-09-21 00:20（本地 UTC+8）跑全量套件时，3 个文件失败：

| 文件                                                          | 失败用例                                                 |
| ------------------------------------------------------------- | -------------------------------------------------------- |
| `src/lawmind/platform/outbound-proxy.test.ts`                 | writes outbound_http audit without request/response body |
| `src/lawmind/platform/safe-command.test.ts`                   | writes safe_command audit on exit                        |
| `apps/lawmind-desktop/src/renderer/lawmind-app-utils.test.ts` | formatRelativeTime covers recent buckets                 |

**根因相同**（已证）：这些用例用 **UTC** 日期算路径/期望值，而被测代码用**本地**日期时间。

- `safe-command.test.ts:151` / `outbound-proxy.test.ts`：`new Date().toISOString().slice(0,10)` 得到
  `2026-09-20`（UTC 日），而审计文件按**本地日**命名 → 本地 00:00–08:00（UTC+8）两者不等，
  `readFileSync` 抛 `ENOENT`。
- `lawmind-app-utils.test.ts:50-52`：`setHours(getHours() - 1)` 后期望 `今天`；
  本地 00:00–01:00 时减一小时落到**昨天**，于是返回 `昨天`。

**证明**：同一份代码在 `TZ=UTC` 下 **26/26 全过**；`git diff HEAD` 显示这三个文件**未被本轮改动**。

> 这条与本轮 P0–P5 无关，但它属于第十四期
> [LAWMIND-ITERATION-SPEED-AND-GUARDRAILS.md](./LAWMIND-ITERATION-SPEED-AND-GUARDRAILS.md)
> §1.6 已记录的「基线红 + flaky」，且 §5 明确把修 flaky 列为
> **与提速同等优先**。这里只做**精确归因**，未修（不在本轮范围，且避免与并行会话冲突）。
>
> **为什么它对本计划重要**：判断层整套论证的前提是「判定质量可测」。
> 一个每晚 00:00–08:00 随机飘红的套件，会让「这个改动有没有改坏判断」无法回答——
> 正是 §10.0 引用的那条结论：_在 flaky 修好之前，护栏给出的信号同样不可信_。
> 建议按 §5 的口径处理（三处都是同一形状：**测试用 UTC、代码用本地**，
> 修法是让测试与代码用同一时区口径，或注入时钟）。

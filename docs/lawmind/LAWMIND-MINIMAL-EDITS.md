# 最短改动（minimal edits）— 全链路的落槌硬约束

本文是 LawMind **所有**落槌修改的单一口径。它不再是「邮件合同短路径」的私规，也不是
`apply_surgical_edits` 一个工具的规矩，而是交付面（Word 修订轨 / 表格 / 跨文书）共同的硬不变量。

## 规则（一句话）

**一处改动里，没动的字必须留在修订轨之外；一句话里只改几个字，就只标那几个字。**

反例（同事无法逐处接受，也会冲掉对方手里的修订轨）：

```
- 甲方应当在收到发票之日起十日内付款，逾期按日万分之五计息。
+ 乙方应当在收到发票之日起五个工作日内付款，逾期按日万分之五计息。
```

正例（只标真正变动的字，中间那 11 个字原封不动）：

```
~~甲~~**乙**方应当在收到发票之日起~~十~~**五个工作**日内付款，逾期按日万分之五计息。
```

## 判定口径（可证明，与长度无关）

- **违反** = 一处改动内部夹着 ≥ `MINIMAL_EDIT_MAX_UNCHANGED_RUN`（6）个**连续未改文字**。
- **不违反** = 改动内部没有这样的连续未改文字。**长度本身不是罪名**：整句确实换成另一句、
  两侧没有任何共有片段时，那本身就是一处合法改动。

## 实现方式：重算，而不是拒绝

`src/lawmind/drafts/minimal-edit-script.ts` 的 `computeMinimalEditSpans(before, after)`：

1. 先摘掉两侧共有的前后缀（未改文字）；
2. 在中间反复找**最长公共片段（锚点，≥ `MINIMAL_ANCHOR_CHARS`=4）**，锚点即「没动的字」，
   从两侧同时摘掉后对左右两段递归；
3. 递归到某一段两侧不存在任何 ≥4 字公共片段时，那一段就是真改动，整段作为一处最短改动输出。

由 `MINIMAL_ANCHOR_CHARS (4) ≤ MINIMAL_EDIT_MAX_UNCHANGED_RUN (6)` 可得两条性质：

- **自动满足不变量**：构造出的每处改动内部都不含 ≥4 字的未改片段 → 不可能撞门槛；
- **不发明、不丢字**：把结果按位置回放到 before 上，逐字等于 after（锚点是两侧共有的原文）。

## 四个落槌边界（都在用同一函数）

| 边界                                       | 位置                                                                             | 做什么                                                                                                                                                                                          |
| ------------------------------------------ | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B1 模型输入**                            | `drafts/apply-surgical-edits.ts`                                                 | 不照抄模型给的 find 粒度：重算成多段最短改动后落槌，并在回执标 `minimalSplitEdits`；过度碎片化才退回收窄                                                                                        |
| **B2 hunk 生成**                           | `drafts/redline-proposal.ts` → `drafts/surgical-diff.ts::splitSurgicalEditSpans` | 所有模式（含 `mode: "section"`）都产出最短 span，不再出现「整节 hunk」直接落 Word                                                                                                               |
| **B3 文件落盘（最后一道）**                | `artifacts/render-docx-tracked.ts::resolveOfficeCliFindReplaceOps`               | 把每处 hunk 展开成多段最短 op，**从右到左**落盘（officecli 歧义锚点用 lookbehind，右侧先改不影响左侧锚点）；任一 op 歧义即整处跳过，不做部分成功                                                |
| **B4 Word 插件**                           | `integrations/word-addin/review-requests.ts::hunksFromRedlineProposal`           | 插件的锚点同样重算；纯插入改成「插入点之后 6 字锚点整体替换」，一个字都不删；过长的真换整节不上插件并如实计数                                                                                   |
| **B5 成品复核（唯一看实际 .docx 的一道）** | `drafts/tracked-xml-qa.ts::qaTrackedDocxXml`                                     | 导出后读 `word/document.xml`，按文档顺序取 `w:del`/`w:ins` 片段，检出「删/增相邻且几乎同句」（共有 ≥8 字且占较短一侧 ≥60%）。命中即 `ok:false` + `code: xml_qa_non_minimal_edits`，不当作已完成 |

计划侧边文件（`drafts/redline-plan.ts`）与跨文书一致改（`drafts/cross-document-edits.ts`）
也走同一重算：前者产出最短计划项，后者对全批一致地展开（避免「A 文书拆了、B 文书没拆」）。

B1–B4 作用在「要写什么」上；**B5 是唯一看落盘文件的**，断言「写出来的确实是那样」。
它的门槛刻意比 `MINIMAL_EDIT_MAX_UNCHANGED_RUN`(6) 更严（≥8 字且占较短一侧大半），
因为 officecli 可能把一处替换切成多个片段，要在**文件级**下断言就得收到「几乎不可能是巧合」的量级。

## 为什么这样比「find 太长就拒」好

- 拒绝只会把成本推给模型重试；**重算**直接给出律师要的结果，且不需要律师仲裁。
- 长度阈值会误伤真改写（整句换整句是合法的），也会漏掉「短 find 里夹了没动的字」。
  按「夹没夹未改文字」判定，两个方向都覆盖。
- 存量路径（意见书、诉讼文书、邮件短路径、Word 插件、工作台逐处接受）自动同口径，
  不必各写一套规则。
